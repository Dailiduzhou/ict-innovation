# AgeGuard：面向独居老人与异地亲属的 AI 关怀协作应用

> 文档性质：参赛方案与产品设计，不是已实现功能清单。
> 参赛方向：第十一届华为 ICT 大赛创新赛，赛题1「基于华为云产品打造 AI 创新应用」。
> 当前基线（2026-10-17）：**完整后端＋自制语音盒＋药盒开合节点＋家庭应用**。具体交互与药品规则见 [13 · 产品形态与硬件闭环](13-产品形态与硬件闭环.md)，未决实施项统一见 `12` §2.7。
> 商用穿戴健康数据仍无已验证接入通路；这不阻塞自制节点。SDK 文档支持、已决策与真机通过分开记录。既有 JPush／HMS 为待实测通知候选，Webhook 只补充，不替代站内待办或移动接收端。

## 1. 一句话介绍

AgeGuard 通过老人低负担的日常表达，将联系、帮助及用药提醒反馈整理成**经授权共享、可跟进、有处理记录的关怀事项**，帮助异地亲属了解需要并采取行动，而不默认暴露老人的全部聊天与健康信息。

核心流程：

```text
老人表达 → AI 理解与必要澄清 → 形成关怀事项
        → 检查共享授权 → 通知指定亲属 → 确认跟进 → 记录处理结果
```

产品价值不以聊天次数、接入硬件数量或模型调用量衡量，而以“是否准确理解需求、减少亲属的信息负担、让事项得到实际跟进”验证。

## 2. 背景、用户与价值假设

### 2.1 待验证的问题

- 老人不一定愿意或能够填写复杂表单，重要需求可能夹在日常聊天中。
- 异地亲属难以持续阅读全部记录；简单摘要也未必能说明“谁需要做什么”。
- 一次通知不代表亲属已看见，更不代表需求已解决。
- 直接共享完整聊天虽然便于查看，却可能损害老人的自主权和隐私。

以上是产品假设，需要通过访谈、场景测试和经同意的试用验证，不预先宣称已得到用户研究支持。

### 2.2 用户与权限

| 角色 | 主要需求 | 权限边界 |
| --- | --- | --- |
| 老人 | 低负担表达、获得提醒、查看自身记录、决定共享范围 | 信息主体与授权者，可查看、更正、删除和撤销共享授权 |
| 获授权亲属 | 了解需要跟进的事项、确认接手、反馈处理结果 | 仅访问明确授权的信息；亲属关系不自动赋予访问权 |
| 医疗人员 | 后续可能参考用户提供的记录摘要 | 首版不建设独立医疗端，不默认开放病史或聊天访问 |

首版面向能够表达意愿并完成授权的使用场景；需要代理授权、监护关系认定等特殊情况，不默认为已覆盖。

### 2.3 差异化与创新假设

1. **从摘要到行动**：将日常表达转成有来源、有接收人、有状态的关怀事项，而不只是生成聊天摘要。
2. **最小共享的家庭协作**：亲属获得必要事项，而不是默认获得全部原始对话。
3. **区分事实与推断**：自报、设备测量、模型提取、已确认事实分别标识，避免将推测包装成病史。
4. **可追踪的跟进流程**：通知、查看、接手、处理结果分开记录，避免“消息发出即任务完成”。

上述优势需要对照实验验证，不宣称市场上不存在类似功能。自制语音盒与药盒开合节点进入一期主交付；降低老人操作负担须与手机／普通通知对照。商用穿戴、跨品牌家居等仍是条件性扩展，不把未接通能力当作已实现创新。

## 3. 范围与非目标

### 3.1 首版计划

- 老人语音盒：按键录音、播报草稿、确认／取消和进度反馈；文字／Web 可先联调，但不能代替硬件验收。
- 自制药盒开合节点：真实事件、去抖、幂等、反复开合、设备状态及有限离线补传。
- 联系与帮助需求：想念亲属、希望通话、请求生活帮助等。
- 个人药品清单、获授权亲属代录、来源核对、计划／提醒新版本与个人别名；具体启用权限见 T-63。
- 按已核对且有效的确认计划执行提醒，分离设备观察、播放执行、人员反馈与协作跟进；开盖不证明服药。
- 身体不适的自述记录和求助提示，不进行自动诊断。
- 亲属端查看授权事项、确认跟进、记录结果。
- 授权管理、信息来源标识、分层记忆、修订与删除。
- 手机适配 Web 页面与在线 Demo。
- 移动通知接收端与主通道端到端验证；Webhook 为可选补充通知。
- 华为云部署、开发过程证据、场景测试及复现文档。

首个语音里程碑是按键式录音／播放，不以远场唤醒、全双工或完整 RN 为前置。第一版盒子无触摸屏，以说话／确认／取消为主要实体控件；布局、音频、供电和适老效果需样机测试。首版一盒一位主要老人，不把设备认证当作本人身份识别。

### 3.2 后续扩展

- iOS 客户端适配与推送验证。
- 天气、增减衣物、生活知识等辅助功能；涉及健康建议仍遵守非医疗边界。
- 经授权的记录摘要导出；先提供页面或 Markdown，按需要增加 PDF、DOCX。
- 符合准入条件的穿戴健康数据、智能家居事件及星闪接入。
- 根据评测需要增加语义／向量检索。

### 3.3 不做或不承诺

- 不诊断、不开处方、不自动调整药物、剂量或服用计划。
- 不替代医生、急救服务或可靠的实时安全监护。
- 不将无人回复、设备离线或数据缺失直接判断为发生危险或状态正常。
- 不以读取完整聊天作为亲属使用产品的默认条件。
- 不建设首版独立医疗工作台，不承诺医院系统对接。
- 不将模拟数据包装成真实设备接入，不声称已改善健康或临床结果。

## 4. 典型流程与领域对象

### 4.1 示例：希望联系亲属

老人说“最近有点想女儿，想跟她聊聊”。AI 判断是否需要澄清，提出联系事项；系统检查该类事项与目标亲属的授权，必要时询问老人。获准后创建亲属待办并推送通用提醒。亲属打开事项、确认跟进，联系后记录结果。

若老人拒绝共享，不创建对亲属可见的事项，也不通过通知摘要间接泄露。

### 4.2 示例：用药提醒与自报

系统按确认的计划提醒。老人说“今天吃过了”时，只记录“老人自报已服药”；说“昨晚没吃”时，先澄清是否指药物、哪次计划，不直接生成漏服结论。

需要亲属协助的反馈按授权进入跟进流程。模型不建议补服、加量或改变计划；药物问题提示联系专业人员。

### 4.3 主要领域对象

| 对象 | 作用与关键约束 |
| --- | --- |
| 用户与亲属关系 | 表达谁与谁关联；关系不等于权限 |
| 共享授权 | 记录主体、接收人、信息类别、授权状态及撤销情况 |
| 来源记录 | 保存被允许保留的自述、对话片段或设备记录及来源时间 |
| 记忆条目 | 区分确认状态，关联来源、时间和修订关系 |
| 关怀事项 | 描述待跟进需求，关联授权、来源、接收人和业务状态 |
| 设备与绑定 | 独立设备身份、作用域、主要使用者、解绑／撤销；不能直接信任消息自填用户 ID |
| 药品与个人别名 | 具体名称、剂型、规格、来源及状态；多候选澄清，换药／规格后重新检查别名 |
| 用药安排版本与提醒配置 | 原文／来源、录入核对人、生效版本、同步；提醒设置不等于治疗方案 |
| 设备事件与活动片段 | 稳定开合、幂等标识、时钟质量；原始物理次数与合并展示分开 |
| 提醒执行与人员反馈 | 播放／观察／自报／跟进四维分开，不误写“服药已核验” |
| 通知尝试 | 记录渠道、请求标识、失败原因及可取得的回执 |
| 跟进记录 | 记录亲属接手、行动与结果；不等同于通知点击 |

### 4.4 状态约束

- 关怀事项区分待澄清／待授权、待跟进、跟进中、已完成、已取消等业务状态；具体转换在实现时定义和测试。
- 通知状态单独记录：待发送、服务受理、送达（有可靠回执时）、失败或未知。
- 用户查看和确认跟进是业务事件，不能仅根据推送 API 成功返回推断。
- 无人回复保持待跟进，不自动标记已解决或发生危险。
- 撤销授权后，旧通知即使仍在设备上，打开时也须拒绝未获授权的详情访问。

## 5. AI、记忆与检索

### 5.1 AI 负责什么

AI 用于自然语言理解、必要澄清、事项提取、信息检索和摘要生成。对外共享、用药计划修改及事项完成等动作，由明确授权和业务规则约束。

不采用一个不受限制的 ReAct 循环控制全部业务。工具调用必须校验身份、授权、输入结构和可执行动作；模型输出是待验证的结果，不能直接成为数据库事实或越权指令。

### 5.2 记忆分层

1. **已确认事实**：经适当确认的偏好、联系安排等，保留来源与确认时间。
2. **待确认信息**：模型提取、含糊表达或冲突信息，不直接作为确定病史或用药依据。
3. **原始记录**：在授权和保留策略允许范围内保存，用于追溯与纠错。

老人自述、设备测量、亲属补充和 AI 推断分别标注。相互冲突时保留来源并澄清，不静默覆盖。记忆整理需去重、合并冗余、标识过期内容，避免无边界增长。

### 5.3 检索与删除

首版使用结构化记录与文本内容，优先全文检索；BM25 等排序能力按最终存储产品验证。向量检索是后续选项，全文检索同样可以为生成过程提供检索上下文，并非“只有向量库才算 RAG”。

允许查看、更正、删除记忆。删除需同步处理相关摘要与检索索引，并防止后台整理重新恢复已删除内容。审计不意味着永久保留全部敏感原文；原始记录、审计与备份的保留及删除期限需在真实试用前明确。

## 6. 客户端、推送与主动关怀

### 6.1 交互形态

- 老人日常主入口为语音盒；Web 仍提供查看、纠错、撤销和配置等辅助入口。
- 亲属 Web 提供待跟进事项、提醒与记录、药品与计划、家庭与设备四类页面，见 `13` §三。
- 移动轻量接收端承担登录、通用通知和事项入口，具体封装与主推送按 T-67 验证，不默认锁完整 RN。
- Webhook 可把通用提示发到获授权渠道；不把机器人发送成功当作亲属接手，也不能替代登录鉴权和站内待办。
- iOS 为后续适配；只有完成 AgeGuard 实测的平台才标为已支持。

### 6.2 移动推送候选与通知边界

既有候选 JPush 已查到 Android、iOS SDK 和服务端 REST API，HMS 为另一候选；不以团队曾试用过替代 AgeGuard 自身验证。Android 需集成对应客户端能力；iOS 需原生工程、APNs 等配置。服务端可通过 HTTP 调用，不据此假设存在所选语言的官方原生 SDK。

当前核对的推送 API 平台列表不包含浏览器 Web Push，不能把移动端 SDK 支持直接视为纯网页后台推送能力。Web Demo 与移动推送接收端分别验收。

推送设计要求：

- 事项及状态持久化在 AgeGuard 后端，JPush 只负责提醒入口。
- 凭据只存于服务端；设备注册标识与登录用户的绑定、解绑需鉴权。
- 默认推送“有一条新的关怀事项”等通用内容，不发送健康细节或聊天原文。
- 通知只携带不直接暴露内容的事项标识；客户端登录并重新鉴权后读取详情。
- API 受理、设备送达、通知点击和确认跟进分别记录，不能伪造缺失的回执。
- 对通知拒绝授权、离线、厂商渠道配置、配额及系统后台限制进行实测，不承诺必达。
- 推送失败保留站内待办，记录原因并有限重试；具体配额与费用待所用套餐核实。

### 6.3 主动关怀规则

用药提醒按确认计划执行；普通关怀遵守用户可配置的安静时段和频率上限。同一事项合并提醒，重复请求应避免重复创建事项或无节制推送。

不让 Agent 自行决定无限频次的“不定期关怀”。普通生活请求仍逐件确认。未反馈跟进可由老人预先明确授权接收人、触发、共享范围和频率，默认关闭、可撤销；执行时后端复核，无人回应也不扩大接收人。具体阈值见 T-62，不由模型自行决定漏服、补服或催服。

### 6.4 药品维护与开盖播报

获授权亲属可以代录和维护已有安排；关键修改形成带来源的新版本，不静默覆盖。家属对照原件核对不等于专业审核，老人同意不等于医学正确。资料不清或冲突只存草稿，不启用具体用法用量播报。OCR／AI 整理只产生待核对候选。

开盖默认只记录事件并提供可选入口；具体播报依赖有效、已核对计划和用户设置。总盖子无法辨识其中哪种药，不猜、不每次开盖朗读全部要求，不因反复开盖催服。注意事项保留来源和条件，采用受控文本，不让 LLM 现场生成个体化指导。

个人别名关联具体药品 ID，新称呼不能仅凭颜色、用途或一次含糊表达永久映射。多候选或关键动作须澄清；无法明确的“药快没了”可以形成请家人联系核对的草稿，不能擅自补药名。详细规则见 `13` §七。

## 7. 数据来源与硬件演进

### 7.1 数据来源及标识

| 来源 | 当前定位 | 必须保留的区别 |
| --- | --- | --- |
| 老人主动输入、问卷及自述 | 首版主要来源 | 自述不等于客观测量或专业诊断 |
| 获授权亲属的跟进反馈 | 首版协作来源 | 明确记录者和记录时间 |
| AI 提取与摘要 | 派生信息 | 关联来源和确认状态，不伪装成原始事实 |
| 自制语音盒与药盒节点 | 一期真实硬件交付目标 | 设备身份／事件可追溯；开合不证明吞服；尚未实测时只写计划 |
| 药品、安排原文与亲属代录 | 获授权的必要持久化资料 | 来源、核对、版本与同步状态；不宣称完全不存健康相关信息 |
| 合成测试数据与模拟设备事件 | 开发、异常测试和显式降级 Demo | 显著标注模拟，不计作真实设备交付或照护效果 |
| 穿戴测量与智能家居事件 | 条件性后续目标 | 接入许可、设备兼容性、授权与真实读取验证缺一不可 |

设备数据接入设计预留来源、指标／事件类型、单位、采集时间、接收时间、设备标识、质量及模拟标记。按实际能力渐进扩展，不提前建立庞大通用设备框架。

### 7.2 华为 Health Service Kit

已核实的不同路径：

- 当前 HarmonyOS 文档提供 ArkTS 示例，使用 `@kit.HealthServiceKit`。
- 官方 Android 接入 Codelab 提供 Java 接口，但教程使用旧工具链，不能照搬为当前版本配置。
- 官方存在云侧 REST API；接口存在不代表绕过资质审核或用户授权，也不意味着已核实 Python／Node.js 原生 SDK。

在本轮核对的 HarmonyOS 数据开放表中：

| 数据 | 开放等级 | 文档标注及时性 |
| --- | --- | --- |
| 步数、热量、距离等日常活动 | 基础 | 小时级 |
| 动态心率、静息心率、HRV | 高阶 | 小时级 |
| 血氧、压力 | 高阶 | 小时级 |
| 血压 | 高阶 | 分钟级 |
| 睡眠分期与睡眠记录 | 高阶 | 分钟级 |

等级通过浏览器渲染页面中的图标核对；文本抽取可能遗漏这些图标。该表不直接外推到所有 Android、REST 或历史版本接入路径。

当前官方资质说明要求个人开发者应用上架华为应用市场，高阶数据暂不向个人开发者开放。企业申请存在资本和成立年限要求；事业单位／政府机构主体可免除相关资金和年限要求，但不等于免审核，学生身份也不自动等于学校主体。

申请流程标注测试权限人工审核约10个工作日、测试阶段前100位用户限制；以实际申请时官方政策为准。设备连接与运动健康 App 后台状态影响及时性，“分钟级／小时级”不是可靠实时监护承诺。

### 7.3 华为 Health Industry SDK

官方存在 HarmonyOS、Android、iOS 分支，各平台能力不完全一致。HarmonyOS 5及以上 HRV 示例使用 ArkTS 和 `@huawei-cbg/health-industry-sdk`。

本轮核对的 HarmonyOS 申请路径要求企业实名认证、审核和开发证书，支持设备页列出 HUAWEI WATCH H7556 及最低固件要求。Android 页面列出明确的行业版型号和固件，不能将消费产品营销名称直接视为兼容证明。

所核对的 HarmonyOS HRV 文档说明每10分钟测量一次，活动状态下可能不出值，历史查询另有窗口限制。不能把“存在 HRV 接口”解释为连续、完整或任意设备可获取。

### 7.4 蓝牙、智能家居与星闪

- **蓝牙研究**：在自有或明确获准测试的设备上，研究公开广播字段、官方 GATT 服务或厂商公开协议。广播发现与连接后读取分别验证；不预设广播包含健康指标，不绕过配对、加密或访问控制。用户同意、协议许可、设备可读和健康信息处理合规是不同条件。
- **智能家居研究**：先确认具体型号、事件字段、授权机制及读取接口。HarmonyOS Connect 的设备接入能力不等于任意应用可读取智慧生活账号下所有门锁、灯具或传感器历史。
- **星闪研究**：持续考察目标设备、公开 SDK、授权和开发环境。满足条件后适配验证并发布支持清单，不预先承诺支持时间或全部星闪设备。连接技术不替代应用层数据接口与授权。

### 7.5 可承诺与不可承诺

可以承诺：预留必要的接入边界、明确来源与时间、按权限访问、验证后发布能力清单。

条件性目标：取得适用资质、平台许可、用户授权及兼容设备后逐步接入健康数据；以实际接口和真机结果决定指标及同步频率。

不承诺：第三方未来开放时间、任意手表可读健康指标、无限制跨品牌家居数据读取或可靠的实时监护。

## 8. 华为云架构与开发实践

### 8.1 逻辑架构

```text
语音盒 ─ HTTPS 音频；语音盒／药盒节点 ─ MQTTS → IoTDA
                  │ 已认证设备事件／下行及回执
Web 亲属端／辅助老人视图＋移动接收端
                  │ 鉴权后的业务请求
                  ▼
             AgeGuard 完整后端
  ┌──────────────────────────────────────┐
  │ 人与设备身份／绑定 │ 授权／事项与跟进  │
  │ 药品／计划版本     │ 事件／人员反馈    │
  │ AI 理解／记忆检索  │ 调度／通知／审计  │
  └──────────────────────────────────────┘
       │              │               │
  RDS 持久化      Redis 辅助能力     模型／语音服务
       │
  持久化发送任务 → 主推送＋补充 Webhook → 登录后读事项
                 → IoTDA 下行 → 盒子接收／执行／用户回执

  后续：获许可的商用穿戴／家居适配器 → 来源规范化
```

这是逻辑设计，不代表已部署。沿用 Python 后端方向；框架、数据库引擎、具体模型及音频服务仍需验证。IoTDA 应用侧 Python SDK 与设备端 SDK 不混用，语言与来源见 `08` §十二。

设备事件幂等、下行过期／版本、上下文确认、事务内持久化发送任务以及离线时钟／计划失效边界见 `13` §四～六。Redis 不是唯一任务账本；一台设备上线或收到命令不等于本次业务完成。

RDS 拟保存用户关系、授权、事项、计划、反馈及通知记录。Redis 拟用于频控、缓存或短期去重等辅助能力，具体边界待实现验证；不能只依靠易失缓存保存唯一任务或关键业务状态。全文检索及排序能力需结合最终数据库引擎核实。

### 8.2 CodeArts、Skills 与 Koo CLI

严格区分两类智能体：

- **开发阶段**：实际使用华为云码道 CodeArts 代码智能体，保留需求理解、代码生成、构建、问题修复和上线的过程证据。
- **产品运行阶段**：AgeGuard 的 AI 理解与关怀协作逻辑，不以它替代赛题要求的开发工具使用。

优先评估赛题提供的已有智能体、Skills 和一键部署案例，再补充项目专用内容。拟覆盖云资源检查、RDS／Redis 创建与关联、配置注入、数据库初始化、应用部署、健康检查及资源清理。Koo CLI 是待验证的执行工具之一，不宣称现有 Skills 已覆盖全部流程。

云操作须区分只读检查、资源创建和删除；费用或破坏性动作显式确认。凭据不进入代码仓库、提示词示例或公开日志。部署脚本需记录前提、版本、失败处理和复现步骤。

## 9. 安全边界与限制分类

| 外部条件／客观取舍 | 必须解决的系统问题 |
| --- | --- |
| 暂无健康数据接入资质 | 明确标注未接入，不能伪装已采集 |
| 药盒只观察开合，不能观察具体吞服 | 不误写服药完成；合并展示不能删掉真实多次动作 |
| 设备离线不能即时收到新版本 | 如实显示同步状态；旧计划失效／时间不可信时降级，不播过期用量 |
| 设备不支持某指标 | 按实际能力展示，不补造数据 |
| 蓝牙断连或云端同步延迟 | 显示时间与缺失状态，不用旧数据断言当前安全 |
| 移动系统或推送渠道限制送达 | 保留待办，正确记录未知／失败，不能标记亲属已查看 |
| 比赛阶段使用模拟回放 | 明确标注模拟，不宣称完成真机或临床验证 |
| 首版不做医疗端和高级硬件分析 | 如实限制产品范围，而不是隐藏未完成能力 |

健康信息、语音、对话及第三方 SDK 的处理需形成明确说明。真实试用前确定最小采集范围、模型及语音服务的数据流向、存储位置、保留期限、撤销和删除流程，并完成必要的合规核验。非医疗定位不免除隐私保护责任。

## 10. 数据集、评测与验收

### 10.1 测试数据与对照

第一阶段建立可复现的合成场景集，记录生成／编写方式、版本和人工标注规则，不冒充真实老人语料。用于调试与最终评测的场景应分离，避免在同一批样例上反复优化后报告泛化效果。

覆盖正常需求、含糊表达、否定、拒绝共享、权限撤销、记忆冲突、重复事项、服务失败、设备离线及模拟数据标识。标注预期提取信息、是否澄清、允许接收人和合法状态转换。

对照普通聊天摘要／人工查看原始对话，比较理解和完成相同任务的表现。后续真实家庭试用须征得同意，数据与模拟测试分开报告，不默认将真实私密记录公开开源。

### 10.2 拟采用指标

| 类别 | 指标或观察项 | 报告要求 |
| --- | --- | --- |
| 事项提取 | 精确率、召回率，错误与遗漏案例 | 说明标注标准、样本量及测试集版本 |
| 澄清与事实区分 | 歧义处理正确率、自报被误写为客观事实的案例 | 不仅展示成功样例 |
| 授权与隐私 | 越权访问／共享、撤销后访问测试 | 报告实际测试范围；发现越权问题须阻断真实试用 |
| 通知可靠性 | API 受理、可观测送达、失败、未知、重复提醒 | 分母和平台分别列明；不混用受理率与送达率 |
| 流程正确性 | 状态转换、失败恢复、待办持久化 | 场景测试通过不等于真实照护效果 |
| 用户价值 | 理解耗时、确认及跟进情况、操作困难 | 区分模拟任务与真实试用，说明样本限制 |
| 开发与部署 | 干净环境复现成功情况、部署耗时、人工干预步骤 | 保留执行环境、日志及失败记录 |

不预填目标准确率或成果数字；数值目标在确定测试集、基线和资源后制定。没有临床研究不宣称改善健康结局。

### 10.3 比赛 Demo 建议

1. 老人表达联系需求，AI 澄清并展示待共享事项。
2. 老人确认授权，亲属 Android 端收到不含敏感详情的通知。
3. 亲属打开详情、确认跟进并记录结果，老人端看到状态变化。
4. 展示用药提醒与“老人自报已服药”的来源区别。
5. 演示拒绝共享或撤销授权后无法读取详情。
6. 用空盒演示真实开合、网络重传、反复开盖但无人员反馈；不产生服药已核验结论。
7. 展示药品代录的来源／新版本、简称歧义及离线旧计划失效边界。
8. 展示通知失败仍保留待办；模拟／回放仅作为显式补充，不能抵扣硬件验收。
9. 展示 CodeArts 与 Skills 的实际创建、关联、部署及验证证据。

以上是验收脚本，只有实际完成的部分才能作为参赛成果展示。运行故障时可以展示已录制证据，但不得把回放伪装成实时执行。
