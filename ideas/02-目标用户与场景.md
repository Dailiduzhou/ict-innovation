# 02 · 目标用户与场景

> 来源：`archive/original/方案优化建议.pdf` 末尾的追问 ——
> *"AgeGuard 希望主要服务于认知能力基本正常、但数字素养较低的独居老人，还是希望进一步覆盖存在轻度认知困难的老人？"*
>
> 这是**评审直接提出的问题，必须回答**。本文件给出建议答案 + 待访谈验证的事项。

---

## 一、三类角色（沿用 v2 定义，补上画像）

### 角色 A：老人（主用户）

**建议锁定的人群（决策 D-05）：**

> **会使用智能手机、认知能力基本正常，但在复杂操作上容易受挫、容易漏跟进的独居/空巢老人。**

理由：
- **"完全不会用智能手机"的老人** → 需要实体设备或无屏交互，成本极高，超出三人大学生团队能力
- **"有轻度认知困难的老人"** → 涉及医疗辅助定位、伦理审查、监护人授权模型，风险与合规成本不适合大创/ICT 赛的 3 人规模
- **"会用但用得吃力"的老人** → 有明确痛点、有智能手机、能配合测试，是**可触及且有价值**的群体

**画像表：**

| 维度 | 描述 |
|---|---|
| 年龄 | 65–80 岁为主 |
| 居住 | 独居 / 空巢（子女在异地） |
| 健康 | 有 1–2 种慢性病，但生活自理 |
| 数字素养 | 会用微信收发消息、会视频通话；不会用复杂 App、不会填长表单 |
| 沟通偏好 | 倾向语音；文字输入慢；对"要点很多次"没耐心 |
| 情感需求 | 怕打扰子女；需求表达含糊、绕弯子 |
| 设备 | 智能手机（**不预设一定是华为**，见 §四） |

### 角色 B：亲属（老人子女 / 亲戚）

| 维度 | 描述 |
|---|---|
| 年龄 | 30–55 岁 |
| 特征 | 工作忙、异地、对父母有愧疚感 |
| 痛点 | 收到消息时在忙，回头忘了；不知道父母到底有没有被照顾好 |
| 关注 | **不想被大量无关信息淹没**，只想看到"需要我做的事" |
| 顾虑 | 隐私（不想让所有亲戚都看到）；被指责"不孝顺" |

### 角色 C：医疗人员

> ⚠️ **建议从 MVP 中移除，降级为远期设想。**
>
> 原因：
> 1. 医疗人员的核心需求是**病史、用药记录、客观检查数据**——而这些数据的获取路径已核实为受限或不可得（`06` §2）
> 2. 引入医疗角色会触发**医疗数据合规**问题（个人健康信息属于敏感个人信息）
> 3. 三方协作会使产品复杂度翻倍，而三人大学生团队无法在 8 个月内验证三方价值
> 4. v2 的四个组成部分里**本来就没有医疗端**——v1 有，v2 已经砍了，这里只是把砍掉的动作明确化

**保留方式**：在 `08` 中记为"远期扩展"，在申报书中写为**主动的边界取舍**。

## 二、核心场景清单

### S1：模糊需求 → 澄清 → 成为事项（主场景，答辩必演）

```
老人："家里米快没了，谁有空周末帮我带一袋？"
  ↓ Agent 提取：动作=购买大米，时间=周末，对象=未指定
  ↓ 对象缺失 → Agent 追问
Agent："您是想请哪位家人帮忙？"
老人："问问我儿子吧。"
  ↓ 生成草稿（内容 + 接收人 + 分享范围）
Agent："我准备把这件事告诉小陈：『家里米快没了，周末方便带一袋吗？』可以发送吗？"
老人："可以。"
  ↓ 老人确认 → 创建事项
  ↓ 亲属端收到 → 接手 → 处理中 → 完成反馈
  ↓ 老人端状态同步 → 老人知道"有人接手了 / 已经办好了"
```

### S2：潜在需求推断（对应优化建议的"多假设推理"）

```
老人："最近家里挺冷清的。"
Agent："最近是不是比较想和家里人聊聊天？"          ← 假设 1，用提问而非断言
老人："是啊，女儿工作忙，我也不好总打扰她。"
Agent："我可以帮您问问她，这周有没有方便通话的时间。您愿意吗？"
老人："愿意。"
```

**规范要点（来自优化建议，非常重要）：**
> - Agent 可以识别表达中的**情绪线索**，但**不应直接推断老人的心理状态**
> - 对**证据不足的需求**，不直接认定其真实性，而是通过**自然、低负担的交互进行澄清**
> - 长期记忆**可以辅助识别可能的协作对象，但不能替代用户对具体行动的确认与授权**

### S3：约定时间已过但无反馈（对应"上下文感知的动态任务规划"）

```
Day 1  老人同意创建关怀事项
Day 2  女儿收到通知，选择"周六下午联系妈妈" → 系统记录联系安排
Day 3  系统发现约定时间已过，无完成反馈
       → 在**频率限制内**询问女儿："之前约定的联系事项还没有记录结果，是否已经完成？"
       女儿确认已完成
Day 4  老人："昨天和女儿聊了很久，挺开心的。"
       → 系统识别这可能是对之前关怀事项的反馈
       → 在**必要确认后**关联历史事项并更新状态
```

### S4：任务条件变化 → 重新分配（对应"多主体任务协作"）

```
亲属 A 无法处理 → Agent 结合历史协作关系 + 当前反馈 + 任务要求生成替代方案
                → 通过多轮协商推动任务调整
```

**强制规范（优化建议原文）：**
> 涉及**新增接收人、扩大信息共享范围或改变重要安排**时，**必须重新确认用户意愿并完成必要授权**。

### S5：失败与异常路径（答辩必须演示）

| 场景 | 期望行为 |
|---|---|
| 网络错误 | 明确提示，草稿不丢失，可重试 |
| 工具调用失败 | 告知用户"没能创建成功"，不静默失败 |
| 重复提交 | 幂等处理，不产生重复事项 |
| 亲属长时间未响应 | 状态变为"待跟进"，按频率限制提醒，不轰炸 |
| 老人中途反悔 | 随时可取消草稿或撤销已分享事项 |
| 语音识别错误 | 老人可修改草稿文本后确认 |
| 澄清轮次过多 | **设置澄清轮次上限**，允许用户随时中断（优化建议明确要求） |

## 三、目标用户验证计划（`07` 的输入）

**必须做，且必须在初赛材料截止（2026-12）前完成第一轮。**

| 阶段 | 时间 | 对象 | 方法 | 产出 |
|---|---|---|---|---|
| R1 需求访谈 | 2026-11 | 5–10 位老人 + 5 位家属 | 半结构化访谈 | 痛点清单、现有工具使用情况、信息共享顾虑 |
| R2 概念测试 | 2026-12 | 5 位老人 | 纸质/线框图走查 | 首页入口是否可理解、确认流程是否可接受 |
| R3 可用性测试 | 2027-01 | 8–10 位老人 + 家属 | 真实任务（提出需求→确认分享→查看进度） | 任务完成率、操作时间、卡点 |
| R4 闭环验证 | 2027-02 | 3–5 个家庭 | 2 周真实使用 | 事项闭环率、亲属响应率 |

### 3.1 访谈提纲（R1 用，20–30 分钟/人）

**对老人：**
1. 您平时怎么跟子女联系？多久一次？
2. 有没有过"想让子女帮忙做件事，但最后没说"或者"说了但没下文"的情况？能举个例吗？
3. 那种时候您会怎么处理？会觉得不好意思催吗？
4. 您现在手机上装了哪些 App？哪个用得最熟？
5. 如果有个 App 能帮您把想说的整理成一条"事情"发给孩子，您觉得有用吗？会有什么顾虑？
6. 您愿意让孩子看到您说的哪些内容？哪些内容不想让他们看到？

**对家属：**
1. 父母上次请您帮忙做一件具体的事，是什么时候？后来怎么样了？
2. 有没有过"当时忙，回头忘了"的情况？后来怎么处理的？
3. 您希望知道父母的哪些情况？不希望被哪些信息打扰？
4. 如果收到一个"父母需要您做 X"的通知，您希望它长什么样？
5. 您会担心隐私问题吗？比如其他亲戚也能看到？
6. 您觉得这类工具最可能在哪一步失败？

### 3.2 访谈必须记录的伦理事项

- 知情同意（口头 + 记录）
- 不采集不必要的个人健康信息
- 老人可随时退出
- **不得在未获授权的情况下录音录像**
- 大创项目涉及人体被试的，需确认学校是否要求**伦理审查**（`08` T-06）

## 四、平台假设（已按 D-07 修订）

> ✅ **决议（2026-10-14）D-07：前期主要适配 Android**，完整理由与推送链路见 [`11-客户端与推送方案.md`](11-客户端与推送方案.md)。

**仍然成立的一个风险点**（保留于此处作为提醒）：

> **不要把产品定位成"华为手机专用"。**

理由：目标用户是"会用智能手机的中国城市独居老人"，其中相当比例用小米/OPPO/vivo/荣耀。
而 `06` 的核查表明，华为侧能力（Health Kit / 星闪 / HarmonyOS Connect / HMS Push）都有强平台绑定。

**结论（双轨）**：
- **平台层**：Android 优先，但**不绑定华为硬件**——用 `PushChannel` / `VitalSource` 抽象层隔离（`09` §3 / `11` §三）
- **华为技术**：只作为**赛题要求的技术栈**（华为云）与**可选增强**（Push Kit、Health Kit），
  并在方案中明确标注"该能力仅对 HarmonyOS / 华为设备用户可用"
