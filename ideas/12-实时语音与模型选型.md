## 二、`qwen-audio-3.1-realtime-plus` 核实结果

### 2.1 事实（阿里云百炼 / Model Studio）

| 项 | 内容 |
|---|---|
| 定位 | **实时双工语音对话模型**，"支持文本和音频输入输出、**工具调用**、**联网搜索**及声音复刻" |
| 默认音色 | `longanqian_v3.1` |
| 上下文长度 | **262,144** tokens |
| 最大输入 | 245,760 tokens |
| 最大输出 | **16,384** tokens |
| 接入协议 | **WebSocket**、**AOQ**、**WebRTC** |
| 地域 | 华北2（北京）、新加坡 |

### 2.2 价格（华北2 北京，每百万 Token）

| 文本输入 | 音频输入 | 文本输出 | **音频输出** |
|---:|---:|---:|---:|
| 5 元 | 40 元 | 40 元 | **150 元** |

> ⚠️ **音频输出 150 元/百万 token 是本项目最大的单项成本风险。**
> 实时语音对话是 token 消耗大户（音频 token 密度远高于文本）。
> → 记为风险 **R-26**；对策见 §七。

### 2.3 三种交互模式（**对老人场景价值极高**）

| 模式 | 说明 | 对 AgeGuard 的意义 |
|---|---|---|
| `server_vad` | 声学 VAD，服务端自动判断起止 | 基础可用 |
| **`smart_turn`** | **"融合声学感知与语义理解判断轮次边界，无意义附和声（如"嗯""啊"）不会打断对话"** | ⭐⭐⭐ **这是老人场景的关键能力** |
| `push-to-talk` | 手动控制 | 可作为老人端的"按住说话"备选 |

> ⭐ **`smart_turn` 直接解决了本项目的一个真实痛点**：
> 老人说话常带语气词、停顿长、自我重复。传统 VAD 会被"嗯""啊"打断，体验很差。
> **这一条应该写进申报书的技术方案**——它证明我们不是随便选了个模型，而是**按场景特征选的**。

### 2.4 ⚠️ 一个必须绕开的硬约束

> 官方原文：**"联网搜索通过 `enable_search` 开启，不能与 Function Calling 同时启用。"**

**这与 AgeGuard 的 Agent 架构直接冲突**：`04-AI-Agent设计.md` 的工具集（`create_item_draft` / `query_item_status` / `write_memory` …）全部依赖 Function Calling。

**解决方案见 §四** —— 不要用 `enable_search`，而是把联网搜索**包装成自己的工具**。

### 2.5 Python SDK

| 项 | 内容 |
|---|---|
| 官方 SDK | **`dashscope`**（PyPI） |
| 版本要求 | 实时多模态 ≥ **1.26.5**；实时语音合成 ≥ 1.25.11 |
| 官方示例仓库 | [`aliyun/alibabacloud-bailian-speech-demo`](https://github.com/aliyun/alibabacloud-bailian-speech-demo) |
| 示例说明 | "qwen-audio-realtime API 的 **Python SDK 与示例** —— 基于 WebSocket 的实时语音对话服务" |
| SDK 结构 | `fun_realtime/` 负责 WebSocket 连接、事件序列化、会话配置、音频编解码工具；**有意保持精简**（无轮次状态机、无内置路由器），便于集成进自己的架构 |
| 示例应用 | 陪伴对话等三种模式 |

> ✅ **`fun_realtime` "有意保持精简" 这一点很适合我们**——它不预设架构，
> 正好可以套进 `04` 的 Agent 主循环和 `09` 的端口设计，不会打架。

## 三、豆包（Seeduplex）核实结果

### 3.1 事实（火山引擎）

| 项 | 内容 |
|---|---|
| 模型 | **豆包实时语音模型 3.0（Seeduplex）** —— "全双工端到端语音大模型，提供低时延、高拟人的实时语音对话能力" |
| 新协议地址 | `wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue` |
| 旧协议地址 | `wss://openspeech.bytedance.com/api/v3/realtime/dialogue` |
| 协议形态 | 标准化 Realtime 事件语义（`session.create` / `input_audio_buffer.append` / `conversation.item.create` / `response.cancel` …），WebSocket 纯 JSON 文本帧 |
| 必填 Header | `X-Api-App-ID` / `X-Api-Access-Key` / `X-Api-Resource-Id` / `X-Api-App-Key` |
| **联网搜索** | **通过 `extension` 透传**（与"唱歌"并列的专有能力） |
| **工具调用** | session 对象内含 **`tools`** 字段 → 支持 |
| 官方示例 | **Go 示例 + Python 示例**；另有 Web Demo 可快速体验 |
| ⚠️ 注意 | "3.0 采用全新的 Realtime 事件协议，**与原版本差异较大**，接入前请务必先完整阅读《接入必读》" |

> ⚠️ **注意协议地址差异**：新协议 `/v3/duplex/realtime/dialogue`（Seeduplex 3.0）
> 与旧协议 `/v3/realtime/dialogue` 不同。网上的教程多数是旧协议的，**照抄会踩坑**。

### 3.2 社区 Python 参考

- [`SUAT-AIRI/RealtimeDialog-doubao`](https://github.com/SUAT-AIRI/RealtimeDialog-doubao)（MIT）：基于火山引擎豆包实时语音接口的 Python 语音交互示例，支持麦克风实时对话 / 本地 WAV 单轮问答。
- 有第三方代理把豆包包装成 **OpenAI Realtime 协议兼容**（`wss://.../v1/realtime?model=doubao-realtime-...`），可用标准 OpenAI Realtime SDK 接入。

> ⚠️ 社区项目**不是官方支持**，评估时不要当依赖。

### 3.3 Qwen vs 豆包 对比

| 维度 | Qwen `qwen-audio-3.1-realtime-plus` | 豆包 Seeduplex 3.0 |
|---|---|---|
| 中文文档完整度 | ⭐⭐⭐ 最全，中文一手文档 | ⭐⭐ 较全 |
| 官方 Python SDK | ✅ `dashscope` + 官方示例仓库 | ⚠️ 官方文档只有示例代码，SDK 需自行封装 / 用社区 |
| 轮次判定 | ⭐⭐⭐ **`smart_turn`（语气词不打断）** | ⭐⭐ 需核实 |
| 工具调用 | ✅ Function Calling | ✅ session.tools |
| 联网搜索 | ⚠️ `enable_search`，**与 FC 互斥** | ✅ extension 透传（是否与 tools 互斥待核实） |
| 协议 | WebSocket / **AOQ** / WebRTC | WebSocket |
| 价格 | 已核实（音频输出 150元/M） | ⚠️ 待核实 |
| 声音复刻 | ✅ | 有声音复刻产品（另计） |

> **倾向 Qwen**：不是因为它更好，而是因为①中文一手文档最全（赶工期时这点最重要）
> ②`smart_turn` 恰好命中老人场景 ③有官方 Python SDK 与示例，少踩坑。
> 但要**保留可替换性**（§六）。

## 四、联网搜索的设计（绕开 `enable_search` 的互斥）

### 4.1 问题

```
AgeGuard Agent 需要：Function Calling（创建事项、查状态、写记忆）
AgeGuard 也需要：  联网搜索（天气、生活小问题） ← v1 idea.md 明确要求
Qwen 的约束：       enable_search 与 Function Calling 不能同时启用
```

### 4.2 ❌ 不要用的方案

| 方案 | 为什么不行 |
|---|---|
| 开 `enable_search`，放弃 FC | Agent 废了，退化成聊天机器人 |
| 按"模式"切换（闲聊开搜索 / 事务开 FC） | 用户一句话可能同时含闲聊和事务；且模式判定本身又要 FC |
| 豆包 extension 搜索 | 同样面临"是否与 tools 互斥"的未知；换供应商等于重新踩坑 |

### 4.3 ✅ 推荐方案：把搜索包装成自己的工具

```
Function Calling 工具集（04 §二）新增：
  web_search(query: string) → {answer, sources[]}
      │
      └── 后端（Python）调第三方搜索 API
          然后用 FC 的 observe 结果喂回模型生成话术
```

**为什么这个方案更好：**

| 收益 | 说明 |
|---|---|
| **不冲突** | 全程只用 Function Calling，不碰 `enable_search` |
| **可控** | 搜什么、什么时候搜、结果怎么用，都在我们手里 |
| **可引用** | 能强制模型返回来源（`04` §8 的证据等级思路一致） |
| **可审计** | 搜索行为进 `ItemEvent` 审计表 |
| **可替换** | 搜索供应商可换（博查 / Tavily / 夸克 / 自建） |
| **答辩友好** | 这是"Agent 工具设计"的正面例子，不是"调了个开关" |

> 顺带解决一个隐患：`enable_search` 是模型自主决定要不要搜，
> 而**老人场景更希望"搜不搜"是可控的**（避免答非所问、避免把无关信息说给老人听）。

## 五、⚠️ 华为云没有对等的端到端实时语音（客观限制）

既然赛题一要求"基于华为云产品"，必须评估华为云自己的方案：

### 5.1 已核实事实

| 华为云产品 | 能力 | 是否是端到端实时语音 |
|---|---|:--:|
| **MaaS（模型即服务）** | 大模型 API 调用；支持流式输出、深度思考、**工具调用**；模型含 `openPangu-2.0-Pro/Flash`、DeepSeek-V4-Flash 等 | ❌ 文本/多模态 LLM，**无实时语音** |
| **SIS（语音交互服务）** | 实时语音识别（ASR，WebSocket，支持连续模式+端点检测）、语音合成（TTS） | ❌ **ASR/TTS 分离**，非端到端 |
| ModelArts | 模型训推平台 | ❌ |

**约束细节**：MaaS 标准 API V2 `https://api.modelarts-maas.com/v2/chat/completions`
**仅支持"西南-贵阳一"区域**；鉴权 `Authorization: Bearer $MaaS_API_Key`；官方提供 **Python 示例**。

### 5.2 结论（**这是一条正当的客观条件限制**）

> 华为云目前在实时语音上的技术路线是 **SIS（ASR）+ MaaS（LLM）+ SIS（TTS）三段拼接**，
> **不提供 `qwen-audio-3.1-realtime-plus` / 豆包 Seeduplex 那样的端到端全双工实时语音模型**。
>
> 三段拼接路线的问题：
> 1. **延迟叠加**（ASR 出结果 → LLM 推理 → TTS 合成，链路长）
> 2. **不支持真正的全双工**（无法在模型说话时被打断）
> 3. **不支持语义轮次判定**（`smart_turn` 这类能力无从实现）
>
> 而本项目目标用户是**口语化、带语气词、停顿长的老人**，
> 全双工与语义轮次判定**恰好是体验的决定性因素**。
>
> 因此：**实时语音通道采用第三方端到端模型；华为云承担平台与 Agent 侧职责。**

> 📌 **这正是 `AGENTS.md` 要求的"客观条件限制"**：
> 换一支更强的团队也拿不到华为云的端到端实时语音——因为**这个产品不存在**，不是我们没做好。
> → 在材料中按 `09` §6.1 的分层写法如实陈述，并给出替代路径。

### 5.3 ⭐ 推荐的双模型分工（两全其美）

```
┌──────────────────────────────────────────────────────────┐
│  实时语音通道  →  qwen-audio-3.1-realtime-plus            │
│  职责：全双工对话、VAD/smart_turn、流式 ASR + TTS          │
│  理由：华为云无对等产品（§五）；smart_turn 命中老人场景     │
├──────────────────────────────────────────────────────────┤
│  Agent 推理 / 工具调用  →  华为云 MaaS（openPangu）        │
│  职责：事项抽取、多假设推理、工具编排、记忆整理            │
│  理由：①赛题一"基于华为云产品"的技术栈体现                  │
│        ②MaaS 支持工具调用，正好承载 04 §二 的工具集         │
├──────────────────────────────────────────────────────────┤
│  后端服务  →  Python，部署在华为云 ECS（10 §七）           │
│  数据  →  华为云 RDS + Redis（赛题一强制项）               │
└──────────────────────────────────────────────────────────┘
```

**这样做的三个好处：**
1. **赛题技术栈扎实**：RDS / Redis / MaaS / ECS / CodeArts 都是华为云
2. **语音体验不打折**：拿到目前最好的中文端到端实时语音
3. **材料可解释**："我们在语音通道上做了客观限制的取舍，并给出了理由" —— 是加分项

> ⚠️ **但要在申报书里主动说明**为什么语音不用华为云（否则评委会问）。
> 按 §5.2 的口径写，并把 §5.1 的核实结论作为依据。

## 六、架构：三个 Provider 抽象

沿用 `09` 的端口—适配器模式，语音侧也做抽象：

```typescript
// TS 侧（客户端）
interface RealtimeVoiceProvider {
  capabilities(): Promise<{
    fullDuplex: boolean;          // 是否全双工（可打断）
    semanticTurnDetection: boolean; // 是否有语义轮次判定
    supportsTools: boolean;
    latencyClass: 'realtime' | 'near-realtime' | 'turn-based';
    available: boolean;
    unavailableReason?: string;
  }>;
  connect(session: VoiceSessionConfig): Promise<VoiceConnection>;
}
```

| 实现 | 阶段 | 说明 |
|---|:--:|---|
| `QwenRealtimeProvider` | 一期 | WebSocket / AOQ 接入 `qwen-audio-3.1-realtime-plus` |
| `DoubaoSeeduplexProvider` | 备选 | 若 Qwen 不可用/成本超预算 |
| `HuaweiSisProvider` | 可隆 | **ASR + TTS 三段拼接**，`capabilities()` 返回 `fullDuplex: false`，作为降级路径 |
| `MockVoiceProvider` | 演示 | 与 `09` 的 mock 规矩一致（必须带徽标） |

> ⚠️ **本抽象只管"语音通道可替换"**。语音层与 Agent 层的连接方式（`request_task` 工具桥）
> 是另一层的事 → 见 [`14-语音层与Agent层分工.md`](14-语音层与Agent层分工.md) §五 / §九。
> ❗ 语音层**只调 `request_task` 一个主工具**，不直接调 `04` §二的 12 个工具（否则两层都在判意图）。

> ⭐ **把 `HuaweiSisProvider` 实现为可用的降级路径**，即使一期不用——
> 这样答辩时可以演示"当外部语音服务不可用时，系统自动降级到华为云分段方案"。
> 与 `09` §3.2 的 `HuaweiSmartHomeSource` 空占位是同一个思路：**把限制编码进系统**。

后端同理：

```python
class AgentProvider(Protocol):
    def chat(self, messages, tools) -> AgentResponse: ...

class MaaSProvider(AgentProvider):      # 华为云 MaaS / openPangu
class DashScopeProvider(AgentProvider): # 阿里云百炼（备用）
```

## 七、成本控制（音频输出 150 元/百万 token）

| 措施 | 说明 |
|---|---|
| **开发期用便宜的模型** | `qwen-audio-3.0-realtime-flash` 做联调；只在演示/评测时用 `-plus` |
| **限制单次通话时长** | 老人闲聊设上限（如 5 分钟），超时温柔收尾 |
| **服务端 VAD 前置过滤** | 静音不上行（官方连续模式本就丢弃静音，但客户端也别发） |
| **按需启停会话** | 不聊天时**断开 WebSocket**，不要挂着 |
| **本地 mock 优先** | 客户端开发全程用 `MockVoiceProvider`，不烧 token |
| **每日额度告警** | 在百炼控制台设预算告警 |
| **代金券优先** | 先确认华为云代金券能否覆盖；百炼需另充值 |

> ⚠️ **代金券的坑**：华为云代金券**只能用于华为云**。
> 阿里云百炼 / 火山引擎**需要另外付费**。
> 这是一笔真实的自付成本，必须先算清楚（记入 `08` 待验证 T-21）。

## 八、后端语言：Python（已定）

| 项 | 结论 |
|---|---|
| **决定** | ✅ **Python** |
| 依据 | 双方都有 Python 支持：Qwen 有官方 `dashscope` SDK（实时语音 ≥1.26.5）；豆包官方文档提供 Python 示例；华为云 MaaS 官方提供 Python 示例 |

**Python 侧要写的模块：**

| 模块 | 职责 |
|---|---|
| `agent/` | ReAct 循环、工具编排（`04` §二） |
| `tools/web_search.py` | **§4.3 的自建搜索工具** |

| `services/` | 事项状态机、权限、提醒调度（`03` §五） |

| `memory/` | 长期记忆 + 闲时整理（`04` §三） |

> ⚠️ **安全红线**：`qwen-audio` 官方文档明确要求
> **"API Key 只保存在业务 AppServer，不要写入客户端"**。
> 客户端通过**自己的后端**换取临时凭证或走中转，绝不内置 API Key。
> → 这与 `10` §七 的凭证三层策略一脉相承。
