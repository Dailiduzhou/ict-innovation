# 03 · 产品与 MVP

> 当前设计基线：2026-10-17。完整交互、设备协议约束、药品维护和硬件验收见 [13 · 产品形态与硬件闭环](13-产品形态与硬件闭环.md)。
> 本文是计划与验收定义，不是已上线功能清单。

## 一、一套后端、两个节点、一个家庭应用

| 组成 | 一期职责 | 不等价的能力 |
|---|---|---|
| 老人语音盒 | 无触摸屏；说话／确认／取消，录音、播报和进度查询 | 不依赖老人打开 App；按键式语音不冒充全双工 |
| 药盒开合节点 | 容器开合及设备状态，经过 IoTDA 进入后端 | 开盖不等于取药、吞服或用药正确 |
| 家庭应用 | Web 主界面；移动接收端提供通知入口；Webhook 只补充 | WebSocket 在线提示不等于后台通知必达 |
| 完整后端 | 人与设备身份、绑定、授权、事项、计划、记录、调度、通知及恢复 | 不能为简化 Demo 删除权限和持久化 |

一台语音盒首版绑定一位主要使用者；不承诺同住者身份自动识别。硬件进入主路线，网页可先联调但不能抵扣硬件验收。OpenHarmony 按实际能力优先采用，不强求所有节点统一系统。

## 二、普通事项的闭环

```text
表达 → 澄清 → 草稿 → 老人确认 → 待接手 → 处理中 → 处理结果
                         ↓                              ↓
                 后端复核授权并提交              盒子反馈／老人知晓状态单独记录
```

草稿可取消；新增接收人或扩大共享范围重新授权。超时保持待跟进，不伪造处理完成或老人确认。亲属报告处理完、设备回报播放完、老人确认满意和系统归档是不同事件。

重复提醒的未反馈跟进可以使用老人事先明确开启的具体规则，默认关闭、可撤销。它不赋予 Agent 自行共享的权利，也不允许扩大接收人。

## 三、亲属端页面

- **待跟进事项**：仅见授权内容；接手、更新、反馈；并发接手由后端裁决。
- **提醒与记录**：分开显示提醒执行、设备观察、人员反馈、协作跟进。
- **药品与提醒**：个人药品、来源、用药安排、提醒配置、版本及设备同步。
- **家庭与设备**：绑定、授权、规则、在线状态和最后同步时间。

老人仍可通过辅助 Web 界面查看、纠错、撤销和配置；不要求其靠复杂表单完成日常流程。

## 四、权限约束

| 操作 | 老人 | 获相应授权亲属 | Agent／设备 |
|---|---|---|---|
| 提出事项草稿 | 可以 | 按业务入口权限 | Agent 可提议；设备仅转交输入 |
| 确认普通事项发送 | 明确确认 | 不能代替老人授权 | 不能自行确认 |
| 查看／接手事项 | 本人查看 | 仅资源级授权范围 | 限当前任务和设备作用域 |
| 药品查看、协助录入、管理提醒 | 决定授权范围 | 三种权限分别授予 | AI 只协助提取待核对内容 |
| 修改关键药品／计划字段 | 按确认流程 | 有来源的新版本，核对后按授权流程启用 | 不自行改药、剂量、频率或启用 |
| 跟进规则／扩大共享 | 决定开启、修改、撤销 | 不得自我扩权 | 执行时后端复核 |
| 解绑／停用设备 | 按绑定授权流程 | 仅获授权的管理操作 | 设备认证不等于本人身份确认 |

身份认证、资源授权、状态合法性、幂等和审计在后端执行，不能由模型提示词或客户端按钮代替。访问历史记录也须重新鉴权。确认按键关联当前有效上下文及版本，不是通用的“已服药”按钮。

## 五、主要领域对象

| 对象 | 关键约束 |
|---|---|
| User／FamilyBinding／Grant | 家庭关系与权限分离；可撤销、最小共享 |
| Device／DeviceBinding | 独立设备凭据、作用域、主要使用者、解绑与撤销 |
| Item／ItemGrant／ItemEvent | 草稿确认、资源级授权、合法流转、并发控制及有来源的结果 |
| DeviceEvent／ActivityEpisode | 事件幂等、发生／接收时间、时钟质量；真实次数与合并展示分离 |
| Medication／MedicationAlias | 药品身份保留剂型规格；别名个人化、可失效，不自动合并相似药 |
| MedicationPlanVersion／ReminderConfig | 来源与安排原文、核对人、新版本、生效／失效及设备同步 |
| ReminderOccurrence／Report／FollowUp | 四个状态维度分离，人员自报不等于客观核验 |
| InteractionContext／DeviceCommand | 明确动作、版本、到期、接收／执行回执、重连恢复 |
| NotificationAttempt／Outbox | 受理／送达／打开／接手分离；业务提交和发送任务共同持久化 |
| MemoryRecord／SourceRecord | 来源、确认状态、纠错、删除与派生数据清理；不默认永久留敏感原文 |

这是逻辑对象表，不是已经创建的数据库表或最终 schema。字段、索引与 API 收敛见 `12` §2.7。

## 六、一期验收边界

| 模块 | 验收要求 |
|---|---|
| 业务骨架 | 文字联调、授权、正常与拒绝共享、失败恢复；后台不阉割 |
| 语音盒 | 录音、播放、草稿确认／取消、状态反馈；不以远场全双工为前置 |
| 药盒节点 | 抖动、重复投递、真实反复开合、断网补传；不误写服药完成 |
| 药品与提醒 | 获授权亲属录入／修改、资料冲突、版本、简称歧义、按需播报 |
| 有限离线 | 条件满足时本地执行已确认有效计划；时间不可信、过期或不同步明确降级 |
| 云上交付 | CodeArts／已有 Skills、资源开通关联、部署、实际连接及业务读写证据 |
| 评测 | `13` H-01～H-16，以及 `10` 的用户价值／安全测试 |

一期不做：医疗端、诊断／处方／自动改药、自动给药、吞服核验、可靠急救监护、多种新增传感器并进、远场唤醒／全双工前置、商用穿戴数据硬性依赖。

## 七、交付责任与成果

职责必须覆盖实现、测试、文档和联调；另一成员按文档复现。不能默认后端负责人承担所有收尾。两位 IoT 成员围绕交互盒和传感节点形成真实交付，云部署、前端与评测也须明确负责人；具体姓名和工期在 T-69 落定，不虚构人员承诺。
