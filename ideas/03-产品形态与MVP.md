# 03 · 产品形态与 MVP

> 来源：v2《说明书》§2、§3、§6、§7 的重整版。
> v2 这一部分质量最高，本文件主要做**结构化 + 补充缺口**（角色权限矩阵、数据模型、分工与赛事对齐）。

---

## 一、四个组成部分

### 1. 老人端 APP

| 项 | 内容 |
|---|---|
| **首页入口（只保留 3 个）** | ① 联系家人 ② 我有件事想说 ③ 查看事情进度 |
| 交互原则 | 大字、大按钮、少步骤、**确认后才分享** |
| 输入方式 | 文字输入为主；**语音输入/播报为增强项**（需按实际开发环境验证，见 `06` §4） |
| Agent 角色 | 整理内容后生成**草稿**；老人可**修改 / 确认 / 取消**；**不能默认替老人发送** |
| 事项展示 | 清晰状态：等待家人接手 / 处理中 / 已完成 / 待跟进 |

### 2. 亲属端 APP

| 项 | 内容 |
|---|---|
| 展示范围 | **仅展示老人主动授权分享的事项**；不默认开放全部聊天或个人信息 |
| 核心操作 | 接手 → 更新进度 → 填写处理结果 |
| 同步 | 老人端同步展示状态 |
| 增强项 | 家庭联系计划：约定联系时间、提醒双方、未确认时提示重新安排 |

### 3. AI Agent 与工具层

| 职责 | 说明 |
|---|---|
| 理解 | 从自然语言中提取**事项内容、时间、对象、期望动作** |
| 工具 | 创建事项草稿、查询事项状态、触发提醒、整理反馈 |
| 校验 | **检查工具执行结果**；失败时提示用户并允许重试 |
| 边界 | Agent 负责**理解和协调**；后台负责**权限校验与数据写入**；分享或外部操作遵循确认机制 |

### 4. 后台服务

- 账号、老人与亲属的**绑定关系**及**访问权限**
- 事项内容、状态变更、时间、必要的**操作记录**
- 双端同步、提醒调度、异常处理、数据保护

## 二、端到端流程（关键闭环）

```
表达 → 确认 → 接手 → 处理 → 反馈 → 老人知晓
```

**七步展开：**

| # | 角色 | 动作 |
|:--:|---|---|
| 1 | 老人 | 通过文字或语音输入自然语言需求 |
| 2 | Agent | 理解需求，提取"购买大米""周末"；**不确定时向老人追问** |
| 3 | 系统 | 生成事项草稿，显示内容和计划分享的亲属 |
| 4 | 老人 | 检查内容、接收人、分享范围后，**确认发送或取消** |
| 5 | 亲属 | 收到授权事项，选择"我来处理" |
| 6 | 亲属 | 更新为"处理中"，完成后填写结果并标记"已完成" |
| 7 | 老人端 | 同步显示状态，老人知道事情是否有人接手、是否完成 |

## 三、MVP 边界（v2 §6 的修订）

### 3.1 第一版**必须**完成

| 模块 | 必须项 | 验收标准 |
|---|---|---|
| 老人端 | 输入需求、查看 AI 事项草稿、确认/取消、查看事项状态 | 老人可独立完成"提出需求 → 确认分享 → 查看进度" |
| 亲属端 | 接收授权事项、接手任务、更新状态、反馈完成结果 | 亲属可完成"接手 → 处理中 → 已完成" |
| 后台 | 双端账号关联、事项存储与同步、**权限校验** | 未授权亲属无法访问；撤销权限后立即失效 |
| Agent | **至少一个**完整的"自然语言 → 事项"工作流，**实际调用**创建或查询工具 | 有可展示的工具调用日志 |
| 测试 | 成功路径 + 取消 / 信息不完整 / 工具失败 | 至少 4 条路径可演示 |

### 3.2 第二阶段（有时间再做）

- 语音输入与播报
- 家庭联系计划自动提醒
- 日历、系统通知等外部服务集成（**先核实接口与授权**）
- ESP32 等实体语音终端或实体按钮设备

### 3.3 首版**不建议投入**（v2 原文，已用 `06` 的核查结论加固）

| 不做 | 原因类别 |
|---|---|
| 自建视频通话、完整社交平台、复杂群聊 | 战略取舍 |
| 未经许可读取微信聊天记录或自动向微信联系人发消息 | 合规红线（无公开接口） |
| **健康监测、跌倒检测** | **客观限制**：数据时延小时级 + 高阶数据需企业资质（`06` §2） |
| **智能家居数据接入** | **客观限制**：无第三方 API（`06` §3） |
| 核心软件价值尚未验证前就投入复杂硬件（含星闪终端） | 战略取舍 |

## 四、角色—权限矩阵（v2 缺失，必须补）

> 这是**竞争力 C4「授权与可追踪性」的落地定义**，也是答辩最容易被追问的点。

| 资源 / 操作 | 老人 | 已绑定亲属 | 未授权亲属 | 后台 | Agent |
|---|:--:|:--:|:--:|:--:|:--:|
| 创建事项草稿 | ✅ | ❌ | ❌ | — | ✅（代理，需老人确认） |
| **确认发送**事项 | ✅ | ❌ | ❌ | ❌ | ❌ **（Agent 无此权限）** |
| 取消/撤回事项 | ✅ | ❌ | ❌ | — | ❌ |
| 查看本人创建的事项 | ✅ | — | — | — | ✅（限当前会话） |
| 查看被授权的事项 | — | ✅ | ❌ | — | ✅（限当前会话） |
| 接手 / 更新进度 | ❌ | ✅ | ❌ | — | ❌ |
| 查看老人全部聊天记录 | ✅ | ❌ **默认不开放** | ❌ | 仅审计 | ❌ |
| 增删绑定关系 | ✅ | ❌ | ❌ | 校验 | ❌ |
| 撤销授权 | ✅ | ❌ | ❌ | 执行 | ❌ |
| 修改分享范围 | ✅ | ❌ | ❌ | 执行 | ❌（须重新确认） |

**三条不可逾越的规则：**

1. **Agent 永远不能替老人做授权决定**——只能生成草稿并请求确认
2. **权限校验发生在后台，不发生在 Agent**——Agent 的输出不可信
3. **扩大共享范围必须重新授权**——包括新增接收人、改变重要安排（来自 `04` §5）

## 五、数据模型草图（v2 缺失，必须补）

```
User
  id, role(elder|relative), name, phone, huawei_account?, created_at

Binding                       # 老人—亲属绑定关系
  id, elder_id, relative_id, status(pending|active|revoked),
  granted_scopes[], created_at, revoked_at

Item                          # 事项（核心实体）
  id, elder_id, created_by(agent|elder),
  action_type, content, expected_time, deadline,
  status(draft|pending|in_progress|done|overdue|reassign|cancelled),
  confirmed_at,              # 老人确认的时刻 —— 审计关键字段
  created_at, updated_at

ItemGrant                     # 事项级授权（谁可以看/接手）
  id, item_id, relative_id, scope(view|handle), granted_at, revoked_at

ItemEvent                     # 状态变更与操作记录（可追踪性 + 审计）
  id, item_id, actor_id, actor_type(elder|relative|agent|system),
  event_type(create|confirm|cancel|take|update_progress|complete|remind|reassign),
  payload, occurred_at

MemoryRecord                  # 长期记忆（见 04）
  id, elder_id, kind(fact|preference|contact|routine),
  content, source, confidence, version, valid_from, valid_to
```

**设计要点：**

- `ItemGrant` 与 `Binding` 分离 → 支持"授权了某个亲属，但只对某件事开放"（v2 §竞争力 4 的核心）
- `ItemEvent` 只追加不修改 → 可追踪性
- `MemoryRecord` 带 `version` / `valid_from` / `valid_to` → 支持 v1 提到的"审计记录"和"不导致过分膨胀"
- `confirmed_at` 是审计与合规的关键字段

## 六、三人团队分工（与 ICT 创新赛要求对齐）

> ⚠️ v2 §7 只写了"三人分工建议"，**漏了指导教师**。ICT 创新赛明确要求 **3 名学生 + 1 名指导教师，且须来自同一所高校**（`00` R2）。

| 角色 | 主要任务 | 阶段成果 | 对应赛题职责 |
|---|---|---|---|
| **A · 前端与体验** | 老人端/亲属端界面、交互流程、**可访问性**（大字、对比度、语音） | 双端可操作原型/应用 | 用户体验（赛题二评分项） |
| **B · Agent 与后端** | 结构化输出、工具调用、API、数据模型、**权限校验**、云上部署 | Agent 工作流与后台接口 | 技术方案（核心） |
| **C · 产品、测试与集成** | 用户访谈、测试用例、部署、**演示脚本和文档**、答辩材料 | 测试记录、演示环境、答辩材料 | 创意点 + demo 视频 + 落地场景 |
| **D · 指导教师** | 方向把关、资源协调、合规与伦理审查、对外沟通 | 推荐、审核 | 报名资格要件 |

**三条纪律：**
1. **三个人都要理解完整业务流程**——避免只有一人能现场演示（v2 原文）
2. **三个人都要能跑通系统**——因为 ICT 赛规定"代码无法复现 PPT 效果将取消资格"（`00` R5）
3. **指导教师必须从第一天介入**——报名后不得更换（`00` R3）
