# 02 · 用户与场景

> 用户定义以 [product/01-用户](../product/01-用户.md) 为准。本文保留实施映射和访谈，不另建“只有独居、患病、有设备才适用”的画像。

## 一、用户与入口

| 角色 | 核心价值 | 入口与权限 |
|---|---|---|
| 老人 | 自然交流、跨次记忆、日常提醒、自主决定分享 | 手机为基础，个人数据隔离，可更正、删除与撤销 |
| 子女 | 理解近况、联系前回顾、真实回应、必要时协助 | 家庭视图，只读取授权内容 |
| 其他亲属 | 在同意范围内参与联系或明确请求 | 单独授权，不默认看到全部聊天或健康记录 |

独居、空巢、异地子女可以优先验证，但不是全部必要条件。老人没有亲属加入，也能独立受益。

首版需要本人能理解基本用途与授权；涉及代理同意、监护认定的情境另行评估。不会复杂手机操作不等于无法决策；普通遗忘不等于认知诊断。

## 二、场景优先级

| 场景 | 产品重点 | 是否需要子女／硬件 |
|---|---|---|
| 自然闲聊与改口 | 全双工、不中断的交流与后台整理 | 都不需要 |
| 下次接着聊 | 可靠个人记忆、来源、检索与纠错 | 都不需要 |
| 换水、检查花土、生活安排 | 提出提醒、确认、调度与反馈 | 都不需要 |
| 分享生活近况 | 经授权摘要与原话，不把生活任务化 | 需要接收亲属，不需硬件 |
| 联系前回顾 | 可接着聊的话题与系统内已知约定 | 需要亲属，不需硬件 |
| 子女留真实回应 | 双向连接，不自动代发 | 需要亲属，不需硬件 |
| 请求买物品或陪同 | 接手、协商和反馈，仅限明确请求 | 需要获授权亲属 |
| 存在／开关等事件 | 改善情境与时机，不作安全断言 | 可选传感器 |

详细虚构脚本见 [典型使用场景](典型使用场景.md)。不是每次聊天都应提取事项，也不要求每条近况已读或办结。

## 三、研究要区分三种问题

1. **交流需求**：期待分享、倾诉和被回应，而非只要一个知识问答工具。
2. **信息负担**：长语音、碎片信息和缺少上下文，是否真的造成遗漏或理解困难。
3. **现实资源**：亲属忘了、不知道做什么，与没有时间／能力／意愿，不能混为一谈。

手机、AI 或待办不能创造家庭的时间与服务资源。降低操作门槛也不一定消除“怕打扰孩子”的关系压力。
