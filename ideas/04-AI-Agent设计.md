## 一、Agent 的边界原则（**最重要的一条**）

> 来自优化建议原文：
> *"时间检查、任务状态判断、提醒频率限制应主要由**确定性程序**完成。Agent 负责理解复杂反馈、选择允许的处理路径以及生成合适的沟通内容。"*

这是把 LLM 放进一个**可靠性敏感**场景（涉及老人、涉及授权、涉及对外发送）的正确做法。

| 交给**确定性程序** | 交给 **Agent（LLM）** |
|---|---|
| 定时触发、超时判定 | 理解老人含糊的自然语言 |
| 事项状态机迁移合法性校验 | 生成澄清问题 |
| 提醒频率限制（如 24h 内不重复） | 选择澄清方式（开放式 / 选项式） |
| 权限校验（谁能看、谁能接手） | 生成沟通话术与共情回应 |
| 幂等与去重 | 从对话中提取结构化字段 |
| 数据写入与审计日志 | 判断"这句话是否在回应之前的事项" |
| 澄清轮次计数 | 生成候选假设 |

**落地形态**：Agent 只产出**结构化意图 + 文本**，所有**副作用（写库、发通知、改权限）**必须经过后台的确定性校验层。

```
老人输入
   │
   ▼
┌──────────────────┐
│  Agent (LLM)     │  产出：{intent, slots, hypotheses, reply_text}
│  ReAct 循环       │        纯计算，无副作用
└────────┬─────────┘
         ▼
┌──────────────────────────────┐
│  确定性校验层（Deterministic） │
│  · 状态机合法性               │
│  · 权限校验                   │
│  · 频率限制                   │
│  · 幂等键                     │
└────────┬─────────────────────┘
         ▼ 通过才执行
   写库 / 通知 / 提醒 → 审计日志
```

## 二、统一 ReAct 循环与工具集

> v1 原文："统一的 ReAct 循环，进行全局记忆的整理"。

```python
# 伪代码：单轮对话的 Agent 主循环
def handle_turn(utterance, elder, session):
    ctx = build_context(
        utterance   = utterance,
        profile     = memory.get_profile(elder),      # 沟通偏好、称呼
        recent      = memory.get_recent(elder, n=10), # 短期上下文
        facts       = memory.search(elder, utterance),# 长期记忆召回
        open_items  = item_store.list_open(elder),    # 未闭环事项
    )

    for step in range(MAX_STEPS):                     # 步数上限，防死循环
        thought, action = llm.react(ctx)

        if action.type == "reply":
            return action.text                        # 纯回应，无副作用

        result = TOOLS[action.name](**action.args)    # 工具调用
        ctx.append(observation=result)

    return fallback_reply()                           # 兜底：转人工/提示重试
```

### 工具清单（首版）

| 工具 | 作用 | 是否有副作用 | 需要确认？ |
|---|---|:--:|:--:|
| `extract_item` | 从自然语言提取事项结构化字段 | ❌ | — |
| `create_item_draft` | 创建事项草稿 | ✅（仅草稿） | ❌ |
| `confirm_item` | 确认并发送事项 | ✅ | ✅ **必须老人确认** |
| `cancel_item` | 取消草稿 / 撤销事项 | ✅ | ✅ |
| `query_item_status` | 查询事项状态 | ❌ | — |
| `search_memory` | 检索长期记忆 | ❌ | — |
| `web_search` | 联网搜索（**自建工具**，不走模型的 `enable_search`） | ❌ | — |
| `write_memory` | 写入/更新长期记忆 | ✅ | ❌（但需审计） |
| `ask_clarification` | 生成澄清问题 | ❌ | — |
| `list_contacts` | 列出可选的协作对象 | ❌ | — |
| `set_reminder` | 设置提醒（受频率限制） | ✅ | ❌（受限制即可） |
| `link_feedback_to_item` | 把老人反馈关联到历史事项 | ✅ | ✅ **必要确认后** |

**工具设计的四条规范：**

1. **每个工具必须返回可判定的成功/失败**——不能静默失败（`03` §3.3 测试项）
2. **有副作用的工具必须幂等**——带 `idempotency_key`，重复提交不产生重复事项
3. **Agent 不能直接调用 `confirm_item`**——必须由用户界面的确认动作触发
4. **每次工具调用写入审计日志**——这是竞争力 C3「Agent 不只回答，还能调用工具」的证据

## 三、长期记忆架构

> v1 原文：
> *"前期使用纯文本 + FTS + BM25，后期可以扩展 RAG"*
> *"实现细节上，可以闲时进行记忆内容的整理，保持记忆内容一定时间更改次数内的审计记录。要求全局记忆的新增和修改不导致过分的膨胀。"*

v1 这一段是**整个 idea.md 里技术判断最成熟的部分**，应当保留并明确化。

### 3.1 分层记忆

| 层 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| **工作记忆** | 当前会话的对话历史 | Redis（含 TTL） | 会话级 |
| **短期记忆** | 最近 N 天的对话摘要、未闭环事项 | RDS + Redis | 天~周 |
| **长期记忆** | 偏好、称呼、协作对象、日常规律、重要事件 | **RDS + FTS/BM25** | 长期 |
| **语义记忆（演进）** | 向量检索增强 | 向量库（可选） | 长期 |
| **审计记录** | 记忆的每次新增/修改 | 只追加表 | 永久 |

### 3.2 记忆分类（落地为 `MemoryRecord.kind`）

| kind | 示例 | 写入时机 | 是否需确认 |
|---|---|---|---|
| `preference` | "喜欢喝淡茶""习惯早上 6 点起" | 闲聊中提取 | ❌（可事后查看/删除） |
| `contact` | "小林是女儿""弟弟叫陈叔" | 闲聊或用户明说 | ✅ 涉及协作对象 |
| `routine` | "每周三上午去菜市场" | 长期观察 | ❌ |
| `fact` | "膝盖做过手术" | 用户明说 | ✅ **属健康信息，谨慎** |
| `event` | "上个月孙女来看过" | 闲聊 | ❌ |

> ⚠️ **`fact` 类中的健康信息属于敏感个人信息**。建议首版**不做健康事实的长期留存**，只做会话内使用。这是合规取舍，不是缺陷。

### 3.3 记忆膨胀控制（v1 明确提出的要求）

| 机制 | 做法 |
|---|---|
| **合并去重** | 相似记忆合并（同 subject + 同 predicate → 更新 value 而非新增） |
| **闲时整理** | 低峰期批量任务：合并、裁剪、摘要化 |
| **版本化** | 不覆盖，写新版本 + `valid_from` / `valid_to` |
| **审计上限** | 同一记忆项"一定时间内的更改次数"超阈值 → 冻结并标记待确认 |
| **容量上限** | 每用户长期记忆条数上限 + LRU/置信度淘汰 |
| **置信度** | 每条记忆带 `confidence`，低置信度不参与推理，只做候选 |
| **过期** | `routine` / `event` 类带自然衰减期 |

### 3.4 从 FTS+BM25 演进到 RAG 的路径

```
阶段 1（MVP）：RDS + 全文索引（FTS）+ BM25 排序
  优点：零外部依赖、可解释、可调试、成本低
  足够支撑：几十~几百条记忆/用户

阶段 2（增强）：BM25 结果 + 向量召回 → 混合排序
  触发条件：记忆条数增长导致 recall 明显下降时才做

阶段 3（可选）：按记忆类型分索引 + 重排序（rerank）
```

> **写作规范**：在申报材料中应写成**有触发条件的技术演进路线**，而不是"后期会上 RAG"。
> 说明"当前方案在 XX 条记忆以内足够，超过后因 YY 原因需要升级"——这体现工程判断力。

## 四、自适应关怀交互

> 优化建议原文：
> *"不同老人具有不同的语言表达能力、理解能力、沟通习惯和交互偏好，Agent 应能够**动态调整沟通方式**。"*

### 4.1 个性化沟通策略（逐条落地）

| 维度 | 策略 | 实现方式 |
|---|---|---|
| **语言复杂度** | 使用简单表达，避免复杂术语 | 提示词约束 + 输出后简易度校验 |
| **信息长度** | 优先简短回应，必要时**分步说明** | 长度阈值；超长拆成多轮 |
| **语音速度** | 允许用户调整播报速度 | 用户配置项 |
| **信息重复** | 支持自然语言请求重复说明 | 意图 `repeat` |
| **澄清方式** | 根据用户反馈选择**开放式**或**选项式**提问 | 见 §4.3 |
| **交流习惯** | 在用户允许范围内记住偏好的**称呼和沟通方式** | `MemoryRecord.kind=preference` |

### 4.2 共情与关怀性回应（**有明确红线**）

> 优化建议原文：
> *"Agent 可以识别当前表达中的情绪线索，但**不应直接推断老人的心理状态**。"*

```
❌ 错误（直接推断心理状态）
   老人："今天又是一个人吃饭。"
   AI  ："您感到很孤独。"                    ← 断言了老人的情绪

✅ 正确（识别线索 + 开放邀请）
   老人："今天又是一个人吃饭。"
   AI  ："今天也是一个人吃饭呀。您想跟我聊聊今天的事吗？"
```

**规范**：Agent 的输出中**禁止出现对用户心理状态的断言**（"您很孤独""您很焦虑""您抑郁了"）。
可以描述**可观察的事实**，并**邀请**用户表达。

### 4.3 澄清方式的选择

| 方式 | 何时用 | 示例 |
|---|---|---|
| **开放式** | 老人表达流畅、情绪开放 | "您想跟我说说是怎么回事吗？" |
| **选项式** | 老人表达困难、或已多轮未澄清 | "您是想让**女儿**帮忙，还是**儿子**帮忙？" |

**选择依据**：老人历史表达长度、澄清轮次、上一轮是否成功。

### 4.4 语音能力

- 多音色选择、情感语音合成、语速音调可调（来自优化建议）
- ⚠️ **方言支持必须先核实清单**（`06` §4），不能写"支持方言"

### 4.5 交互失败恢复（优化建议明确要求）

| 机制 | 说明 |
|---|---|
| **澄清轮次上限** | 例如 3 轮后改用选项式或转人工 |
| **随时可中断** | 用户任何时刻可打断、取消、要求重来 |
| **降级路径** | Agent 无法理解 → 提示老人"我有件事想说"按钮下的表单直接填写 |
| **不静默失败** | 任何失败都有明确提示 |

## 五、记忆驱动的多假设推理

> 优化建议原文：
> *"有时候需求不会这么明确……Agent 应结合当前表达、长期记忆和历史上下文，识别可能存在的潜在需求，并生成**多个候选假设**。对于**证据不足**的需求，**不直接认定其真实性**，而是通过自然、低负担的交互进行澄清。长期记忆可以辅助识别可能的协作对象，但**不能替代用户对具体行动的确认与授权**。"*

### 5.1 推理流程

```
输入表述 + 长期记忆 + 历史上下文
        │
        ▼
 生成 N 个候选假设，每个带：
   · hypothesis     假设内容
   · evidence       支撑证据（来自哪条记忆 / 哪句上下文）
   · confidence     置信度
   · cost_of_error  猜错的代价（低 / 中 / 高）
        │
        ▼
 决策：
   confidence 高 且 cost_of_error 低  → 直接执行（仍需轻量确认）
   confidence 中 或 cost_of_error 高  → **提问澄清**
   confidence 低                      → 只做共情回应，不推断
```

### 5.2 完整示例

```
陈阿姨："最近有点想小林，想跟她说说话。"
  ├─ 假设1: 希望与"小林"通话  (evidence: 长期记忆 contact{小林=女儿}, conf=0.85, cost=低)
  └─ 假设2: 只是想倾诉        (conf=0.3, cost=低)

AgeGuard："你希望我把想通话这件事告诉小林吗？"
陈阿姨："可以，告诉她我今晚有空。"
AgeGuard："我会创建一条联系事项。她是否已经查看或跟进，会在事项里显示。"

───────────────────────────────────────────

陈阿姨："家里米快没了，想请弟弟明天带一小袋来。"
  ├─ 假设1: 采购请求，对象="弟弟"→ 长期记忆解析为"陈叔" (conf=0.9)
  └─ 假设2: 对象未确定

AgeGuard："是请陈叔明天帮你买米吗？这次采购请求是否可以分享给他？"
陈阿姨："对，可以。"
```

### 5.3 **证据不足时的行为**

```
老人："最近家里挺冷清的。"
  ├─ 假设1: 想和家里人聊天 (conf=0.4, cost=中)
  ├─ 假设2: 家里真的冷（温度）(conf=0.2, cost=低)
  └─ 假设3: 抱怨孤独          (conf=0.4, cost=高 —— 猜错会冒犯)

→ conf 不足且存在 cost=高 的假设 → 用**开放式提问**，不下断言

AI："最近是不是比较想和家里人聊聊天？"      ← 提问式，不是断言式
```

**红线（优化建议原文）**：
> 长期记忆**可以辅助识别可能的协作对象**，但**不能替代用户对具体行动的确认与授权**。

## 六、上下文感知的动态任务规划

> 优化建议原文：
> *"以及 Agent 能否根据时间事件和现实反馈，**动态调整后续协作策略**。例如若超过约定时间如何保持**待跟进**的状态？"*

### 6.1 四天生命周期（优化建议的完整场景）

| 天 | 事件 | 系统行为 | 确定性 / Agent |
|:--:|---|---|---|
| D1 | 老人说"最近家里挺冷清的" → 同意创建关怀事项 | 创建事项 | Agent 生成内容，**确定性**创建 |
| D2 | 女儿收到通知 → 选择"周六下午联系妈妈" | 记录联系安排 | **确定性**（写库） |
| D3 | 系统发现**约定时间已过，无完成反馈** | 在**频率限制内**询问女儿：<br>"之前约定的联系事项还没有记录结果，是否已经完成？" | 超时判定=**确定性**；话术=Agent |
| D4 | 老人说"昨天和女儿聊了很久，挺开心的" | 识别这可能是对之前关怀事项的**反馈** → **必要确认后**关联历史事项并更新状态 | 匹配=Agent 建议，**关联=需确认** |

### 6.2 待跟进状态保持策略

| 情况 | 策略 |
|---|---|
| 约定时间已过，无反馈 | 状态 → `overdue`；按**频率限制**提醒（如 24h 最多 1 次） |
| 提醒后仍无响应 | 状态保持 `overdue`，**不升级、不轰炸**；到达阈值后提示老人"是否换个人帮忙" |
| 老人主动问"事情办了吗" | Agent 查 `query_item_status` 如实回答，**不美化** |
| 亲属说"我忘了" | 允许重新安排时间 → 记录新约定 |
| 亲属说"我做不了" | 进入 `reassign` 流程（见 §7） |

### 6.3 频率限制规则（确定性实现）

```
同类提醒最小间隔       : 24h
单事项提醒总次数上限   : 3 次
静默时段               : 22:00 - 08:00（可配置）
老人主动询问不计入限额 : ✅
紧急标记事项可突破     : 需老人显式标记
```

## 七、多主体任务协作

> 优化建议原文：
> *"当任务执行条件发生变化时，Agent 可以结合**历史协作关系、当前反馈和任务要求**生成替代方案，并通过**多轮协商**推动任务调整。
> 涉及**新增接收人、扩大信息共享范围或改变重要安排**时，**必须重新确认用户意愿并完成必要授权**。"*
>
> v2 现状：*"目前方案有亲属授权、通知和反馈，可以增加**多轮协商、任务重新分配、异常处理和结果确认**。"*

### 7.1 v2 → v3 的增量

| 能力 | v2 | v3 |
|---|:--:|:--:|
| 亲属授权 | ✅ | ✅ |
| 通知 | ✅ | ✅ |
| 反馈 | ✅ | ✅ |
| **多轮协商** | ❌ | ✅ |
| **任务重新分配** | ❌ | ✅ |
| **异常处理决策** | ❌ | ✅ |
| **结果确认** | ❌ | ✅ |

### 7.2 重新分配流程

```
条件变化（亲属拒绝 / 超时 / 能力不匹配）
        │
        ▼
Agent 检索：历史协作关系（谁办过类似的事）+ 当前反馈 + 任务要求
        │
        ▼
生成 1~N 个候选方案（含理由）
        │
        ▼
**回到老人处重新确认**  ← 不可跳过
        │
        ▼
老人确认 → 重新授权 → 通知新接收人
   或   老人取消 → 事项关闭
```

**硬规则**：任何"新增接收人""扩大共享范围""改变重要安排"都必须**重新走一遍老人确认流程**。

### 7.3 协作结果的双维度评价（优化建议提出的概念）

单项事项的完成质量应记录为**两个维度**，而不是一个"完成/未完成"：

| 维度 | 含义 | 取值 |
|---|---|---|
| **是否完成** | 事项本身有没有被办成 | 已完成 / 部分完成 / 未完成 / 已失效 |
| **协作体验** | 老人的主观感受 | （老人可选反馈）满意 / 一般 / 不满意 |

**用途**：
- 提高"事项闭环率"测量的真实性（避免"人来了但什么都没做"被算成闭环）
- 为亲属匹配提供依据（哪个人响应快、完成好）
- 为 `07` 的指标提供原始数据

## 八、不确定性感知与证据可靠性管理

> 优化建议原文（**这是一个尖锐且非常好的问题**）：
> *"idea 中有区分'老人**自报**已服药'和'**客观确认**已服药'，但是应该**从哪里去获取事实依据**？以及老人自报已服药后**是否需要进一步推进**？"*

### 8.1 先回答"从哪里获取事实依据"

`06` 的核查给出了明确答案：

| 证据来源 | 可得性 | 结论 |
|---|:--:|---|
| 老人自述 | ✅ | 唯一稳定的来源 |
| 亲属反馈 | ✅ | 第二来源，但依赖亲属配合 |
| 华为穿戴客观数据（心率等） | ⚠️ | **小时级**；高阶数据需企业资质；不能用作实时核验 |
| 智能家居（是否起床、是否开灯） | ❌ | **不可得**（`06` §3） |
| 智能药盒等专用硬件 | ❌ | 无（首版投入硬件已被否决） |

> **结论：在客观条件限制下，"服药"这类事件在首版中无法获得独立的客观证据链。**
> 这是一个**客观限制**，不是系统缺陷。正确做法是**不假装能核实**，而是：
> **明确标注每条记录的证据等级。**

### 8.2 证据分级模型（v3 新增）

| 等级 | 定义 | 来源 | 可展示给谁 |
|:--:|---|---|---|
| **E0** | 无任何记录 | — | — |
| **E1** | 老人自报 | 老人对话 / 手动打卡 | 亲属可见，**须标注"老人自报"** |
| **E2** | 老人自报 + 亲属确认 | 老人 + 亲属反馈 | 亲属可见，标注"已确认" |
| **E3** | 设备客观记录 | 华为穿戴/血压计（受限） | 标注"设备记录"+ 采集时延 |
| **E4** | 专业机构确认 | 医院/医生（首版不可得） | — |

**展示规范（关键）**：
- 亲子端看到的每条健康相关记录，**必须显示证据等级和采集时间**
- **绝不允许**把 E1（老人自报）渲染成"已服药 ✓"这种确认性表述

### 8.3 "自报后是否需要进一步推进" —— 决策树

```
老人自报已服药
     │
     ├─ 该事项是否由老人主动提出？（是 → 低干预）
     │     └→ 记录 E1，不追问，仅在下次闲聊自然提及
     │
     ├─ 是否为重复模式？（如连续 3 天未记录）
     │     └→ Agent 用非质问方式询问：
     │         "这周好像有几天没记录吃药，是忘记点了还是没吃呀？"
     │         而不是："您是不是没吃药？"
     │
     ├─ 是否涉及高风险药物？（需长期医嘱）
     │     └→ 首版**不做**医疗建议，仅记录并在亲属端标注
     │
     └─ 亲属是否设置了关注？
           └→ 按频率限制在亲属端提示"老人自报已服药（未独立核实）"
```

**三条红线：**
1. **不追问到让老人有压力**——干预强度随证据不足**递减**，不是递增
2. **不做医疗判断**——不推断药效、不建议改药、不判断"是否该吃"
3. **不把低证据等级数据当作高证据等级用**——尤其在亲属端展示时

## 九、失败恢复与降级

| 失败类型 | 处理 | 是否需要用户知晓 |
|---|---|:--:|
| LLM 超时 / 限流 | 重试（退避）→ 失败则降级为表单填写 | ✅ |
| 工具调用失败 | 明确告知"没能创建成功"，草稿保留，可重试 | ✅ |
| 意图识别置信度过低 | 不猜测，走澄清或降级 | ✅ |
| 澄清轮次超限 | 改用选项式 → 再超限则降级为表单 | ✅ |
| 记忆检索失败 | 无记忆上下文继续，不阻塞 | ❌ |
| 云服务不可用 | 本地缓存草稿，恢复后同步 | ✅ |

## 十、Agent 设计的评测钩子（对接 `07`）

| 设计要素 | 对应可测指标 |
|---|---|
| 工具调用循环 | 工具调用成功率、平均步数、失败恢复率 |

| 动态规划 | **事项闭环率**、超时响应率、重新分配成功率 |
| 证据分级 | 证据等级标注正确率（人工抽查 100 条） |
