## 1. NearLink Kit（星闪服务）

### 已核实事实

| 项目 | 结论 | 出处 |
|---|---|---|
| 支持语言/平台 | **HarmonyOS（ArkTS / ArkUI）**，通过 DevEco Studio 开发；**无 Android / iOS / Web SDK** | 华为开发者联盟 NearLink Kit 文档；OpenHarmony `communication_nearlink_service` 仓库 |
| 提供的能力 | 设备发现（扫描/广播）、连接管理、**SSAP**（SparkLink Service Access Protocol）数据传输、基于端口的数据传输、属性读/写/通知 | 官方 API 文档 `nearlink-ssap-server-connect`、`nearlink-start-data-transfer` |
| **不提供**的能力 | 任何业务/语义能力（无位置、无行为识别、无健康数据）；它只是**一条链路** | 同上 |
| 硬件要求 | 手机需**硬件支持**星闪；官网明确"星闪与具体硬件支持能力有关，**无法通过系统升级支持**" | 华为官网《华为手机星闪™（NearLink）功能》 |
| 数据发送约束 | 连续调用 `writeData` 会造成发送队列拥塞；官方建议**发送间隔 10ms** | NearLink Kit 常见问题 |

### 对本项目的意义

- **星闪 = 自研硬件终端（如 ESP32 类）与手机之间的通信方式**，仅此而已。
- 它**不能**帮我们拿到老人健康数据（那是 Health Service Kit 的事），也**不能**帮我们控制智能家居。
- 引入星闪会带来一串连带成本：HarmonyOS 开发能力 + 硬件模组 + 天线设计 + 认证。
- **在与 ICT 创新赛的关系上**：第十一届创新赛是"华为云"导向（赛题 1/2/3 全部围绕云与 Agent），星闪**不是任何赛题的技术要求**，对报名资格零帮助。

### 定性

> ⚠️ **客观条件限制下的取舍**：星闪技术上可用，但**投入产出比低，且与赛事技术要求无关**。
>
> ✅ **决议（2026-10-14）**：星闪在项目书中写为**后期扩展**，架构上仅在 `TransportChannel` 端口保留占位
> （见 `09` §3.2）。不进入一期实现，但**不删除**——保留它才能体现"我们评估过并给出了演进路径"。
>
> ❗ 赛题一（已选定）是**华为云**导向（CodeArts + RDS/Redis + 云上部署），
> 星闪**不是赛题一的技术要求**，对报名资格零帮助。

## 2. Health Service Kit（运动健康服务）

### 2.1 架构事实（关键，v1 理解有误）

v1 写的是"智能穿戴提供的心率、血压、HRV"。实际情况：

```
华为穿戴设备 / 血压计 / 体脂秤
        │ （蓝牙）
        ▼
   华为运动健康 App          ← 数据在这里聚合
        │ （用户授权 + 华为账号）
        ▼
   Health Service Kit  API    ← 第三方应用只能到这里
        │
        ▼
     我们的应用
```

**我们拿到的不是传感器原始数据，而是"华为运动健康 App 里已聚合的数据集"。**

### 2.2 数据项与时效性（官方《数据开放总览》）

| 数据子类 | 数据项 | 数据及时性 | 支持读 | 支持写 |
|---|---|:--:|:--:|:--:|
| 日常活动 | 步数、热量、距离 | **小时级** | Y | Y |
| **心率** | 动态心率、静息心率、**心率变异性（HRV）** | **小时级** | Y | Y |
| 血氧 | 瞬时血氧饱和度 | 小时级 | Y | Y |
| 压力 | 压力得分 | 小时级 | Y | Y |
| 体温 | 体温、皮肤体温 | 分钟级 | Y | Y |
| **血压** | 收缩压、舒张压、脉搏 | **分钟级** | Y | Y |
| 体重 | 体重、体脂、BMI | 分钟级 | Y | Y |
| 身高 | 身高 | 分钟级 | Y | Y |
| 情绪 | 情绪数据 | 小时级 | Y | Y |
| 睡眠 | 睡眠分期采样、睡眠记录 | 分钟级 | Y | Y |

> ⚠️ **"小时级"对"实时监护"是硬伤。** 官方原文提示：若穿戴设备**未连接手机蓝牙**、或**华为运动健康 App 未设置后台保活**，则"**无法保证数据及时性体验**"，并要求开发者"考虑各类极端情况"。

### 2.3 血压数据的真实来源

官方《查询健康类数据》说明：

> 体重、血糖、**血压**数据来自华为运动健康 App"设备 > 添加设备"中支持的**体脂秤、血糖仪、血压计**测量的数据，及**手动输入**的数据和**应用写入**的数据集合。

即：**血压不是所有华为手表都能测**。手表测血压需要医用级设备（Watch D 系列）。

### 2.4 开发者资质限制（**对高校团队影响最大**）

官方《数据开放总览》原文：

> 开放等级中，表示该数据权限为**高阶数据，暂不对个人开发者开放**。如需使用，请使用**企业账号**重新注册并申请权限；基础数据，个人及企业开发者均可申请查询/使用。

行业 FAQ 补充：个人开发者可申请接入，但**读/写开放等级为基础的**用户数据（如步数、热量、距离），且需**明确项目或测试结束时间**，存在被回收的机制。

**结论：学生团队以个人开发者身份，只能稳定拿到"基础数据"；心率/血压等"高阶数据"需企业资质。**
**审核周期约 15 个工作日。**

### 2.5 其他硬性限制

| 限制 | 说明 |
|---|---|
| 产品类型 | 申请时**产品类型必须选"HarmonyOS 应用"** |
| 团队账号 | **暂不支持团队账号下的成员账号独立**使用运动健康开发服务 |
| 权限最小化 | 不可申请超出业务范围或暂不使用的权限；华为会**不定期抽查**（抽样检查、API 监控、派专员核查） |
| 用户授权 | 最终可用的数据 = **服务审批通过的权限 ∩ 用户逐项授权的权限**（用户可只授权部分） |

### 定性

> ⚠️ **这是"客观条件限制"与"系统缺陷"的典型混合体，必须分开写：**
>
> - **客观条件限制**：数据时延小时级、依赖用户已用华为穿戴 + 运动健康 App、高阶数据需企业资质 → **不是我们能修的**
> - **系统缺陷**：如果我们把"小时级数据"包装成"实时健康监护"，那是**方案层面的错误**，必须改

## 3. 智能家居数据（HarmonyOS Connect / 鸿蒙智联）

### 已核实事实

- HarmonyOS Connect 的官方定位是**面向消费领域的智能硬件开放生态**，服务对象是**设备商、解决方案提供商、模组伙伴、芯片伙伴**。
- 接入路径是：**产品解决方案 → 产品集成 → 应用开发 → 产品测试 → 产品认证**，通过认证才能获得 HarmonyOS Connect 品牌授权。
- 健康设备接入还有独立流程：**"与华为 BD 沟通合作意向，签署合作协议后，获取 Wellness Profile 开发套件"**。

### 对 v1 的判定

v1 期望读取的"卧室灯开关时段、不同区域人体传感器激活情况、门锁解锁情况"：

- 这些数据属于**设备厂商的云侧数据**，**不存在面向第三方 App 的公开 API**。
- 即使有，也需要**与厂商签合作协议**——高校团队不具备该条件。
- 华为的 IoT 平台（智慧生活 App）是**统一管理平台**，不是数据开放平台。

### 定性

> ❌ **不可得（客观条件限制）**。
> 不是"难度大"，是"没有这条路"。
>
> ✅ **决议（2026-10-14）**：**不删接口，改为空实现占位**。
> `HuaweiSmartHomeSource.capabilities()` 直接返回
> `{available: false, unavailableReason: 'HarmonyOS Connect 未提供面向第三方应用的设备状态接口'}`，
> UI 据此自动降级（不渲染该维度）。
> **这比删掉更好**：它把"不可得"编码进了系统，答辩时可直接演示降级行为。
> 详见 `09` §3.2 / §四。

## 6. 推送能力（华为 Push Kit / HMS Core）

> 新增依赖。动因：`11` 已决议 D-07（**前期主要适配 Android**，因为需要真正的离线推送）。
> 完整方案见 [`11-客户端与推送方案.md`](11-客户端与推送方案.md)。

### 已核实事实

| # | 事实 |
|:--:|---|
| 1 | **FCM 在中国大陆基本不可用** → Android 必须走厂商通道或第三方 |
| 2 | 华为 Push Kit **支持平台**：Android、iOS、Web、Quick App、HarmonyOS |
| 3 | 需在 **AppGallery Connect 开通"推送服务"权益** |
| 4 | 开发环境：JDK 1.8.211+、Android Studio Chipmunk 2021.2.1+、**minSdkVersion 19+** |
| 5 | **建议测试设备为 EMUI 10 及以上的华为手机** |
| 6 | SDK 最新 **`com.huawei.hms:push:6.13.0.301`**（2025-12-24），建议匹配 HMS Core APK 6.12.0.300+ |
| 7 | 有 **QPS 配额**；错误码 503 = 流量控制 |
| 8 | 错误码 **6003 = 指纹证书配置不一致**（打包证书与 AGC 配置的 SHA256 指纹不符） |
| 9 | 存在社区项目 `fei-ke/HMSPush`（817 stars），目标为**"让非华为设备支持 HMS 推送"** |
| 10 | ❗ **荣耀已从华为拆分，推送通道独立**：荣耀 100 系列起"完全剔除了 HMS 与华为全家桶"；腾讯云文档明确"**无法继续通过华为通道下发消息**" |
| 11 | ❗ **两个硬门槛**：荣耀推送需**荣耀开发者企业账户**；**小米要求必须上架应用市场**才能正常推送 |
| 12 | 聚合方案覆盖面：**个推**（含华为/鸿蒙/荣耀/小米/OPPO/vivo/魅族/UPS）、**极光**（含小米/华为/OPPO/vivo/荣耀/魅族/FCM/鸿蒙/蔚来） |

### 定性

> ⚠️ **受限**。华为 Push Kit 的到达率**强依赖设备是华为手机**：
> 官方测试建议为华为手机；社区存在专门让非华为设备支持 HMS 推送的项目，侧面说明非华为设备原生支持有限。
>
> ❗ **重要更正**：**荣耀不是华为**。荣耀 2020 年已拆分，2024 年起系统能力逐步从华为转移，
> **HMS 通道不再能下发到荣耀新机型**，必须单独接 HONOR Push。
>
> ❗ **且存在企业门槛**：荣耀推送需企业账户，小米要求上架应用市场——学生团队大概率拿不到。
> → **长连接兜底不是可选项，而是必需品**。
>
> ❗ **尚未实测确认**（记为 T-12）：在实测之前，**不要写"支持全部 Android 设备"**。
>
> ⚠️ **另一个容易说错的地方**：Push Kit 属于 **HMS Core**，**不是华为云产品**。
> 赛题一要求"基于华为云产品"，Push Kit 属于**额外使用的华为技术**，能加分但**不能替代**四项强制要求。
> 华为云**没有**面向 App 的推送服务（SMN 是云资源运维通知，不是 App 推送）。

### 替代路径

采用 **`PushChannel` 抽象 + 双通道**：主通道 HMS Push（仅华为设备离线可达），
兜底自建 WebSocket 长连接（全平台在线可达），
两者均不可用时在应用内留"未读事项"红点（拉取兜底）。详见 `11` §三。

## 7. 端到端实时语音（已核实）

> 完整选型与对比见 [`12-实时语音与模型选型.md`](12-实时语音与模型选型.md)。这里只记结论。

| 供应商 | 模型 | 结论 |
|---|---|:--:|
| **阿里云百炼** | `qwen-audio-3.1-realtime-plus` | ✅ **存在**：实时双工、支持工具调用与联网搜索、默认音色 `longanqian_v3.1`、上下文 262,144；有官方 `dashscope` Python SDK + 官方示例仓库 |
| **火山引擎** | 豆包实时语音 3.0（Seeduplex） | ✅ **存在**：全双工端到端，官方文档含 Python 示例 |
| **华为云** | MaaS / SIS | ❌ **无对等产品**：MaaS 是文本/多模态 LLM（支持工具调用）；SIS 是 ASR/TTS **分离**方案，非端到端 |

### 关键约束

1. ❗ **联网搜索与工具调用互斥**（Qwen）：`enable_search` **不能与 Function Calling 同时启用**
   → 对策：把搜索包装成自建工具走 FC（`12` §四）
2. ❗ **成本**：Qwen 音频输出 **150 元/百万 token**；且**华为云代金券不能用于阿里云/火山引擎**
3. ⭐ **`smart_turn` 语义轮次判定**（"啰""啊"不打断）**恰好命中老人口语场景** —— 这是个真实的选型理由

### 定性

> ⚠️ **客观条件限制**：华为云**不存在**端到端全双工实时语音产品，
> 其路线是 SIS(ASR) + MaaS(LLM) + SIS(TTS) 三段拼接，延迟叠加且不支持全双工打断。
> 而本项目目标用户是口语化、带语气词、停顿长的老人，**全双工与语义轮次判定是体验的决定性因素**。
> → 实时语音通道采用第三方；**华为云承担平台与 Agent 侧职责**（双模型分工，见 `12` §5.3）。
