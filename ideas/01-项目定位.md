## 一、一句话定位

> **AgeGuard 是一个面向老年人与异地家庭的 AI 关怀协作系统。它不替代微信，而是把"老人表达的需求"变成"可追踪、可接手、可反馈的家庭事项"。**

对应的英文一句话（答辩用）：

> *AgeGuard turns an elder's spoken need into a tracked, owned, and closed-loop family task.*

---

## 二、问题定义

### 2.1 我们要解决的"那一个"问题

家庭关怀的失败**不在于缺少沟通工具**，而在于：

| 现象 | 真实缺口 |
|---|---|
| 老人给子女发了一条消息，子女在忙，回头忘了 | 需求**没有归属人** |
| 老人不好意思反复提，就把事放下了 | 需求**没有跟进状态** |
| 子女做了但没说，老人不知道，又不好意思问 | 结果**没有回传** |
| 老人的需求表达很含糊（"最近家里挺冷清的"） | 需求**没有被翻译成可执行动作** |

**核心命题：把"关怀"从一次性的消息传递，变成一个有状态、有归属、有反馈的协作流程。**

### 2.2 为什么现有工具不够

| 现有方案 | 擅长 | 缺口 | AgeGuard 的补充 |
|---|---|---|---|
| 微信 / 电话 | 聊天、通话、消息传递 | 事项散落在聊天记录；跟进靠人记 | 把确认后的需求整理成**结构化事项卡片** |
| 备忘录 / 待办清单 | 提醒某人做某事 | 不是为"老人—亲属"协作设计的；老人不会用 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、内容生成 | 停留在对话 | 通过**受控工具调用**推动流程 |
| 智能手表健康监测 | 心率、步数、睡眠 | 数据 ≠ 行动；老人看了也不知道该做什么 | （本项目的**非核心**补充） |

### 2.3 明确"不做什么"（边界即定位）

以下事项**已被有意排除**，并在材料中明确写出（这是加分项，不是减分项）：

| 不做 | 原因 |
|---|---|
| ❌ 再造一个微信 / 完整社交平台 | 没有差异化，且用户迁移成本不可承受 |
| ❌ 自建视频通话、复杂群聊 | 与核心闭环无关，成本极高 |
| ❌ 读取微信聊天记录 / 自动发微信消息 | 无公开接口，违反平台条款（见 `06` §6） |
| ❌ **智能家居数据采集**（灯、人体传感器、门锁） | **技术不可得**：HarmonyOS Connect 面向硬件厂商，无第三方数据 API（见 `06` §3） |
| ❌ **实时健康监护 / 跌倒检测** | 数据时延为**小时级**，且高阶数据不对个人开发者开放（见 `06` §2） |
| ❌ 首版投入复杂硬件（含星闪终端） | 核心软件价值未验证前投入硬件，成本收益比差（见 `06` §1） |
| ❌ 疾病诊断、用药建议 | 医疗器械监管风险，超出团队资质 |

> ⚠️ **写作规范**：上表中"技术不可得"的三条，在申报材料里必须写成**"能力边界与取舍"**（客观条件限制），
> 而**不能**写成"后期将支持"（那是虚假承诺），也**不能**写成"我们还没做完"（那是系统缺陷）。
> 区分标准：**换一支更强的团队能不能做到？** 能 → 系统缺陷；不能 → 客观限制。

## 三、产品形态（四层）

```
┌──────────────────────────────────────────────────────────┐
│  老人端 APP                                               │
│  ① 联系家人   ② 我有件事想说   ③ 查看事情进度             │
│  大按钮 · 少步骤 · 确认后才分享                            │
├──────────────────────────────────────────────────────────┤
│  亲属端 APP                                               │
│  ① 查看授权事项  ② 接手处理  ③ 更新进度  ④ 反馈完成结果    │
├──────────────────────────────────────────────────────────┤
│  后台服务                                                 │
│  账号绑定 · 事项数据 · 状态同步 · 权限校验 · 提醒调度       │
├──────────────────────────────────────────────────────────┤
│  AI Agent + 工具层                                        │
│  理解需求 → 生成事项草稿 → 调用工具 → 检查执行结果 → 反馈   │
│  可选扩展：系统通知 · 日历接口 · 语音终端（ESP32）          │
└──────────────────────────────────────────────────────────┘
```

**核心理念：不替代微信沟通，而是帮助家庭把关怀落实到行动。**

**状态机（产品的技术核心）：**

```
草稿(draft) ──老人确认──→ 待接手(pending)
   │                          │
   └──老人取消──→ 已取消       ├──亲属接手──→ 处理中(in_progress)
   (cancelled)                │                    │
                              │                    ├──反馈完成──→ 已完成(done)
                              │                    └──超时未响应──→ 待跟进(overdue)
                              └──亲属拒绝/超时──→ 待重新分配(reassign)
```

## 四、核心竞争力（修订版）

> ⚠️ v2 的表述中反复出现"仍需验证""尚需原型验证"。这本身是诚实的，但**在答辩现场是弱表述**。
> 处理方式：**主张（claim）要确定，证据（evidence）要标注状态。**
> 例：不说"这可能有用"，而说"**我们主张 X，当前证据等级为 B（小样本用户测试，n=8），后续计划提升到 A**"。

| # | 竞争力 | 主张 | 证据状态 |
|:--:|---|---|---|
| C1 | **从聊天沟通转向家庭事项闭环** | 把老人表达的需求转换成可跟进、可接手、可反馈的事项，是本项目与微信的根本差异 | ⚠️ 待用户测试验证（`07` E-03 事项闭环率） |
| C2 | **面向老人设计的低门槛交互** | 首页只呈现少数明确动作；大字、大按钮、自然语言输入、可撤销的确认流程 | ⚠️ 待可用性测试（`07` E-01/E-02） |
| C3 | **Agent 不只回答，还能在权限范围内调用工具** | 展示的是"输入 → 工具调用 → 执行结果 → 错误处理"的真实工作流，而不是聊天文本 | ✅ 可由系统日志证明 |
| C4 | **授权与可追踪性** | 老人可确认分享对象、取消草稿、撤销访问；亲属只能看到被授权的事项；状态与操作可追溯 | ✅ 可由权限测试证明（`07` E-05） |
| C5 | **不要求家庭迁移全部通信习惯** | 首版不依赖微信私有接口；外部连接在接口能力、权限、测试均确认后才加入 | ✅ 可由架构图证明 |

### 4.1 竞争定位矩阵（v2 §5 的修订）

| 方案 | 擅长解决的问题 | 可能的缺口 | AgeGuard 补充价值 |
|---|---|---|---|
| 微信等通信工具 | 聊天、通话、消息 | 事项易分散，跟进依赖用户 | 将授权需求变成**可追踪事项** |
| 普通待办工具 | 提醒某人做某事 | 未针对老人—亲属协作场景 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、内容生成 | 可能停留在对话 | 通过**受控工具**推动流程 |
| 健康监测设备 | 采集生理指标 | 数据 ≠ 行动 | （不做这条） |
| **AgeGuard 目标形态** | **家庭关怀协作闭环** | 价值需原型验证 | 低门槛交互 + 授权 + 状态可见 |

## 五、与 v1 的关系（已重新定位，非作废）

v1 `idea.md` 把项目定义为"结合智能硬件了解关怀老人"的**监测型产品**。
✅ **决议（2026-10-14）**：产品中心采纳 v2 的**协作型**定位，但 v1 的硬件要素**不作废**——
改为**架构抽象 + 二期扩展**，在项目书中分层论述（依据 `09` §6.1 强制模板）。

| v1 要素 | v3 处理 | 依据 |
|---|---|---|
| 智能穿戴 SDK 取心率/血压/HRV | **保留为 `VitalSource` 端口的二期适配器**（`HuaweiHealthSource`），一期用 `MockVitalSource` | `06` §2；`09` §3.2 |
| 智能家居传感器数据 | **保留为 `EnvironmentSource` 端口的空实现占位**（运行时返回不可用，UI 自动降级） | `06` §3；`09` §3.2 |
| 星闪 NearLink | **保留为 `TransportChannel` 端口的预留实现**，写为后期扩展 | `06` §1；`09` §3.2 |
| 全局记忆"前期 FTS+BM25，后期 RAG" | ✅ **完整保留**，抽象到 `04` §三 | — |
| ReAct 统一循环 | ✅ **完整保留**，抽象到 `04` §二 | — |
| AI 闲聊采集需求 | ✅ **完整保留**，是一期主要数据源 | — |

> ⚠️ **保留 ≠ 声称已实现**。分层论述规则见 `09` §六（含禁用表述清单）。
