# 13 · 产品形态与硬件闭环

> 2026-10-17 用户逐轮确认的设计基线；**已决策不等于已实现或已通过测试**。
> 本文统一产品形态、设备交互、药盒事件及药品维护规则；与旧版 RN／全双工／纯软件设计冲突时，以本文及 `12` §四为准。
> 外部能力、SDK 语言与来源见 `08` §十二；实施参数和未决问题集中在 `12` §2.7。

## 一、产品与一期范围

**一套完整后端＋两个硬件节点＋一个家庭应用。**

- 老人语音盒：日常表达、澄清、草稿确认／取消、查询进度、接收反馈。
- 药盒开合节点：提供可追溯的容器开合事件，不证明取药、吞服或用药正确。
- 家庭应用：保留 Web 亲属／配置／联调入口及移动通知接收能力；最终客户端路线、框架和封装见 T-67。主推送在既有候选中实测选择，Webhook 仅补充通知，不能替代站内待办和身份校验。
- 完整后端：人的身份、家庭关系、设备身份与绑定、资源级授权、事项状态机、药品与计划、记忆、调度、通知记录、审计、持久化和失败恢复不删减。

核心价值仍是经授权的家庭关怀协作；硬件是主要交互入口和真实事件来源，不是装饰性加分项。Web 文字流程可以先做通联调，但不能代替最终硬件验收。

首版不同时扩展毫米波、温湿度、墨水屏、远场唤醒或全双工。OpenHarmony 是能力和可复现性合适时的优先选项，不要求所有节点采用同一系统；使用 ESP-IDF 的节点不得标成 OpenHarmony。板型、固件和音频方案必须单独实测。

使用对象须能表达意愿并完成授权；一台语音盒首版绑定一位主要老人，不承诺识别同住者身份。设备认证不能证明当次操作一定由本人完成。

## 二、老人实际操作的盒子

### 2.1 外形与操作

第一版无触摸屏，主要控件为大号说话键、确认键、取消键；另有清晰录音指示、状态灯、扬声器、音量和麦克风静音控制。具体尺寸、布局、单击开始／结束还是长按录音，在样机上验证，不预填适老效果。

- 按键式录音与播放是第一语音里程碑；远场唤醒和全双工不阻塞它。
- 状态灯区分录音、处理、待确认、离线和错误；业务状态还须用准确播报表达，不以一种绿灯同时代表处理中与完成。
- 多个事项并存时，提供查询和逐项反馈，不用一盏灯表示所有事项已经解决。
- 共享空间的敏感播报遵守老人设置；录音范围、静音行为和隐私提示需要真机验证。

### 2.2 确认上下文

确认键只作用于当前明确播报、未过期的操作，不是永久的“已吃药”按钮。

后端维护单个设备当前有效的 `context_id`、操作类型、资源 ID、版本和有效期。盒子播放内容后上报执行结果；确认／取消事件关联这一上下文。后端在执行时再次校验绑定、权限、版本和有效期。

无有效上下文、上下文过期或已被替换时，按键不得发送旧草稿、授权新接收人或补写服药记录。如何在断线、重启和多个待办下恢复上下文见 T-58。

## 三、亲属端的具体页面

| 页面 | 内容与操作 | 边界 |
|---|---|---|
| 待跟进事项 | 授权请求、接收人、责任人、接手、处理反馈 | 两人同时接手由后端原子裁决；不默认展示全部聊天 |
| 提醒与记录 | 每次提醒执行、药盒事件、本人自报、亲属反馈 | 不压成一个“服药已核验”勾选框 |
| 药品与提醒 | 个人药品清单、计划草稿、来源、差异、版本、设备同步 | 查看权限不等于编辑或启用权限 |
| 家庭与设备 | 绑定／解绑、授权、规则、在线状态、最后同步时间 | 亲属不能给自己扩大共享范围 |

移动通知默认提供通用入口；打开后登录并重新鉴权读取详情。Webhook 发出、平台受理、送达、打开、接手分别记录，缺少回执时保留未知。

## 四、设备如何与完整后端交互

### 4.1 分离通道与业务入口

```text
语音盒 ──音频上传／获取（HTTPS）─────────→ 后端语音接口
   │                                            │
   └─事件、状态、回执（MQTTS）→ IoTDA → 设备接入适配层
药盒节点 ──开合与设备状态（MQTTS）───→ IoTDA ────┘
                                                ↓
                      身份／绑定／授权／事项／药品计划／证据／审计
                                                │
                   RDS：业务事实、事件、持久化发送任务
                   Redis：会话、缓存、频控等辅助能力
                                                │
             ┌──────────────────────────────────┴───────────┐
             ↓                                              ↓
       亲属端业务 API                              IoTDA 下行 → 盒子反馈
       主通知＋补充 Webhook
```

音频不默认走 IoTDA 消息分片；实时音频通道是后续验证项。IoTDA→后端的数据转发接口与面向亲属的通知 Webhook 是不同用途；转发协议及认证见 T-57。

- 设备只持有设备作用域凭据，不下发云账号 AK/SK 或模型 Key。
- 音频接口使用经验证的设备身份和限权凭证；不能凭请求体里的 `elder_id` 访问数据，也不能把 MQTT 已连上等同于后端 HTTPS 已认证。
- 绑定、更换使用者、解绑、停用与凭据撤销须有明确流程。
- 接入层认证来源、检查结构与绑定、幂等入库，再交业务规则处理。传感器消息不直接调用 LLM 修改事项。

### 4.2 普通事项的端到端顺序

1. 录音并建立会话；AI 提取需求，不明确时澄清。
2. 后端保存草稿；盒子播报内容、接收人和当前确认动作。
3. 老人确认；后端复核授权、草稿版本和有效期。
4. 一次事务持久化事项状态、事件记录及待发送任务；成功后才能反馈“已发送”。
5. 后台任务有限重试通知；亲属接手、处理、提交结果。
6. 后端下发最新状态，盒子回报接收和执行结果；不能据此断言老人已理解或需求已满足。

通知任务与业务变更共同持久化，避免事务提交后进程崩溃导致通知永久丢失。客户端重复请求、多个亲属并发接手和工作进程重试都由后端幂等／并发约束处理，不能只靠 Redis TTL。

### 4.3 下行、回执与状态恢复

下行契约至少表达 `command_id`、`context_id`、资源版本和 `expires_at`。具体字段和 Topic 不是已经实现的 API，见 T-57～T-59。

设备区分已接收、执行成功／失败、用户确认／取消。协议 ACK 不等于后端持久化，也不等于播放完成；播放完成不等于听懂。重发时不重复播放，过期内容不执行，旧版本不覆盖新状态。

## 五、如何处理药盒信息

### 5.1 分层而不是一个“去重”操作

| 层 | 输入与处理 | 不允许的捷径 |
|---|---|---|
| 传感稳定化 | 按安装和实测参数过滤抖动，生成稳定开／关事件 | 用过长屏蔽窗口删掉真实多次动作 |
| 传输幂等 | 重传保持同一 `event_id`；后端以设备＋事件标识唯一入库 | 把重传算作新开盖 |
| 活动片段 | 保留多次真实事件，按规则合并展示、减少打扰 | 把合并展示当成物理动作只有一次 |
| 业务关联 | 按容器、计划、事件时间及质量关联；不唯一则保留不确定 | 一次开盖同时算给所有药品／计划 |
| 提醒与跟进 | 低打扰询问、记录本人反馈、执行有效的授权规则 | 开盖即服药、无反馈即漏服 |

事件契约应保留事件 ID、启动标识、序号、类型、设备观察时间或空值、时钟质量，以及后端接收时间；设备身份来自经过认证的接入上下文。发生时间不可靠时不能用接收时间冒充发生时间。重复数据的幂等约束和具体消息适配见 T-57／T-59。

诊断边沿、物理事件、片段摘要有不同保留期限；可追溯不等于永久保存家庭活动轨迹。

### 5.2 一次提醒的四个独立维度

| 维度 | 状态示例 |
|---|---|
| 提醒执行 | 待播放、设备回报已播放、播放失败、未知 |
| 设备观察 | 开／关事件、活动片段、离线、时间不可靠 |
| 人员反馈 | 未反馈、本人自报已服用、本人自报未服用、本人不确定 |
| 协作跟进 | 无需跟进、待联系、已接手、已有反馈 |

“已完成”必须说明对象：提醒播放完成、亲属联系完成或反馈记录完成，均不能替代“客观服药已核验”。来源标签不是可以累加升级的真实性分数。

### 5.3 反复开盖但无人服药

- 系统只有开合信号时，只能显示“检测到多次开启，尚未收到本人反馈”。
- 传感器不能区分补装、整理、查看、他人开启与吞服。可低打扰询问一次，不逐次催服或逐次通知亲属。
- 本人说明未服用时，保存自报；开盖次数不覆盖这一反馈。
- 本人自报已服用但没有开盖记录时，保留两种来源，不自动判定撒谎，可能使用了别的容器。
- 亲属说明在补装药时，增加有来源的解释，不删除物理记录。
- 设备离线不等于没有动作；无反馈不等于漏服或发生危险。

演示与测试使用空盒和脚本化反馈，不要求老人真实漏服、补服或重复服用。

## 六、预授权跟进与有限离线

### 6.1 跟进规则

普通生活事项逐件确认。重复提醒可由老人**事先明确开启**具体规则：接收人、触发条件、共享内容、频率和有效性；默认关闭、可撤销。

规则执行时后台重新检查授权，不因为未回复自动扩大接收人。没有有效预授权时，不向亲属擅自共享健康反馈。询问／重试次数、普通关怀静默时段和触发阈值见 T-62，不照抄旧稿固定数值。

普通关怀频控不得擅自移动已确认的用药提醒；无反馈时不反复催促服用，不建议补服、加量或改药。

### 6.2 有限离线

- 有限缓存事件；容量、溢出提示、补传、加密和清理见 T-60／T-66。
- 在时钟可信、配置仍有效等前提下执行已同步、已确认的本地提醒。
- 离线不声称已通知家属；云端无法实时获知本地执行结果时显示未知。
- 离线重启、时间不可信、计划失效或上下文过期时明确降级，不猜时间执行。
- 恢复联网后去重补传并同步最新版本，不重播过期提醒。

设备离线时不能保证即时撤回旧计划。后端已更新与设备已接收是不同状态；旧计划有效期、具体用量播报的失效降级及同步确认见 T-61／T-65。失效时只能提供核对当前安排的通用提示，不能继续播报不确定的用量。

## 七、个人药品清单与亲属协助维护

### 7.1 数据对象与来源

| 对象 | 必须保留的区别 |
|---|---|
| 个人药品记录 | 内部 ID；规范名称、商品名、剂型、规格及按需提供的识别依据；相似名称不自动合并 |
| 用药安排版本 | 原文／来源、已核对结构化字段、录入与核对人、起止／生效时间、修订关系 |
| 提醒配置 | 通知时间与方式、播报开关、跟进规则；不等同于治疗方案 |
| 注意事项 | 原文、来源、按需详细内容及经核对的短播报；家属生活备注单列 |
| 个人别名 | 对应具体药品 ID、确认者、适用范围、时间及失效状态 |
| 提醒执行实例 | 对应当时计划版本，关联设备事件、人员反馈、通知和跟进 |

厂商说明书、个体处方／药师交代、家属便签分别标识；有标签不代表完整、最新或适用于该人。图片按必要范围采集，不默认上传整份含无关身份／诊断信息的处方；保留及删除策略见 T-66。

“每天两次”不自动转换为“每十二小时一次”，“饭后”不擅自转换成固定钟点；具体安排不清晰时保留草稿，联系专业人员核实，不让 LLM 补齐。

### 7.2 授权、修改和启用

查看、协助录入、管理提醒是不同权限，不因亲属绑定自动获得。获授权亲属可以帮助整理已有安排，不因此获得制定治疗方案的能力。

关键字段修改形成新版本：展示前后差异、来源与核对状态，按授权流程确认启用。资料不明确或冲突时存待核对稿，不投入具体用法用量播报。界面写“家属已对照原件核对”，不得冒充专业审核。

老人确认解决意愿与权限，不证明医学正确性。停用应用提醒不等于停药；改字段不等于医嘱变化。角色权限和启用确认的具体组合见 T-63；AI 不得自行确认或启用。

变更后取消旧版本未来任务和播报，跟踪设备同步；历史执行和反馈继续关联当时版本。不能只更新数据库而让过期音频继续执行。

### 7.3 开盖与特定药品播报

默认开盖只记录事件，并在规则允许时提供一次可选入口，不无条件读出药名、用量和注意事项。

- 到已确认提醒时间：按当前有效配置短提示，具体内容播报需已开启且已核对。
- 开盖可能关联当前提醒：可问“需要听当前提醒内容吗”；容器含多药或对应不明时不猜药品。
- 主动询问：先确定所指药品，再读取有来源且有效的内容；不足时提示查看标签或联系家人／药师。
- 反复开盖不反复催服；已记录反馈后不因新开盖再次要求服用。

具体用法播报采用受控模板／已核对文本，不由 LLM 现场自由生成。AI 整理的长说明只能先成为待核对稿，不能丢失条件、否定、单位或适用范围后直接播出。联网搜索不充当个体化用药指导。

### 7.4 简称与模糊指代

个人别名表＋当前会话上下文＋必要澄清，替代全局“简称等于某药”的规则。

- 别名属于该老人的具体药品记录；新称呼不因听懂一次就永久保存。
- 已确认且仍唯一的别名可提出候选；涉及服药反馈或具体用法播报时清楚复述对象。
- 多候选、识别不可靠或找不到记录时澄清，不取置信度最高者直接执行。
- 颜色、外观、用途或“早上那个”不能单独证明药品身份。
- 药品停用、换剂型／规格、计划变化后重新检查别名，不自动迁移到新药。
- “药快没了”无法明确具体品种时，可形成“药物可能不足，请亲属联系核对”的草稿；不能猜药。
- 无法确定药品及本次计划时，自报保留为待关联记录，不误写到某次执行实例。

## 八、验收与分工纪律

| 编号 | 必测场景 | 通过条件 |
|---|---|---|
| H-01 | 未确认草稿／过期确认／上下文替换 | 无越权发送或错误服药记录 |
| H-02 | 未授权用户、错误设备绑定、解绑后重放 | 后端拒绝未获授权访问／执行 |
| H-03 | 同一事件重传 | 一个业务事件，无重复通知 |
| H-04 | 抖动与真实连续开合 | 区分噪声和真实次数；参数有测试依据 |
| H-05 | 多次开盖但无服药 | 设备事件真实保留，服药反馈仍未知 |
| H-06 | 开盖与本人未服用／已服用自报不一致 | 来源并存，不自动改成核验完成 |
| H-07 | 多药／多计划关联歧义 | 不批量算作各药已服用 |
| H-08 | 断网、补传、时间不可靠 | 不伪造发生时间，不误触发当前提醒 |
| H-09 | 下行重发、过期、旧版本与播放失败 | 无重复／过期执行，不把受理当作听懂 |
| H-10 | 预授权默认关闭、撤销及接收人变更 | 无擅自共享或扩大范围 |
| H-11 | 亲属改关键字段、资料冲突、无编辑权限 | 草稿／新版本／核对机制有效，不冒充专业审核 |
| H-12 | 模糊简称、冲突别名、换规格／停用 | 必要澄清，旧别名不误指新药 |
| H-13 | 计划变更而设备离线 | 同步状态真实、旧任务与播报按失效策略处理 |
| H-14 | 删除、撤销及备份／索引恢复 | 不从派生摘要或恢复流程无意重建已删除敏感记录 |
| H-15 | 进程在提交后崩溃、并发接手 | 持久化任务可恢复，状态无重复副作用 |
| H-16 | 空盒实验与老人使用对照 | 原始实验条件清楚；硬件降低负担的主张有独立测量 |

以上是验收要求，不是已通过结果。硬件真实采集、模拟事件与视频回放逐项标识；空盒实验不证明真实服药或临床效果。

## 九、取舍与限制

- **当前配置的能力边界**：开合传感器不能观察吞服；设备离线不能即时收到新计划。不能用模型弥补不存在的观测。
- **战略取舍**：一期不做医疗端、自动给药、复杂传感融合或远场全双工；商用穿戴／家居通路不阻塞自制设备。
- **必须解决的系统问题**：误计次数、误写服药事实、越权访问、过期播报、旧计划未撤销、数据与通知丢失等不能伪装成外部限制。

官方评分与工程采用的产品数量不是同一回事；IoTDA／OpenHarmony／MaaS 要有真实职责和证据，不承诺技术覆盖度保证晋级。部署自动化不能替代用户价值与对照评测。
