# 04 · Agent 架构

> 当前原则：Agent 产出待校验的理解、候选与草稿；身份、授权及业务副作用由后端控制。
> `13` 是当前产品／硬件基线。本文一～四及延迟表的 Qwen 全双工流程为增强候选，不再作为首个按键语音盒的前置；具体模型见 `11`。
> 药品、计划、个人别名和传感器事件遵守 `13` 的来源、版本与证据边界。

## 一、两层架构

### 1.1 本质区别

> **全双工语音层**解决 **"怎么听、怎么说、什么时候该说"** —— 交互问题
> **事务层（Agent）**解决 **"要做什么、怎么做、做完没有"** —— 任务问题

| 维度 | 语音层（Qwen Realtime） | 事务层（华为云 MaaS） |
|---|---|---|
| 解决什么 | 交互：听力、表达、轮次、打断 | 任务：意图、工具、状态、追踪 |
| 核心指标 | **延迟**、自然度、可打断 | **准确率**、可靠性、可追踪 |
| 输入/输出 | 音频 ↔ 音频（流式双向） | 文本 ↔ 结构化结果（+ 工具调用） |
| 是否有状态 | ❌ 基本无状态（会话内） | ✅ 强状态（事项状态机、记忆、权限） |
| 出错代价 | 说错一句话 → 再说一遍 | **错发/漏发事项给家人** → 破坏家庭信任 |
| 可替换性 | 换供应商只换通道 | 换供应商要重验工具调用 |

**关键差别在出错代价**：语音出错是**体验问题**，Agent 出错是**正确性问题**。
→ 直接推出 §1.3 的核心原则。

### 1.2 唯一的交叠点：谁来理解意图

两层**都能**理解老人在说什么，这是唯一必须划清的地方。不说清会出三种坏情况：

| 坏情况 | 后果 |
|---|---|
| 两层都判意图 | 老人听到两遍，或语音层先答了 Agent 又说一遍 |
| 语音层判了却自己动手 | 绕过权限校验 |
| 事务层直接生成话术 | 语气不统一 |

### 1.3 两条铁律（跨层纪律）

> **铁律 1：事务层永远不直接对老人说话。**
> 只返回**结构化结果**，由语音层翻译成人话 → 保证语气一致（§七）

> **铁律 2：语音层永远不直接写数据。**
> 只能通过工具调用，副作用经确定性校验层 → 保证权限与状态一致

### 1.4 事务层的边界原则

> 来源：外部评审意见 —— *"时间检查、任务状态判断、提醒频率限制应主要由确定性程序完成。
> Agent 负责理解复杂反馈、选择允许的处理路径以及生成合适的沟通内容。"*

```
老人输入
   │
   ▼
┌──────────────────┐
│  Agent (LLM)     │  产出：{intent, slots, hypotheses, reply_text}
│  ReAct 循环       │        纯计算，无副作用
└────────┬─────────┘
         ▼
┌──────────────────────────────┐
│  确定性校验层（Deterministic） │
│  · 状态机合法性               │
│  · 权限校验                   │
│  · 频率限制                   │
│  · 幂等键                     │
└────────┬─────────────────────┘
         ▼ 通过才执行
   写库 / 通知 / 提醒 → 审计日志
```

| 交给**确定性程序** | 交给 **Agent（LLM）** |
|---|---|
| 定时触发、超时判定 | 理解老人含糊的自然语言 |
| 事项状态机迁移合法性校验 | 生成澄清问题 |
| 提醒频率限制 | 选择澄清方式（开放式 / 选项式） |
| 权限校验 | 生成沟通话术与共情回应 |
| 幂等与去重 | 从对话中提取结构化字段 |
| 数据写入与审计日志 | 判断"这句话是否在回应之前的事项" |
| 澄清轮次计数 | 生成候选假设 |

## 二、连接方式：Agent-as-a-Tool + 先应答后落实

### 2.1 五种架构方案

| 方案 | 做法 | 适用场景 |
|---|---|---|
| **A** 语音模型全包 | Qwen 同时做对话和工具调用 | **纯陪伴闲聊**（不需要事务状态）。缺点：用不上 MaaS→失去赛题技术栈与代金券；长链推理不适合低延迟模型 |
| **B** 分段录音／识别／播放 | 按键录音→识别→受控业务→播放 | 当前首个硬件里程碑；不承诺全双工，但有明确实际场景，见 `13` |
| **C** 路由式 | 先分类再分派 | 语音层**不具备 FC** 时的替代方案 |
| **D** Agent-as-a-Tool ⭐ | 把整个 Agent 能力封装成语音层的**一个工具** | **全部场景（当前方案）** |
| **E** 快慢双脑 | 快脑即时回应、慢脑异步处理 | D 的落地方式（与 D 不互斥） |

```
Qwen Realtime（语音层）
    │  Function Calling
    └─→ request_task(raw_utterance) → 后端 → MaaS Agent（事务层）
                                            └─ 返回结构化结果
        ←──────────────────────────────────────┘
    Qwen 把结构化结果"翻译"成人话
```

### 2.2 先应答、后落实

全双工的价值是**不让老人等**。若每次都要等 MaaS 处理完再出声，就退化成轮次式了。

```
老人："家里米快没了，谁有空周末帮我带一袋？"
  │
  ├─ t0  流式 ASR（边说边转写，不需等说完）
  ├─ t1  smart_turn 判定轮次结束
  ├─ t2  Qwen 立即出声（不等待！）同时发起工具调用
  │        出声："好，我帮您记一下～"
  │        调用：request_task(raw="家里米快没了，谁有空周末帮我带一袋？")
  │                  ↳ 异步，不阻塞说话
  ├─ t3  MaaS 处理：
  │        抽取 {action: 购买大米, time: 周末, target: 未指定}
  │        → 缺槽位 → 返回 {need_clarify: "target"}
  ├─ t4  Qwen 收到 → 澄清："您是想请哪位家人帮忙？"
  ├─ t5  老人："问问我儿子吧" → 再次 request_task(target=儿子)
  │        MaaS：生成事项草稿 → {draft_id, share_target: 小陈}
  │        Qwen："我准备告诉小陈：『家里米快没了，周末方便带一袋吗？』可以发送吗？"
  └─ t6  老人明确确认 → 交互入口提交当前上下文／版本 → 后端复核提交；不是模型自行调 confirm_item
```

**t2/t3 并行**——老人听到"好，我帮您记一下"的瞬间，MaaS 还没处理完。
目标是降低感知等待，但需测量端到端延迟，不能承诺“零等待”或提前宣称业务成功。

与产品闭环天然同构：

```
表达 → [先应答] → 确认 → [后落实] → 接手 → 处理 → 反馈 → 老人知晓
```

### 2.3 由此得到的设计自由

> **语音层延迟预算要卡死，事务层延迟预算可以宽松。**

MaaS 的延迟不体现在老人感知里，只影响"AI 什么时候说下一步"。
→ **事务层可以用更强但更慢的模型**（`11` §三）。

## 三、语音层的工具集（**只有一个主工具**）

```
Qwen Realtime 的 tools:
├── request_task(raw_utterance: str) → TaskResult     ← ★ 唯一的主工具
│      ├─ {"type": "need_clarify", "slot": "target", "question": "..."}
│      ├─ {"type": "draft_ready", "draft_id": "...", "summary": "...", "share_target": "..."}
│      ├─ {"type": "query_result", "status": "...", "detail": "..."}
│      └─ {"type": "error", "reason": "..."}
├── web_search(query: str) → {answer, sources[]}      ← 自建工具（11 §四）
└── end_conversation(reason: str)                     ← 收尾；旧五分钟候选非盒子首验收参数
```

**为什么只有一个入口**：工具越少，模型越不会调错。把复杂度关在事务层内部，
跨层接口保持极窄——与 `06` §4.1 "Kotlin 只暴露窄接口"是同一条设计原则。

### 边界情况

| 情况 | 处理 |
|---|---|
| Qwen 没调 `request_task`（漏判） | 后端**旁路检测**：一轮对话出现可提取的事项特征但无工具调用 → 日志告警；二期做规则兜底 |
| 调了但参数为空 | 接受空 `raw_utterance` 时用**上一轮原文**，不报错 |
| MaaS 超时 | 返回 `{"type":"error"}` → Qwen 说"我这边有点慢，您再说一次好吗？"（不静默失败） |
| 老人中途改主意 | 再次 `request_task`，事务层用 `cancel_item` / 更新草稿 |

## 四、场景分工表

| # | 老人说的话 | 谁处理 | 路径 | 为什么 |
|:--:|---|---|---|---|
| 1 | "今天天气怎么样？" | **语音层** | 内置知识 或 `web_search` | 无事务状态，延迟敏感 |
| 2 | "今天又是一个人吃饭。" | **语音层** | 纯共情 | 情感场景，**不能等** |
| 3 | "最近家里挺冷清的。" | **语音层**追问 + 可能 `request_task` | §八 多假设推理 | 模糊需求，需澄清 |
| 4 | "家里米快没了，谁有空帮我带一袋？" | **事务层** | `request_task` → 抽取 → 缺槽位 → 澄清 | 事务 |
| 5 | "上次那件事办了吗？" | **事务层** | `request_task` → `query_item_status` | **需要真实数据，绝不能编** |
| 6 | "我昨天忘吃药了。" | **事务层** | `request_task` → 记记录（E1 级） | 事务 + §十一 的低干预原则 |
| 7 | 老人在 AI 说话中途插话 | **语音层** | 全双工打断 | 只有全双工能做 |
| 8 | 口齿不清、反复停顿 | **语音层 `smart_turn`** | 语音层处理 | "嗯""啊"不打断 |
| 9 | 亲属端收到事项通知 | **事务层（NotifyService）** | 推送（`06`） | 与语音无关 |
| 10 | 定时关怀提醒到点 | **确定性程序** + 语音层播报 | §一 分工 | 时间检查必须确定性 |
| 11 | "我想跟女儿说说话" | **事务层** | `request_task` → 创建联系事项 | 事务 |
| 12 | "这道菜怎么做" | **语音层** | 可用 `web_search` | 生活小问题 |

**归纳：**

> **需要改变系统状态 / 读取系统真实数据的 → 事务层**
> **只需要说、听、安抚、解答的 → 语音层**
> **必须准点发生的 → 确定性程序**

## 五、事务层：有界工具编排与业务写入口

以下为示意伪代码，不是已实现的授权系统。身份来自认证入口；工具白名单、schema、授权、确认、幂等及状态由网关强制校验。传感器入库、版本失效和受控播报不必经过 LLM 循环。

```python
def handle_turn(utterance, elder, session):
    ctx = build_context(
        utterance  = utterance,
        profile    = memory.get_profile(elder),       # 沟通偏好、称呼
        recent     = memory.get_recent(elder, n=10),  # 短期上下文
        facts      = memory.search(elder, utterance), # 长期记忆召回
        open_items = item_store.list_open(elder),     # 未闭环事项
    )
    for step in range(MAX_STEPS):                     # 步数上限，防死循环
        thought, action = llm.react(ctx)
        if action.type == "reply":
            return action.text                        # 纯回应，无副作用
        result = tool_gateway.execute_validated(
            action=action,
            authenticated_context=session.auth_context,
            # 校验结构、资源权限、当前确认上下文、幂等及业务状态
        )
        ctx.append(observation=result)
    return fallback_reply()                           # 兜底，不静默失败
```

| 工具 | 作用 | 副作用 | 需确认？ |
|---|---|:--:|:--:|
| `extract_item` | 从自然语言提取事项结构化字段 | ❌ | — |
| `create_item_draft` | 创建事项草稿 | ✅（仅草稿） | ❌ |
| `confirm_item` | 确认并发送事项 | ✅ | ✅ **必须老人确认** |
| `cancel_item` | 取消草稿 / 撤销事项 | ✅ | ✅ |
| `query_item_status` | 查询事项状态 | ❌ | — |
| `search_memory` | 检索长期记忆 | ❌ | — |
| `web_search` | 联网搜索（自建，不走模型的 `enable_search`） | ❌ | — |
| `write_memory` | 允许范围内的记忆候选／更新 | ✅ | 敏感事实不自动确认为真；药品计划走专门版本流程 |
| `ask_clarification` | 生成澄清问题 | ❌ | — |
| `list_contacts` | 列出可选的协作对象 | ❌ | — |
| `set_reminder` | 提醒候选或执行已确认有效配置 | ✅ | 用户确认或明确有效预授权；不自由更改药物安排 |
| `link_feedback_to_item` | 把老人反馈关联到历史事项 | ✅ | ✅ **必要确认后** |

**四条规范：**
1. 每个工具必须返回可判定的成功/失败——不能静默失败
2. 有副作用的工具必须**幂等**——带 `idempotency_key`
3. **Agent 不能直接调 `confirm_item`**——必须由用户界面确认动作触发
4. 每次工具调用写入审计日志——这是竞争力 C3 的证据

> ⚠️ **MaaS 官方警告**（`11` §二）：*"模型并不总是生成有效的 JSON，并且可能会虚构出一些您的函数参数规范中未定义的参数。在调用函数之前，请在您的代码中验证这些参数是否有效。"*
> → `arguments` 必须先校验再执行，不能直接 `**args`。

## 六、长期记忆

> 来源：v1 原始构想 —— *"前期使用纯文本 + FTS + BM25，后期可以扩展 RAG"*；
> *"闲时进行记忆内容的整理，保持记忆内容一定时间更改次数内的审计记录。要求全局记忆的新增和修改不导致过分的膨胀。"*

### 6.1 分层

| 层 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 当前会话对话历史 | Redis（含 TTL） | 会话级 |
| 短期记忆 | 最近 N 天对话摘要、未闭环事项 | RDS + Redis | 天~周 |
| 长期记忆 | 偏好、称呼、协作对象、日常规律、重要事件 | **RDS + FTS/BM25** | 长期 |
| 语义记忆（演进） | 向量检索增强 | 向量库（可选） | 长期 |
| 审计记录 | 记忆的每次新增/修改 | 只追加表 | 永久 |

### 6.2 分类

| kind | 示例 | 写入时机 | 需确认 |
|---|---|---|---|
| `preference` | "喜欢喝淡茶""习惯早上 6 点起" | 闲聊中提取 | ❌（可事后查看/删除） |
| `contact` | "小林是女儿""弟弟叫陈叔" | 闲聊或用户明说 | ✅ 涉及协作对象 |
| `routine` | "每周三上午去菜市场" | 长期观察 | ❌ |
| `fact` | "膝盖做过手术" | 用户明说 | ✅ **属健康信息，谨慎** |
| `event` | "上个月孙女来看过" | 闲聊 | ❌ |

> 健康相关记录属于敏感范围。一期经授权最小保存药品身份、计划版本／来源、执行与人员反馈，不再宣称完全不存健康信息。
> 药品计划用专门结构化对象，通用记忆整理不能自动改写或启用。聊天、音频、来源图片、业务记录与审计有不同期限；摘要／索引／备份的删除边界见 T-66。

### 6.3 防膨胀机制

| 机制 | 做法 |
|---|---|
| 合并去重 | 相似记忆合并（同 subject + 同 predicate → 更新 value 而非新增） |
| 闲时整理 | 低峰期批量任务：合并、裁剪、摘要化 |
| 版本化 | 不覆盖，写新版本 + `valid_from` / `valid_to` |
| 审计上限 | 同一记忆项"一定时间内更改次数"超阈值 → 冻结并标记待确认 |
| 容量上限 | 每用户长期记忆条数上限 + LRU/置信度淘汰 |
| 置信度 | 每条记忆带 `confidence`，低置信度不参与推理，只做候选 |
| 过期 | `routine` / `event` 类带自然衰减期 |

### 6.4 FTS/BM25 → RAG 的演进路径

```
阶段 1（MVP）：RDS + 全文索引（FTS）+ BM25 排序
  零外部依赖、可解释、可调试、成本低；足够支撑几十~几百条记忆/用户
阶段 2（增强）：BM25 + 向量召回 → 混合排序
  触发条件：记忆条数增长导致 recall 明显下降时才做
阶段 3（可选）：按记忆类型分索引 + 重排序
```

> 写作规范：材料中应写成**有触发条件的技术演进路线**，而不是"后期会上 RAG"。

## 七、自适应交互策略（语音层执行，事务层提供内容）

### 7.1 个性化沟通策略

| 维度 | 策略 | 实现 |
|---|---|---|
| 语言复杂度 | 简单表达，避免复杂术语 | 提示词约束 + 输出简易度校验 |
| 信息长度 | 优先简短，必要时**分步说明** | 长度阈值；超长拆多轮 |
| 语音速度 | 允许用户调整播报速度 | 用户配置项 |
| 信息重复 | 支持自然语言请求重复说明 | 意图 `repeat` |
| 澄清方式 | 根据反馈选**开放式**或**选项式** | 见 §7.3 |
| 交流习惯 | 在用户允许范围内记住偏好称呼与沟通方式 | `MemoryRecord.kind=preference` |

### 7.2 共情与关怀性回应（**有明确红线**）

> 来源：外部评审意见 —— *"Agent 可以识别当前表达中的情绪线索，但**不应直接推断老人的心理状态**。"*

```
❌ 老人："今天又是一个人吃饭。"
   AI  ："您感到很孤独。"                    ← 断言了老人的情绪

✅ 老人："今天又是一个人吃饭。"
   AI  ："今天也是一个人吃饭呀。您想跟我聊聊今天的事吗？"
```

**规范**：输出中**禁止出现对用户心理状态的断言**。可描述**可观察的事实**，并**邀请**用户表达。

### 7.3 澄清方式选择

| 方式 | 何时用 | 示例 |
|---|---|---|
| 开放式 | 老人表达流畅、情绪开放 | "您想跟我说说是怎么回事吗？" |
| 选项式 | 老人表达困难、或已多轮未澄清 | "您是想让**女儿**帮忙，还是**儿子**帮忙？" |

**选择依据**：历史表达长度、澄清轮次、上一轮是否成功。

### 7.4 交互失败恢复

| 机制 | 说明 |
|---|---|
| **澄清轮次上限** | **3 轮**后改用选项式或转人工 |
| 随时可中断 | 用户任何时刻可打断、取消、要求重来 |
| 降级路径 | Agent 无法理解 → 提示老人用"我有件事想说"下的表单直接填 |
| 不静默失败 | 任何失败都有明确提示 |

## 八、多假设推理

> 来源：外部评审意见 —— *"Agent 应结合当前表达、长期记忆和历史上下文，识别可能存在的潜在需求，并生成**多个候选假设**。对于**证据不足**的需求，**不直接认定其真实性**。长期记忆可以辅助识别可能的协作对象，但**不能替代用户对具体行动的确认与授权**。"*

### 8.1 流程

```
输入表述 + 长期记忆 + 历史上下文
        │
        ▼
 生成 N 个候选假设，每个带：
   · hypothesis     假设内容
   · evidence       支撑证据（来自哪条记忆 / 哪句上下文）
   · confidence     置信度
   · cost_of_error  猜错的代价（低 / 中 / 高）
        │
        ▼
   confidence 高 且 cost_of_error 低  → 直接执行（仍需轻量确认）
   confidence 中 或 cost_of_error 高  → **提问澄清**
   confidence 低                      → 只做共情回应，不推断
```

### 8.2 示例

```
陈阿姨："最近有点想小林，想跟她说说话。"
  ├─ 假设1: 希望与"小林"通话  (contact{小林=女儿}, conf=0.85, cost=低)
  └─ 假设2: 只是想倾诉        (conf=0.3, cost=低)

AgeGuard："你希望我把想通话这件事告诉小林吗？"
陈阿姨："可以，告诉她我今晚有空。"
AgeGuard："我会创建一条联系事项。她是否已经查看或跟进，会在事项里显示。"

───────────────────────────────────────────

陈阿姨："家里米快没了，想请弟弟明天带一小袋来。"
  ├─ 假设1: 采购请求，对象="弟弟"→ 长期记忆解析为"陈叔" (conf=0.9)
  └─ 假设2: 对象未确定

AgeGuard："是请陈叔明天帮你买米吗？这次采购请求是否可以分享给他？"
```

### 8.3 证据不足时的行为

```
老人："最近家里挺冷清的。"
  ├─ 假设1: 想和家里人聊天 (conf=0.4, cost=中)
  ├─ 假设2: 家里真的冷（温度） (conf=0.2, cost=低)
  └─ 假设3: 抱怨孤独         (conf=0.4, cost=高 —— 猜错会冒犯)

→ conf 不足且存在 cost=高 的假设 → 用**开放式提问**，不下断言
AI："最近是不是比较想和家里人聊聊天？"      ← 提问式，不是断言式
```

**红线**：长期记忆可辅助识别协作对象，但**不能替代用户对具体行动的确认与授权**。

## 九、动态任务规划

> 来源：外部评审意见 —— *"Agent 能否根据时间事件和现实反馈，**动态调整后续协作策略**。例如若超过约定时间如何保持**待跟进**的状态？"*

### 9.1 四天生命周期

| 天 | 事件 | 系统行为 | 确定性 / LLM |
|:--:|---|---|---|
| D1 | 老人同意创建关怀事项 | 创建事项 | LLM 生成内容，**确定性**创建 |
| D2 | 女儿选择"周六下午联系妈妈" | 记录安排 | **确定性** |
| D3 | **约定时间已过，无反馈** | 在频率限制内询问女儿是否已完成 | 超时判定=**确定性**；话术=LLM |
| D4 | 老人："昨天和女儿聊了很久，挺开心的" | 识别可能是反馈 → **必要确认后**关联历史事项 | 匹配=LLM 建议，**关联=需确认** |

### 9.2 待跟进状态保持

| 情况 | 策略 |
|---|---|
| 约定时间已过，无反馈 | 状态 → `overdue`；按频率限制提醒 |
| 提醒后仍无响应 | 保持 `overdue`，**不升级、不轰炸**；到阈值提示老人"是否换个人帮忙" |
| 老人主动问"事情办了吗" | 查 `query_item_status` 如实回答，**不美化** |
| 亲属说"我忘了" | 允许重新安排时间 → 记录新约定 |
| 亲属说"我做不了" | 进入 `reassign` 流程（§十） |

### 9.3 频率限制规则（确定性业务控制）

旧 24h／3 次／22:00–08:00 不是本轮已确认参数，统一在 T-62 验证。普通关怀尊重频率和安静时段；用药提醒按已确认有效计划执行，不擅自改时刻。

未反馈规则默认关闭，老人明确授权接收人、触发、内容及频率后执行，可撤销且执行时复核。亲属关注不自行产生授权。无反馈不判断漏服、不反复催服，也不因紧急标记把普通推送冒充急救。

## 十、多主体任务协作

> 来源：外部评审意见 —— *"当任务执行条件发生变化时，Agent 可以结合**历史协作关系、当前反馈和任务要求**生成替代方案，并通过**多轮协商**推动任务调整。涉及**新增接收人、扩大信息共享范围或改变重要安排**时，**必须重新确认用户意愿并完成必要授权**。"*

| 能力 | v2 现状 | 本项目 |
|---|:--:|:--:|
| 亲属授权 / 通知 / 反馈 | ✅ | ✅ |
| **多轮协商** | ❌ | ✅ |
| **任务重新分配** | ❌ | ✅ |
| **异常处理决策** | ❌ | ✅ |
| **结果确认** | ❌ | ✅ |

### 重新分配流程

```
条件变化（亲属拒绝 / 超时 / 能力不匹配）
        │
        ▼
检索：历史协作关系 + 当前反馈 + 任务要求
        │
        ▼
生成 1~N 个候选方案（含理由）
        │
        ▼
**回到老人处重新确认**  ← 不可跳过
        │
        ├─ 老人确认 → 重新授权 → 通知新接收人
        └─ 老人取消 → 事项关闭
```

**硬规则**：任何"新增接收人""扩大共享范围""改变重要安排"都必须**重新走老人确认流程**。

### 协作结果的双维度评价

| 维度 | 取值 |
|---|---|
| **是否完成** | 已完成 / 部分完成 / 未完成 / 已失效 |
| **协作体验** | （老人可选反馈）满意 / 一般 / 不满意 |

用途：① 提高"事项闭环率"测量的真实性（避免"人来了但什么都没做"算成闭环）
② 为亲属匹配提供依据 ③ 为 `10` 的指标提供原始数据

## 十一、不确定性感知与证据可靠性

> 来源：外部评审意见（**尖锐且切中要害**）—— *"idea 中有区分'老人**自报**已服药'和'**客观确认**已服药'，但是应该**从哪里去获取事实依据**？以及老人自报已服药后**是否需要进一步推进**？"*

### 11.1 获取了什么、究竟证明什么

| 来源 | 当前定位 | 能证明／不能证明 |
|---|---|---|
| 老人自述 | 首版人员反馈 | 记录了该自述，不等于独立核验 |
| 亲属反馈 | 授权协作 | 标明记录者、观察或转述依据，不冒充专业确认 |
| 自制药盒节点 | 首版硬件目标 | 观察开合，不证明操作者、具体药物、吞服或医学正确性 |
| 商用穿戴／家居 | 条件性后续 | 主体、接口／设备、授权和时效分别验证 |
| AI 提取 | 待核对候选 | 保留来源，不产生新健康事实 |

限制在观测语义，而不是“硬件都不可做”。开合、自报和亲属说明并存，不静默互相覆盖。

### 11.2 来源类型，不是服药真实性阶梯

保留旧 E 标签以兼容文档，但不能相加或升级为统一可信分数：

| 标签 | 来源 | 展示规范 |
|---|---|---|
| E0 | 没有记录／不可用 | 无记录与设备离线分开，不推断未发生 |
| E1 | 老人自述 | “老人自报本次已服药”，标明时间和对象明确程度 |
| E2 | 亲属反馈 | “亲属反馈／转述”，注明依据，不笼统标“已确认” |
| E3 | 设备记录 | “药盒开启／设备测量”，附具体能力、时钟质量和同步时间 |
| E4 | 有来源的专业资料（如适用） | 明确机构、原文与时间，家属核对不冒充专业审核 |

AI 候选和模拟数据另行标识。E3 开盖不会比 E1 自报更接近吞服证明，两者也不构成客观服药核验。来源不自动产生亲属访问权限。

### 11.3 "自报后是否需要进一步推进" —— 决策树

```
老人自报已服药
     │
     ├─ 该事项是否由老人主动提出？（是 → 低干预）
     │     └→ 记录 E1，不追问，仅在下次闲聊自然提及
     │
     ├─ 是否存在未反馈记录？
     │     └→ 低打扰非质问式询问，阈值见 T-62
     │         无记录不等于未服药，不能生成漏服结论
     │
     ├─ 是否涉及高风险药物？
     │     └→ 一期**不做**医疗建议，仅记录并在亲属端标注
     │
     └─ 是否有老人明确开启、仍有效且覆盖该内容的共享／跟进规则？
           └→ 后端复核接收人和范围；默认关闭，不扩大范围
```

**三条红线：**
1. **不追问到让老人有压力**——干预强度随证据不足**递减**，不是递增
2. **不做医疗判断**——不推断药效、不建议改药
3. **不把低证据等级数据当高证据等级用**——尤其亲属端展示时

## 十二、失败恢复

| 失败类型 | 处理 | 需用户知晓 |
|---|---|:--:|
| LLM 超时 / 限流 | 重试（退避）→ 失败则降级为表单填写 | ✅ |

| 澄清轮次超限 | 改选项式 → 再超限降级为表单 | ✅ |
| 记忆检索失败 | 无记忆上下文继续，不阻塞 | ❌ |
| 云服务不可用 | 本地缓存草稿，恢复后同步 | ✅ |

## 十三、延迟预算（**目标值，非实测**）

| 阶段 | 目标 | 说明 |
|---|---|---|
| 老人说完 → 语音层出声 | **< 1 秒** | 全双工的核心体验线 |
| `request_task` → MaaS 返回 | 目标 < 2 秒 | 用 `openpangu-2.0-flash` + `thinking=disabled` |
| 完整事务闭环（含澄清） | 多轮，不作硬性要求 | 异步，老人感知不到等待 |

**关键洞察**：因为做了先应答后落实，**MaaS 的延迟不体现在老人感知里**。
→ **语音层延迟预算要卡死，事务层可以宽松。**
→ 事务层因此可以用更强的模型（`11` §三）。

## 十四、常见误区

| ❌ | ✅ |
|---|---|
| "全双工语音 = Agent 的一种形态" | 语音是**通道**，Agent 是**决策** |
| "用了 Qwen 就不需要 MaaS" | 失去赛题技术栈 + 代金券；长链推理与工具可靠性都更弱 |
| "用了 MaaS 就不需要 Qwen" | MaaS **无语音能力**；配 SIS 就失去全双工 |
| "让 Qwen 也调那 12 个工具" | ⚠️ 不行。两层都在判意图，违反铁律 |
| "事务层直接生成给老人听的话术" | ⚠️ 不行。语气会不一致 |
| "事务处理要同步等 MaaS 完成" | 不必要。先应答后落实 |
| "全双工就是可以随便打断" | 还有 `smart_turn` 语义轮次判定——语气词不算打断 |
