# 04 · 全双工语音与并行 Agent 架构

> 核心目标是手机自然交流与后台 Agent Loop 同时工作，不是语音盒串行录音，也不只提取家庭工单。本文为设计契约；具体模型与调用方式见 [11](11-语音与模型.md)，SDK 证据见 [08](08-外部依赖核查.md)。

## 一、职责分离，而不是体验割裂

| 层 | 职责 | 不应做什么 |
|---|---|---|
| 实时语音交互 | 持续收发音频、轮次、打断、改口、统一发声 | 直接绕过业务服务写记忆、创建任务或共享 |
| 并行 Agent | 结合上下文与授权记忆，检索、整理候选、规划允许动作 | 把所有闲聊任务化，无限循环，替用户决定共享 |
| 输出协调 | 合并后台结果与当前话题，处理取消、版本和发声顺序 | 重复回应，播报迟到旧结果，提前宣布成功 |
| 确定性业务服务 | 身份、授权、确认、schema、版本、幂等、持久化、调度 | 把模型输出或提示词当权限系统 |
| 个人记忆与共享投影 | 持久化用户信息，按接收人生成授权内容 | 用一份全局 prompt 给全家读取私人资料 |

这是逻辑职责，不强制两个不同模型。双模型是候选实现；单模型也必须满足独立业务控制、并行处理与可测可靠性。

## 二、事件驱动的并行主线

```text
手机音频 ↔ 会话／语音适配 ↔ 实时语音模型
                 │
       轮次、来源修订、打断、更正、取消事件
                 ▼
          持久化处理事件／去重
                 ▼
         Agent Loop（有界编排）
       ├ 授权上下文与个人记忆检索
       ├ 记忆候选、提醒候选、分享候选
       └ 受控工具调用
                 ▼
      业务网关：身份／授权／确认／版本／幂等
       ├ 私人记忆与修订
       ├ 提醒计划／单次执行／调度任务
       ├ 共享投影／真实留言／明确请求
       └ 事务内发送任务 → 调度与通知工作进程
                 │
           带来源、版本的结果
                 ▼
       输出协调 → 当前会话／后续界面反馈
```

原始音频是否落盘依保留策略；可靠处理可以保存获准转写和处理事件，不以永久录音为前提。事件名和队列产品尚未定案，不是已有代码。

定时触发、进程恢复和发送重试由确定性程序完成。Agent 可被对话、用户操作或允许的事件唤起，单次步数、超时、费用有上限；不需要无限推理或不停轮询才能称为 Agent Loop。

## 三、全双工与并行的正确性

### 3.1 不能只依靠语音模型愿不愿意调用工具

长闲聊中值得记住的信息，可能没有明确“帮我记住”的指令。若只有 `request_task` 被调用才触发后台，会漏掉习惯、生活近况和后续话题。

需要验证“已提交轮次／转写事件驱动后台整理”与“模型工具调用”的组合：工具可以加速明确动作，完整轮次处理应有可观测状态、去重和漏处理检测。具体通路在 T-77 定案，不以一个 FC 成功样例证明全部覆盖。

### 3.2 临时转写、更正与取消

- 临时转写只能准备候选，不据此对外发送或启用重要计划。
- 来源至少关联用户、会话、轮次、转写修订及处理标识；缺原文不能静默借用上一轮。
- 用户改口使旧候选失效；结果提交前检查当前版本，迟到结果不能覆盖新意愿。
- 打断播放、取消回应、取消草稿、撤销已建立计划是不同动作。说“等等”不自动删除全部任务。
- 处理重试不重复写记忆、创建计划或发送消息；处理状态不能只有 Redis TTL。
- 会话结束不静默丢弃已接受的后台工作；尚未落实的操作显示处理中／失败，不假称成功。

### 3.3 先回应，不先宣布业务完成

可以先说“我听到了，正在整理”。持久化成功后才能说“提醒已保存”，发送服务受理后只能说相应状态。

并行可减少阻塞，但后台延迟仍影响澄清与结果反馈，不能写“事务延迟用户感知不到”。分别测说话响应、处理完成与执行延迟。

## 四、受控工具与确认

| 工具能力 | 允许的作用 | 写入条件 |
|---|---|---|
| 记忆检索 | 查当前用户或请求者可见内容 | 读权限与使用目的校验 |
| 记忆候选／修订 | 提取习惯、偏好、事件、来源 | 保留策略、schema、版本；敏感／含糊事实待核对 |
| 提醒建议／计划变更 | 创建、修改、取消生活安排 | 本人明确确认或仍有效的预授权，关联动作与版本 |
| 授权投影 | 生成近况、原话、话题候选 | 生成上下文与结果输出双重权限检查 |
| 真实留言发送 | 提交用户本人确认的留言 | 认证发送者、内容版本、接收设置 |
| 明确求助 | 创建请求、接手、协商、反馈 | 具体对象、共享许可、合法业务状态 |
| 联网查询（可选） | 查询实时公共信息 | 出站最小化；不把私人原文随意发给第三方 |
| 传感情境（可选） | 使用具体来源的观测 | 设备绑定、用途、时效与能力限制 |

所有副作用经业务入口校验。语音确认可作为意愿输入，但后端必须根据认证会话、当前上下文和明确语义生成有效确认记录，不接受模型任意自填 `confirmed=true`。

模型参数是待验证输入；工具白名单、结构校验、资源权限、唯一约束与并发裁决不能由 prompt 替代。业务提交与发送任务用事务或等价可靠机制共同持久化。

## 五、个人长期记忆

### 5.1 隔离与分层

- 会话工作上下文可用缓存，但必要恢复点与唯一业务事实持久化。
- 个人长期记忆跨会话可用，按用户隔离，不把“全局”解释为全家共用。
- 通用记忆存背景、偏好、候选习惯、事件与关系上下文。
- 提醒计划、用药安排、共享授权与明确请求用专门对象，不能被摘要整理直接覆盖。
- 子女只检索授权投影；不是先把私人全量记忆给模型，再靠输出过滤碰运气。

### 5.2 一条记忆需要什么

来源、发生或表达时间、适用时间、记录者、候选／确认状态、修订关系与删除状态。模型置信度可以辅助排序，不是事实证明，也不是访问许可。

合并重复表达时保留来源与冲突，不用“相似”直接覆盖；一次不方便不永久推断偏好，一次完成不改写周期安排。

### 5.3 可靠存储与可遗忘

写入幂等、事务提交、备份恢复、来源追溯、跨次检索和删除是分别验证的能力。会话缓存、向量索引和模型上下文都不是唯一账本。

后台整理须尊重删除标记与保留策略；旧摘要、索引、共享投影和备份恢复不能复生已删除内容。审计也有最小化和期限，不永久保存全部敏感原文。

先用结构化记录与适用全文检索，FTS／排序能力按数据库引擎验证；向量或混合检索按召回效果引入。全文检索也可提供生成上下文，不能把“上向量库”当作唯一 RAG 路径。

## 六、提醒与调度

计划包含本人意愿、时区、生效／失效、重复规则和版本；单次实例单独记录。Agent 不负责持续看时间，调度程序按已确认计划创建／执行实例。

修改取消旧未来任务，重试不重复执行，迟到执行按过期策略处理；本次反馈不误改未来全部计划。创建、调度受理、发送受理、终端展示和本人反馈不是同一个完成状态。

用药提醒只使用有来源且核对有效的安排；不将普通习惯推理用于剂量或补服。未知时提示核对，不猜测。

## 七、家庭连接不是工单循环

共享内容分为近况／原话、交流线索／邀请、明确请求。只有最后一类需要接手与处理状态。真实留言是另一条双向通路，不能等同于工单评论。

授权在生成输入、读详情、派生摘要、原话播放、话题回顾和通知时复核。撤销后旧链接不可读，已在处理中生成的过期内容不能继续发送；删除与共享撤销影响的范围分别说明。

对方不回应，不编造回复，不自动扩大接收人，不生成孝心排名，也不把系统内已读当成真实交流。

## 八、失败与验收

| 失败 | 要求 |
|---|---|
| 语音断流／误打断 | 可停止、恢复或明确降级，不谎称核心仍正常 |
| Agent 超时／限流 | 有界重试、处理状态、稍后继续或取消；不要求老人反复重说全部内容 |
| 记忆检索失败 | 如实缺上下文，不编造记得；依赖该记忆的重要动作暂停核对 |
| 存储失败／提交后崩溃 | 不提前宣布完成；恢复任务与幂等验证 |
| 共享或提醒配置已变更 | 拒绝旧版本结果，按最新授权／计划处理 |
| 手机离线／通知无回执 | 记录未知、持久化内容、有限重试，不冒充必达 |

评测见 [10](10-评测方案.md)，关键验证 T-31／33／34／74／76～83 见 [12](12-风险与待验证.md)。核心验收不因可选硬件未接入而停止，也不能用文字流程替代真实全双工证据。
