## 二、NearLink Kit（星闪服务）

| 项目 | 结论 |
|---|---|
| 支持语言/平台 | **HarmonyOS（ArkTS / ArkUI）**；**无 Android / iOS / Web SDK** |
| 提供的能力 | 设备发现（扫描/广播）、连接管理、**SSAP** 数据传输、端口数据传输、属性读/写/通知 |
| **不提供** | 任何业务/语义能力（无位置、无行为识别、无健康数据）——它只是**一条链路** |
| 硬件要求 | 手机需**硬件支持**；官网明确"星闪与具体硬件支持能力有关，**无法通过系统升级支持**" |
| 约束 | 连续 `writeData` 会拥塞发送队列；官方建议**发送间隔 10ms** |

**定性**：星闪 = **自研硬件终端与手机之间的通信方式**，仅此而已。
不是赛题一独立技术必选项；是否有产品价值须另证。保留为条件性传输扩展，不阻塞首版 MQTT／HTTPS。

## 三、Health Service Kit（运动健康服务）

### 3.1 路径、语言与真实含义

- 穿戴／测量设备通常经运动健康 App 聚合后供获授权应用读取，不等于任意传感器直连。
- 当前 HarmonyOS 指南含 ArkTS、`@kit.HealthServiceKit`；Android Codelab 有 Java 示例但工具链较旧；另有云侧 REST 路径。
- 路径存在不等于当前账号获得审批／用户授权，也不意味着已核实 Python／Node.js 原生 SDK。

来源：[采样管理](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/health-samplepoint-manage)、[Android Codelab](https://developer.huawei.com/consumer/cn/codelab/HUAWEIHealth-DevEco/)、[REST 介绍](https://developer.huawei.com/consumer/en/doc/HMSCore-Guides/overview-restful-api-0000001050071695)。

### 3.2 本次所查 HarmonyOS 数据表

| 数据 | 开放等级 | 文档及时性 |
|---|---|---|
| 步数、热量、距离等日常活动 | 基础 | 小时级 |
| 动态心率、静息心率、HRV | 高阶 | 小时级 |
| 血氧、压力 | 高阶 | 小时级 |
| 血压 | 高阶 | 分钟级 |
| 睡眠分期与睡眠记录 | 高阶 | 分钟级 |

开放等级需要核对渲染页面的图标，文本抽取可能遗漏。该表不外推所有 Android／REST／历史版本；数据延迟也不构成实时监护承诺。血压记录不代表所有手表可测血压，来源须具体标明。

来源：[数据开放总览](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/health-data-overview)。

### 3.3 主体、审批与授权

所查资质页面要求个人开发者应用上架华为应用市场，高阶数据暂不向个人开发者开放；企业存在资金／年限要求，事业单位／政府机构相应条件不同但仍需审核。学生团队不自动等于学校申请主体。

所查申请页面标注测试权限人工审核约十个工作日、测试前百位用户等限制；落地以实际政策和审批为准。可读数据是服务审批与用户逐项授权的交集；蓝牙连接、App 状态和同步影响及时性。

来源：[申请资质](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/health-application-qualifications)、[申请服务](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/health-apply)、[用户授权](https://developer.huawei.com/consumer/cn/doc/hmscore-guides/add-permissions-0000001050069726)。

### 3.4 对本项目的决定

当前没有已验证通路，作为条件性后续能力；不作为药盒节点、提醒或首个硬件闭环的硬依赖。不要写“所有健康信息永远不可得”，也不承诺一行配置即可接入。

## 四、商用智能家居与自主节点

HarmonyOS Connect 官网说明其为面向消费硬件的开放生态，不能仅据此宣称第三方应用已经能读取任意门锁／灯具／人体传感器事件。

本项目尚未核实当前主体可用的通用授权事件 API；特定厂商合作、开放 API、网关和本地协议须逐项查证，不泛化为高校团队永久无路可走。商用适配不可用时如实降级。

**自制药盒节点走独立板卡、固件、设备凭据与 IoTDA，不依赖上述商用生态权限。** 固件和接入属于团队可实施且必须验证的工程任务。平台不提供事件语义不等于自主传感不可行。

来源：[HarmonyOS Connect](https://developer.huawei.com/consumer/cn/smarthome/)；板卡与协议见 §十二。

| 依据 | 内容 |

| 厂商 | 系统级通道 | 学生团队可用性 |

| OPPO / vivo / 魅族 | 各自通道 | ⚠️ 部分有上架要求 |

| 服务 | 已覆盖通道 |

### 6.4 两个硬门槛

1. **企业账户**：荣耀推送需荣耀开发者**企业**账户
2. **上架要求**：小米等厂商要求**上架应用市场**才能正常推送

→ **学生团队大概率拿不到**。这决定了长连接兜底不是可选项而是必需品（`06` §二）。

### 6.5 RN 新架构时间线（与官方推送插件相关）

| 版本 | 日期 | 关键变化 |
|---|---|---|
| 0.76 | 2024-10-23 | 新架构**默认启用** |
| **0.82** | 2025-10-08 | **第一个完全在新架构上运行的版本；旧架构配置被忽略（"仅限新架构"）** |
| 0.83 | — | **移除旧架构代码** |
| **0.84** | 2026-02-11 | 继续移除旧架构组件；**Node.js 最低要求 v22** |
| **0.88** | 2026-10-12 | 当前最新稳定版（本项目锁定级别） |

> ❗ **"使用新架构"在今天不是选项，而是唯一状态。** `newArchEnabled=false` 会被忽略。

**对官方推送插件的影响：**

- `@hmscore/react-native-hms-push`（v6.13.0-302，HMS Core 团队第一方，Apache-2.0）
  是**旧式 Native Module** → 在 0.82+ 上只能走 **Interop Layer**
- 官方文档：*"The Interop Layer makes it possible to use existing native modules written for the legacy architecture with the New Architecture"* → **理论上仍可用**
- **但**：事件（推送模块的核心）正是互操作层的薄弱点；已有 RN 0.86 Bridgeless 下 `RCTEventEmitter` 失效的踩坑记录
- 该仓库有**仍 open** 的 RN 版本构建 issue（#286 / #301），第三方评估 **"Modestly maintained"**

**定性：⚠️ 大概率需要自写 TurboModule**（设计见 `06` §五）。

## 七、端到端实时语音

| 供应商 | 模型 | 结论 |
|---|---|:--:|
| **阿里云百炼** | `qwen-audio-3.1-realtime-plus` | ✅ 实时双工、支持工具调用与联网搜索、上下文 262,144；有官方 `dashscope` Python SDK + 官方示例仓库 |
| **火山引擎** | 豆包实时语音 3.0（Seeduplex） | ✅ 全双工端到端，官方文档含 Python 示例 |
| **华为云** | MaaS / SIS | ❌ **无对等产品** |

### 关键约束

1. ❗ **联网搜索与工具调用互斥**（Qwen）：`enable_search` **不能与 Function Calling 同时启用**
   → 对策：把搜索包装成自建工具走 FC（`11` §四）
2. ❗ **成本**：Qwen 音频输出 **150 元/百万 token**；且**华为云代金券不能用于阿里云/火山引擎**
3. ⭐ **`smart_turn` 语义轮次判定**（"嗯""啊"不打断）**恰好命中老人口语场景**——真实的选型理由

### 华为云路线（客观限制）

| 产品 | 能力 | 端到端实时语音 |
|---|---|:--:|
| **MaaS** | 文本/多模态 LLM，支持流式、工具调用、深度思考 | ❌ |
| **SIS** | ASR + TTS 分离（实时语音识别支持连续模式+端点检测） | ❌ |
| ModelArts | 训推平台 | ❌ |

> 华为云的路线是 **SIS(ASR) + MaaS(LLM) + SIS(TTS) 三段拼接**，问题：
> ① 延迟叠加 ② 不支持全双工打断 ③ 无法实现语义轮次判定。
> 而本项目目标用户是**口语化、带语气词、停顿长的老人**，这三条恰好是体验的决定性因素。
>
> **这是正当的客观条件限制**：换更强的团队也拿不到——因为这个产品**不存在**。

## 八、AI Agent 搜索 API

> 用途：实现自建 `web_search` 工具，绕开 Qwen `enable_search` 与 Function Calling 互斥（`11` §四）。

### 8.1 博查（BochaAI）⭐ 选定

| 项 | 结论 |
|---|---|
| 公司 | 杭州博查搜索科技有限公司 |
| 定位 | *"给 AI 用的世界知识搜索引擎"*；**DeepSeek 官方联网搜索供应方**；阿里/腾讯/字节官方推荐的搜索 API |
| 客户规模 | 60,000+ 泛企业客户 |
| 内容源 | 全网近千亿网页 + 生态内容（短视频/新闻/百科/天气/医疗/火车票/酒店/餐厅/景点/企业/学术） |
| Base URL | `https://api.bochaai.com` |
| 鉴权 | `Authorization: Bearer {{API_KEY}}` |
| **免费额度** | **控制台可免费领取 1000 次调用资源包** |
| 三个 API | Web Search、AI Search、Semantic Reranker |

**Web Search** `POST /v1/web-search`：`query`(必需) / `freshness` / `summary`(bool, 默认 false) /
`include` / `exclude`（域名白/黑名单，≤100 个）/ `count`(1–50, 默认 10)。
返回网页标题、链接、摘要与正文、发布时间、网站名称。

**AI Search** `POST /v1/ai-search`：`query` / `freshness` / `include` / `count` /
**`answer`**(bool, 默认 true) / `stream`。
返回**多模态参考源 + 总结答案 + 追问问题**，以及**结构化模态卡**
（天气卡、百科卡、**医疗卡**、日历卡、股票卡）。

**错误码**：400（参数缺失）/ 401（Key 无效或**无接口调用权限**，`ai-search` 可能需白名单）/
403（余额不足）/ 429（频率超限）/ 500。排错保留 **`log_id`**。

> ⚠️ 具体单价未核实（第三方转售渠道见"0.01 PTC/次"，非官方口径）→ `12` T-48。

**官方周边**（可参考，不引入项目）：`Bocha-Labs/bocha-skills`（Apache-2.0，含 `bocha-web-search` SKILL.md）、
`Bocha-Labs/bocha-search-mcp`（MIT，Python MCP Server）。

### 8.2 Tavily（备选）

| 项 | 结论 |
|---|---|
| 定位 | 专为 AI Agent 打造的实时网络搜索 API |
| Python SDK | `tavily-python`（MIT，1.4k★），有同步/异步客户端 |
| 特点 | 返回经结构化提取与 chunk 分段的结果，可直接注入 RAG；有 LangChain 集成 |
| ⚠️ 风险 | **海外服务**，大陆访问的稳定性与合规性需评估 |

### 8.3 定性

> ✅ **可行**。博查是国内公司、专为 LLM 设计、有免费额度、覆盖天气/医疗等结构化模态卡，
> 与本项目"老人常问天气与生活小问题"的场景高度匹配。
> Tavily 作为技术备选，但因是海外服务，**不作为主选**。

## 九、华为云产品事实

| 产品 | 用途 | 关键约束 |
|---|---|---|
| **CodeArts 代码智能体（码道）** | AI 编码、项目级代码生成、单元测试、Skills 技能包、可接入 DeepSeek/GLM/本地模型 | 赛题一 M1 强制；有**沙箱模式会拦截 KooCLI**（`09` §五） |

## 十二、本轮硬件、通信与药品依据（2026-10-17）

### 12.1 板卡与固件候选：不是采购定案

| 候选 | 官方文档支持的能力／语言 | 不据此推断的能力 |
|---|---|---|
| ESP32-S3-Korvo-2（所读 V3.1） | 双麦、音频 ADC／Codec、功放输出及实体按键；ESP-IDF 主要为 C API，支持 C++ 应用开发 | 不能等同于完整语音服务、已适配 OpenHarmony 或已跑通 IoTDA；板版本和 ADF／IDF 配对待锁定 |

### 12.2 IoTDA 应用侧 Python SDK

官方文档提供 Python 3 应用侧 SDK：核心包 `huaweicloudsdkcore`、IoTDA 包 `huaweicloudsdkiotda`，示例创建客户端并查询设备列表；其他操作以实际应用侧 API、区域、权限与实例为准。

这支持 Python 后端集成，不意味着微控制器端运行该 SDK。设备凭据与云应用凭据是不同信任域，不能把 AK/SK 烧进节点。

来源：[应用侧 Python SDK](https://support.huaweicloud.com/sdkreference-iothub/iot_10_10003.html)。

### 12.3 消息／命令与执行语义

IoTDA MQTT 消息下发支持 QoS 0／1，不支持 QoS 2；相应下发路径可能缓存和重发。系统 Topic、自定义 Topic 及设备订阅的限制不同，须按实际选用接口验证，不能只说“MQTT 保证刚好一次”。

消息下发和命令下发也不能混为一种完成语义：平台受理、设备协议 ACK、命令业务响应、实际播放和人员确认不是同一件事。平台缓存期限不应代替业务 `expires_at`，断线后迟到命令仍需设备检查版本／过期及幂等。

来源：[命令下发说明](https://support.huaweicloud.com/usermanual-iothub/iot_01_0331.html)、[平台消息下发协议](https://support.huaweicloud.com/api-iothub/iot_06_v5_3017.html)、[消息状态通知](https://support.huaweicloud.com/api-iothub/iot_06_v5_01203.html)。核查材料同时覆盖官方消息缓存／QoS 使用说明；不把某路径默认数值写成全部实例的固定配额。

### 12.4 移动通知与 Webhook

JPush 有 Android／iOS 客户端文档及服务端 REST API；所查推送 API 平台列表不包含浏览器 Web Push。服务端 HTTP 可调不等于存在所选语言的官方原生 SDK；移动 SDK 也不等于纯网页可后台必达。

来源：[Android](https://docs.jiguang.cn/jpush/client/Android/android_guide)、[iOS](https://docs.jiguang.cn/jpush/client/iOS/ios_guide_new)、[服务端 REST](https://docs.jiguang.cn/jpush/server/push/rest_api_v3_push)。

Webhook 的可发送内容、回调交互、配额和权限按选定平台另验。当前设计只将其作为补充通用通知，不把某机器人接收请求成功当作用户已查看／接手。

### 12.5 药品标签、药袋与个体安排

市场监管总局公开的《药品说明书和标签管理规定》第十七／十八条列举内外标签内容，同时存在小包装或“详见说明书”等情形。因此不能承诺拍一张外盒就能完整、正确、自动得到个人用法及全部注意事项。

国家卫健委公开的《处方管理办法》第三十三条涉及药师调剂交付、药袋／标签与用药交代，适用背景是处方调剂，不是授予家属或 AgeGuard 开方权。厂商通用说明、专业交代、家属备注与应用提醒应分别记录来源。
