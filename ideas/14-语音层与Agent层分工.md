# 14 · 语音层与 Agent 层的分工

> 回答：**全双工语音聊天与 Agent 是什么关系、有什么区别，各自在什么场景生效。**
>
> 关联：`04`（Agent 设计）、`12`（语音模型选型）、`13`（MaaS）
> 核实日期：2026-10-14

---

## 一、一句话结论

> **它们不是同一个东西的两个版本，而是两层。**
>
> - **全双工语音层**解决 **"怎么听、怎么说、什么时候该说"** —— 交互问题
> - **Agent 层**解决 **"要做什么、怎么做、做完没有"** —— 任务问题
>
> 二者**分层协作**，通过 **Function Calling 工具桥**连接。
> **不是"选一个"，而是"每一层只做自己该做的事"。**

---

## 二、本质区别（七条）

| 维度 | 全双工语音层（Qwen Realtime） | Agent 层（华为云 MaaS） |
|---|---|---|
| **解决的问题** | **交互**：听力、表达、轮次、打断 | **任务**：意图、工具、状态、追踪 |
| **核心指标** | **延迟**、自然度、可打断性 | **准确率**、可靠性、可追踪性 |
| **输入/输出** | 音频 ↔ 音频（流式双向） | 文本 ↔ 结构化结果（+ 工具调用） |
| **是否有状态** | ❌ **基本无状态**（会话内上下文） | ✅ **强状态**（事项状态机、长期记忆、权限） |
| **出错的代价** | 说错一句话 → 老人再说一遍 | **错发/漏发一条事项给家人** → 破坏家庭信任 |
| **能被谁替换** | 换供应商只换**通道**（`12` §六 已做抽象） | 换供应商要**重新验证工具调用**（`13` §三） |
| **典型失败模式** | 打断、延迟、答非所问 | 工具调错、参数虚构、状态不一致 |

**关键差别在"出错的代价"**：
语音层出错是**体验问题**，Agent 层出错是**正确性问题**。
→ 这直接决定了 `04` §1 的核心原则：**Agent 层不能有副作用权限，副作用必须过确定性校验层。**

---

## 三、唯一的交叠点：**谁来理解意图？**

两层**都能**"理解老人在说什么"——这是唯一必须划清的地方，也是设计难点。

```
老人："家里米快没了，谁有空帮我带一袋？"
        │
        ├─ 语音层能理解：这是一句话 → 该我回话了
        └─ Agent 层能理解：这是采购请求，缺"对象"槽位
```

**如果不说清楚，就会出现三种坏情况：**

| 坏情况 | 后果 |
|---|---|
| 两层都判断意图 → 重复回应 | 老人听到两遍，或语音层先答了、Agent 又说一遍 |
| 语音层判断了却自己动手 | 绕过权限校验 → 违反 `04` §1 |
| Agent 层直接生成话术 | 语气不统一 → 违反 `04` §4 的自适应沟通策略 |

## 四、五种架构方案与各自适用场景

### 方案 A：语音模型全包（Qwen 同时做对话和工具调用）

```
老人 ↔ Qwen Realtime（对话 + 工具调用）
                    └─ 直接调 04 §二 的工具
```

| 项 | 评价 |
|---|---|
| 优点 | **延迟最低**（只有一个模型，链路最短） |
| 缺点 | ① **用不上 MaaS** → 失去赛题一技术栈 + 代金券 ② 端到端语音模型的工具调用**可靠性通常弱于文本 LLM**（待实测 T-31）③ 长链推理（多假设、记忆整理）不适合为低延迟优化的语音模型 |
| **适用场景** | **纯陪伴闲聊**（情感支持、天气、生活小问题）——不需要事务状态的部分 |

### 方案 B：语音降级为 ASR + TTS，Agent 全接管

```
Qwen(ASR) → 文本 → MaaS Agent → 文本 → TTS 合成
```

| 项 | 评价 |
|---|---|
| 优点 | Agent 完全可控，MaaS 全程参与 |
| 缺点 | ❌ **失去全双工**、延迟叠加、不能打断 —— **退化成华为云 SIS 三段拼接那套**（`12` §5.2 已论证不可取） |
| **适用场景** | **无**（仅在外部语音服务不可用时的降级路径） |

### 方案 C：路由式（先分类，再分派）

```
老人说的话 → 路由器判断 → ├─ 闲聊类 → Qwen 直接回
                          └─ 事务类 → Agent 处理
```

| 项 | 评价 |
|---|---|
| 优点 | 概念清晰 |
| 缺点 | ⚠️ **路由器本身要一次判断**，又是一层延迟；且判断错了体验很差 |
| **适用场景** | 若语音层不具备 Function Calling 能力时的替代方案 |

### 方案 D：Agent-as-a-Tool ⭐ **推荐**

```
Qwen Realtime（对话层）
    │  Function Calling
    └─→ request_task(raw_utterance) → 后端 → MaaS Agent（事务层）
                                            └─ 返回结构化结果
        ←──────────────────────────────────────┘
    Qwen 把结构化结果"翻译"成人话
```

**核心：把整个 Agent 能力封装成语音层的**一个**工具。**

| 项 | 评价 |
|---|---|
| 优点 | ① **全双工保持**（只在事务轮次才叠加延迟）② Agent 用 **MaaS** → 赛题技术栈 + 代金券 ③ 职责清晰，只有一条跨层通道 ④ 与 `09`/`11`/`12`/`13` 的端口—适配器思路一致 |
| 缺点 | 依赖 Qwen realtime 的 FC 可靠度（**待实测 T-31**） |
| **适用场景** | **全部场景**（这是我们的主架构） |

### 方案 E：快慢双脑（D 的强化版）

```
快脑 Qwen   —— 永远在线，即时回应，负责"不让老人等"
慢脑 MaaS   —— 异步处理，慢慢想，负责"把事情办对"
                二者通过事件总线通信，不互相阻塞
```

**这是 D 的落地方式**，具体机制见下节。

> ⚠️ 注意：**方案 D 和 E 不是二选一**。D 定义了"用什么通道连接"，E 定义了"怎么避免互相阻塞"。
> 推荐的做法是 **D 的连接方式 + E 的异步策略**。

## 五、✅ 推荐架构：Agent-as-a-Tool + **先应答、后落实**

### 5.1 两条铁律（跨层纪律）

> **铁律 1：事务层（MaaS）永远不直接对老人说话。**
> 它只返回**结构化结果**，由对话层翻译成人话。
> → 保证语气一致（`04` §4 的自适应沟通策略：语言复杂度、信息长度、澄清方式）

> **铁律 2：对话层（Qwen）永远不直接写数据。**
> 它只能通过工具调用请求，副作用经确定性校验层（`04` §1）。
> → 保证权限与状态一致性

### 5.2 为什么要"先应答、后落实"

全双工的价值是**不让老人等**。但如果每次都要等 MaaS 处理完再出声，就退化成轮次式了。

**解法：对话层先出声安抚，同时异步调工具。**

```
老人："家里米快没了，谁有空周末帮我带一袋？"
  │
  ├─ t0  流式 ASR（边说边转写，不需要等说完）
  ├─ t1  smart_turn 判定轮次结束
  ├─ t2  Qwen 立即出声（不等待！）同时发起工具调用
  │        出声："好，我帮您记一下～"
  │        调用：request_task(raw="家里米快没了，谁有空周末帮我带一袋？")
  │                  ↳ 异步，不阻塞说话
  ├─ t3  MaaS 处理：
  │        抽取 {action: 购买大米, time: 周末, target: 未指定}
  │        → 缺槽位 → 返回 {need_clarify: "target"}
  ├─ t4  Qwen 收到 → 澄清："您是想请哪位家人帮忙？"
  ├─ t5  老人："问问我儿子吧" → 再次 request_task(target=儿子)
  │        MaaS：生成事项草稿 → {draft_id, share_target: 小陈}
  │        Qwen："我准备告诉小陈：『家里米快没了，周末方便带一袋吗？』可以发送吗？"
  └─ t6  老人："可以" → Qwen 调 confirm_item(draft_id) → 事项创建
```

**注意 t2/t3 是并行的** —— 老人听到"好，我帮您记一下"的瞬间，MaaS 还没处理完。
这就是全双工的意义：**感知上零等待，业务上不偷懒。**

### 5.3 这套流程为什么天然契合 AgeGuard

因为 AgeGuard 的产品设计**本来就要"确认后发送"**（`03` §二）。
所以"先应答、后落实"不是权宜之计，而是**与产品闭环同构**的：

```
表达 → [先应答] → 确认 → [后落实] → 接手 → 处理 → 反馈 → 老人知晓
```

## 六、⭐ 场景分工表（**最实用的一张表**）

| # | 老人说的话 | 谁处理 | 走什么路径 | 为什么 |
|:--:|---|---|---|---|
| 1 | "今天天气怎么样？" | **Qwen 直接回** | 内置知识 或 `web_search` | 无事务状态，延迟敏感 |
| 2 | "今天又是一个人吃饭。" | **Qwen 直接回** | 纯共情（`04` §4.2 不得断言心理状态） | 情感场景，**不能等** |
| 3 | "最近家里挺冷清的。" | **Qwen 追问** + 可能 `request_task` | `04` §5 多假设推理 | 模糊需求，需澄清 |
| 4 | "家里米快没了，谁有空帮我带一袋？" | **Agent** | `request_task` → 抽取 → 缺槽位 → 澄清 | 事务 |
| 5 | "上次那件事办了吗？" | **Agent** | `request_task` → `query_item_status` | **需要真实数据，绝不能编** |
| 6 | "我昨天忘吃药了。" | **Agent** | `request_task` → 记记录（E1 证据级） | 事务 + `04` §8.3 的低干预原则 |
| 7 | 老人在 AI 说话中途插话 | **Qwen（纯语音层）** | 全双工打断 | **只有全双工能做** |
| 8 | 老人口齿不清、反复停顿 | **Qwen `smart_turn`** | 语音层处理 | "嗯""啊"不打断（`12` §2.3） |
| 9 | 亲属端收到事项通知 | **Agent 层（NotifyService）** | 推送（`11`） | **与语音无关** |
| 10 | 定时关怀提醒到点 | **确定性程序** 触发 + Qwen 播报 | `04` §1 分工 | 时间检查必须确定性 |
| 11 | 老人说"我想跟女儿说说话" | **Agent** | `request_task` → 创建联系事项 | 事务（`04` §5.2 示例） |
| 12 | 问"这道菜怎么做" | **Qwen 直接回** | 可用 `web_search` | 生活小问题（v1 idea.md 明确要求） |

**归纳成一句规则：**

> **凡是需要"改变系统状态"或"读取系统真实数据"的 → Agent 层。**
> **凡是只需要"说、听、安抚、解答"的 → 语音层。**
> **凡是"必须准点发生"的 → 确定性程序。**

## 七、延迟预算（**关键指标，待实测**）

全双工的成败在于延迟。下表是**目标值，不是实测值**（T-32）：

| 阶段 | 目标 | 说明 |
|---|---|---|
| 老人说完 → 语音层出声 | **< 1 秒** | 这是全双工的核心体验线 |
| `request_task` → MaaS 返回 | 目标 < 2 秒 | 用 `openpangu-2.0-flash` + `thinking=disabled`（`13` §3.2） |
| 完整事务闭环（含澄清） | 多轮，不作硬性要求 | 因为是异步的，老人感知不到等待 |

**关键洞察**：因为做了"先应答、后落实"，
**MaaS 的延迟不会体现在老人感知里** —— 它只影响"AI 什么时候说出下一步"。
→ **所以语音层的延迟预算要卡死，Agent 层的延迟预算可以宽松。**

这是一个非常重要的设计自由：**Agent 可以用更强的模型（更慢但更准），因为它不阻塞对话。**

## 八、常见误区

| ❌ 误区 | ✅ 实际 |
|---|---|
| "全双工语音 = Agent 的一种形态" | 不是。语音是**通道**，Agent 是**决策**。语音模型也能做一点决策，但那是交叠，不是等价 |
| "用了 Qwen Realtime 就不需要 MaaS 了" | 失去赛题一技术栈 + 代金券；且长链推理与工具可靠性都更弱 |
| "用了 MaaS 就不需要 Qwen 了" | MaaS **无语音能力**；配 SIS 就失去全双工（`12` §5.2） |
| "让 Qwen 也调 `create_item_draft` 等 12 个工具" | ⚠️ **不行**。那会让两层都在判意图 → 违反铁律 1/2。**Qwen 只调 `request_task` 一个工具** |
| "Agent 直接生成给老人听的话术" | ⚠️ **不行**。语气会不一致。Agent 只返回结构化结果，话术由语音层出 |
| "事务处理要同步等 MaaS 完成" | 不必要。**先应答后落实**，老人感知不到等待 |
| "全双工就是可以随便打断" | 还有 `smart_turn` 的语义轮次判定 —— 语气词不算打断（`12` §2.3） |

## 九、语音层可调用的工具集（**只有一个**）

```
Qwen Realtime 的 tools:
├── request_task(raw_utterance: str) → TaskResult     ← ★ 唯一的主工具
│      ├─ {"type": "need_clarify", "slot": "target", "question": "..."}
│      ├─ {"type": "draft_ready", "draft_id": "...", "summary": "...", "share_target": "..."}
│      ├─ {"type": "query_result", "status": "...", "detail": "..."}
│      └─ {"type": "error", "reason": "..."}
├── web_search(query: str) → {answer, sources[]}      ← 12 §四 的自建工具
└── end_conversation(reason: str)                     ← 温柔收尾（D-23 的 5 分钟上限）
```

**为什么 `request_task` 只有一个入口？**
因为工具越少，模型越不会调错。**把复杂度关在事务层的内部**，跨层接口保持极窄——
这与 `11` §4.1 "Kotlin 只暴露窄接口" 是同一条设计原则。

### 边界情况处理

| 情况 | 处理 |
|---|---|
| Qwen 没调 `request_task`（漏判） | 后端**旁路检测**：若一轮对话里出现可提取的事项特征但没有工具调用 → 日志告警；二期做规则兜底 |
| Qwen 调了但参数为空 | `request_task` 接受空 `raw_utterance` 时用**上一轮原文**，不报错 |
| MaaS 超时 | `request_task` 返回 `{"type":"error"}` → Qwen 说"我这边有点慢，您再说一次好吗？"（不静默失败） |
| 老人中途改主意 | 语音层再次 `request_task`，Agent 用 `cancel_item` / 更新草稿 |
