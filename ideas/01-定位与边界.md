# 01 · 定位与边界

---

## 一、一句话定位

> **AgeGuard 把老人一句含糊的话，变成一件有人负责、有状态、有反馈的家庭事项。**
>
> 不替代微信，不以 AI 陪聊为核心。

答辩英文句：*AgeGuard turns an elder's spoken need into a tracked, owned, and closed-loop family task.*

---

## 二、问题定义

### 2.1 要解决的那一个问题

家庭关怀的失败**不在于缺少沟通工具**：

| 现象 | 真实缺口 |
|---|---|
| 老人发消息，子女在忙，回头忘了 | 需求**没有归属人** |
| 老人不好意思反复提，就把事放下了 | 需求**没有跟进状态** |
| 子女做了但没说，老人不知道，又不好意思问 | 结果**没有回传** |
| 老人表达含糊（"最近家里挺冷清的"） | 需求**没被翻译成可执行动作** |

**核心命题**：把"关怀"从一次性消息传递，变成有状态、有归属、有反馈的协作流程。

### 2.2 为什么现有工具不够

| 现有方案 | 擅长 | 缺口 | AgeGuard 的补充 |
|---|---|---|---|
| 微信 / 电话 | 聊天、通话、消息 | 事项散落在聊天记录；跟进靠人记 | 把确认后的需求整理成**结构化事项卡片** |
| 待办清单 | 提醒某人做某事 | 非为"老人—亲属"协作设计 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、生成 | 停留在对话 | 通过**受控工具调用**推动流程 |
| 健康监测设备 | 采集生理指标 | 数据 ≠ 行动 | （本项目不做这条） |

## 三、不做什么（三类，**必须区分**）

> 判定法：**换一支更强的团队能不能做到？** 能 → 系统缺陷；不能 → 客观条件限制。

### A 类 · 客观条件限制（**换谁做不到**）

| 事项 | 依据 | 替代路径 |
|---|---|---|
| 智能家居数据接入（灯 / 人体传感器 / 门锁） | `08` §四：HarmonyOS Connect 面向硬件厂商，无第三方数据 API | 老人自述 + 亲属反馈；架构留 `EnvironmentSource` 占位 |
| 实时健康监护（心率 / 血压实时核验） | `08` §三：数据时延**小时级**；高阶数据不对个人开发者开放 | 老人自报 + **证据分级标注**（`04` §十一） |
| 读取微信聊天记录 / 自动发微信消息 | 无公开接口，违反平台条款 | 系统内通知 |
| 华为云的端到端实时语音 | `11` §二：MaaS 是文本 LLM，SIS 是 ASR/TTS 分段 | 语音通道用第三方（并在材料中主动说明） |
| 医疗人员端的三方接入 | 依赖上述受限数据 + 敏感个人信息合规 | 亲属端标注"仅供家属参考"，不做医疗建议 |

### B 类 · 战略取舍（**做得到但不划算**）

| 事项 | 理由 | 二期？ |
|---|---|:--:|
| 自建视频通话 / 完整社交平台 | 与核心闭环无关，成本极高 | ❌ |
| 实体硬件终端（含星闪模组） | 核心软件价值未验证前投硬件 | ✅ |
| 跌倒检测 | 需专用传感器 + 实时性，误报代价高 | ✅ |
| 医疗人员端进一期 | 三方协作使复杂度翻倍，8 个月无法验证 | ✅ 远期 |
| 轻度认知困难老人 | 涉医疗辅助定位、伦理审查、监护人授权，超出 3 人团队 | ✅ 远期 |
| 健康事实的长期记忆留存 | 敏感个人信息合规成本（`04` §六） | ⚠️ 待定 |
| 方言支持 | ASR 方言覆盖需逐项核实 | ✅ 可能 |

### C 类 · 系统缺陷（**我们的活，未完成**）

| 事项 | 状态 |
|---|---|
| 商业计划书所需的市场测算、财务预测 | ⏳ 未写（见 §六） |
| 三入口线框图 / 交互稿 | ⏳ 未产出 |
| 预算表、里程碑甘特图 | ⏳ 未产出 |
| Agent 评测集 | ⏳ 未构建（`10` §4.2） |

> ⚠️ **红线**：把 C 类伪装成 A 类（"不是我们不行，是环境限制"）＝撒谎；
> 把 A 类写进"后续规划"＝画饼。两者同样致命。

## 五、核心竞争力

> **主张要确定，证据要标注状态。** 不说"这可能有用"，而说"我们主张 X，当前证据等级 B（n=8）"。

| # | 竞争力 | 主张 | 证据状态 |
|:--:|---|---|---|
| C1 | **从聊天沟通转向家庭事项闭环** | 把需求转成可跟进、可接手、可反馈的事项，是与微信的根本差异 | ⚠️ 待用户测试（`10` E-03） |
| C2 | **面向老人设计的低门槛交互** | 首页仅 3 个明确动作；大字、大按钮、可撤销的确认流程 | ⚠️ 待可用性测试（E-01/E-02） |
| C3 | **Agent 不只回答，还能在权限范围内调用工具** | 有"输入 → 工具调用 → 执行结果 → 错误处理"的真实工作流 | ✅ 系统日志可证 |
| C4 | **授权与可追踪性** | 老人可确认分享对象、取消草稿、撤销访问；亲属只见被授权事项 | ✅ 权限测试可证（E-05） |
| C5 | **不要求家庭迁移通信习惯** | 不依赖微信私有接口；外部连接待接口与授权核实后再评估 | ✅ 架构图可证 |

**竞争定位矩阵：**

| 方案 | 擅长 | 缺口 | AgeGuard 的补充 |
|---|---|---|---|
| 微信等通信工具 | 聊天、通话、消息 | 事项易分散，跟进依赖用户 | 将授权需求变成**可追踪事项** |
| 普通待办工具 | 提醒某人做某事 | 未针对老人—亲属协作 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、生成 | 可能停留在对话 | 通过**受控工具**推动流程 |
| 健康监测设备 | 采集生理指标 | 数据 ≠ 行动 | （不做这条） |
| **AgeGuard** | **家庭关怀协作闭环** | 价值需原型验证 | 低门槛交互 + 授权 + 状态可见 |

## 六、商业模式（创业训练必备，**待补**）

大创创业训练需要回答三问：

| 问题 | 当前状态 |
|---|---|
| **谁付钱？**（老人 / 子女 / 社区 / 养老机构 / 保险） | ⏳ 待定义 |
| **规模多大？**（目标市场测算、可触达用户数） | ⏳ 待测算 |
| **凭什么赢？**（竞品分析与差异化） | 部分见 §五 |

**已有的一个具体设计**：**freemium**——
免费版单次语音通话 5 分钟上限（成本约束），**付费版放开时长**。
该设计已在架构上留出扩展位（`04` §九 的 `end_conversation` 工具，上限值后端可配）。
