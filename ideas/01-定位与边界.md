# 01 · 定位与边界

> 当前基线见 `13`：语音盒＋药盒开合节点进入一期，完整后端保留；已决策不等于已交付。

---

## 一、一句话定位

> **AgeGuard 把老人一句含糊的话，变成一件有人负责、有状态、有反馈的家庭事项。**
>
> 不替代微信，不以 AI 陪聊为核心。

答辩英文句：*AgeGuard turns an elder's spoken need into a tracked, owned, and closed-loop family task.*

---

## 二、问题定义

### 2.1 要解决的那一个问题

家庭关怀的失败**不在于缺少沟通工具**：

| 现象 | 真实缺口 |
|---|---|
| 老人发消息，子女在忙，回头忘了 | 需求**没有归属人** |
| 老人不好意思反复提，就把事放下了 | 需求**没有跟进状态** |
| 子女做了但没说，老人不知道，又不好意思问 | 结果**没有回传** |
| 老人表达含糊（"最近家里挺冷清的"） | 需求**没被翻译成可执行动作** |

**核心命题**：把"关怀"从一次性消息传递，变成有状态、有归属、有反馈的协作流程。

### 2.2 为什么现有工具不够

| 现有方案 | 擅长 | 缺口 | AgeGuard 的补充 |
|---|---|---|---|
| 微信 / 电话 | 聊天、通话、消息 | 事项散落在聊天记录；跟进靠人记 | 把确认后的需求整理成**结构化事项卡片** |
| 待办清单 | 提醒某人做某事 | 非为"老人—亲属"协作设计 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、生成 | 停留在对话 | 通过**受控工具调用**推动流程 |
| 健康监测设备 | 采集生理指标 | 数据 ≠ 行动 | （本项目不做这条） |

## 三、不做什么（三类，**必须区分**）

> 判定法：先说明主体、授权、具体设备、版本与时效。条件受限不等于所有主体永久不可行；主动不做是取舍；已承诺功能的缺陷是系统责任。

### A 类 · 当前客观条件／观测限制

| 事项 | 依据 | 替代路径 |
|---|---|---|
| 第三方商用家居数据 | `08` §四：未核实当前主体可用的通用授权通路，不泛化为所有厂商永不开放 | 自制药盒节点不依赖该通路；原商用适配保持不可用 |
| 穿戴数据用于实时监护 | 时效、指标、账号和授权依路径不同；文档不保证可靠实时性，见 `08`／`idea.md` §7.2 | 不作为首版硬依赖，标明来源、时间与缺失 |
| 通过药盒开合证明吞服 | 传感器只观察容器状态，不知道操作者及具体药物 | 保留开合事件与人员反馈，不写成服药核验 |
| 读取微信聊天记录 / 自动发微信消息 | 无公开接口，违反平台条款 | 系统内通知 |
| 已核查服务中的端到端实时语音 | `11` 所核查 MaaS／SIS 路径不等同于全双工产品，不作全云产品永久不存在的断言 | 首里程碑用按键录音／播放；适用服务实测后选择 |

### B 类 · 战略取舍（**做得到但不划算**）

| 事项 | 理由 | 二期？ |
|---|---|:--:|
| 自建视频通话 / 完整社交平台 | 与核心闭环无关，成本极高 | ❌ |
| 首版之外的传感器与星闪 | 先完成语音盒＋药盒节点，不同时铺开毫米波、温湿度、墨水屏 | ✅ 按价值验证 |
| 跌倒检测 | 需专用传感器 + 实时性，误报代价高 | ✅ |
| 医疗人员端进一期 | 三方协作使复杂度翻倍，8 个月无法验证 | ✅ 远期 |
| 轻度认知困难老人 | 涉医疗辅助定位、伦理审查、监护人授权，超出 3 人团队 | ✅ 远期 |
| 无边界留存健康聊天／医疗分析 | 只经授权保存必要药品、计划、来源及反馈；不能再宣称完全不存健康信息 | 不默认扩张 |
| 方言支持 | ASR 方言覆盖需逐项核实 | ✅ 可能 |

### C 类 · 系统缺陷（**我们的活，未完成**）

| 事项 | 状态 |
|---|---|
| 商业计划书所需的市场测算、财务预测 | ⏳ 未写（见 §六） |
| 盒子／家庭应用交互稿与硬件样机 | 未提供完成证据，见 T-54～T-58 |
| 预算、模块负责人、里程碑 | 需按硬件新路线重排，T-69 |
| 设备异常、药品版本与 Agent 评测集 | 未提供构建／通过证据，见 `10`／T-68 |
| 越权、重复副作用、过期播报、数据／通知丢失 | 必须通过实现与测试解决，不能归咎于外部数据受限 |

> 红线：不能把已承诺功能的缺陷伪装成外部限制，也不能把当前账号限制外推为永久不可能。条件性扩展须写出实际主体、许可、资源和验证前提，不能代平台承诺未来开放。

## 四、产品四层

| 层 | 职责 |
|---|---|
| 老人交互 | 自制无触摸屏语音盒，按键说话／确认／取消、播报和进度反馈 |
| 真实事件 | 自制药盒开合节点，事件／时间／来源可追溯，不观察吞服 |
| 家庭应用 | Web／移动接收端，授权事项、协作反馈、药品提醒、家庭设备；Webhook 仅补充 |
| 完整后端＋AI | 人与设备身份、授权、持久化、状态机、调度、审计；AI 理解和提议，不自行授权 |

状态与权限见 `03`，跨端协议与药品规则见 `13`。

## 五、核心竞争力

> **主张要确定，证据要标注状态。** 不说"这可能有用"，而说"我们主张 X，当前证据等级 B（n=8）"。

| # | 竞争力 | 主张 | 证据状态 |
|:--:|---|---|---|
| C1 | **从聊天沟通转向家庭事项闭环** | 把需求转成可跟进、可接手、可反馈的事项，是与微信的根本差异 | ⚠️ 待用户测试（`10` E-03） |
| C2 | **面向老人设计的低门槛交互** | 实体控件、按键语音、明确确认与撤销；主张减少手机操作负担 | 待盒子／手机对照，不预设成功 |
| C3 | **Agent 不只回答，还能受控协作** | 输入 → 待校验提议 → 业务执行 → 结果／错误反馈 | 待实现和真实日志，不以架构图代替 |
| C4 | **授权与可追踪性** | 老人决定分享；人的权限与设备身份分离 | 待权限与撤销测试（E-05／H-02） |
| C5 | **不要求家庭迁移通信习惯** | 不依赖微信私有接口，继续用现有电话等实际沟通 | 架构主张；用户价值仍待测试 |

**竞争定位矩阵：**

| 方案 | 擅长 | 缺口 | AgeGuard 的补充 |
|---|---|---|---|
| 微信等通信工具 | 聊天、通话、消息 | 事项易分散，跟进依赖用户 | 将授权需求变成**可追踪事项** |
| 普通待办工具 | 提醒某人做某事 | 未针对老人—亲属协作 | 把**表达、接手、反馈**连起来 |
| AI 聊天机器人 | 问答、建议、生成 | 可能停留在对话 | 通过**受控工具**推动流程 |
| 健康监测设备 | 采集生理指标 | 数据 ≠ 行动 | （不做这条） |
| **AgeGuard** | **家庭关怀协作闭环** | 价值需原型验证 | 低门槛交互 + 授权 + 状态可见 |

## 六、商业模式（创业训练必备，**待补**）

大创创业训练需要回答三问：

| 问题 | 当前状态 |
|---|---|
| **谁付钱？**（老人 / 子女 / 社区 / 养老机构 / 保险） | ⏳ 待定义 |
| **规模多大？**（目标市场测算、可触达用户数） | ⏳ 待测算 |
| **凭什么赢？**（竞品分析与差异化） | 部分见 §五 |

**既有商业候选**：免费／付费服务可讨论，但旧稿“五分钟通话上限、付费放开”不是当前按键盒子的已确认定价或验收参数。需结合 BOM、云与语音费用、家庭需求和支付意愿验证，不以架构扩展位证明商业模式成立。
