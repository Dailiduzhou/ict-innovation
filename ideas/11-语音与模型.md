## 二、华为云没有对等的端到端实时语音（客观限制）

| 华为云产品 | 能力 | 端到端实时语音 |
|---|---|:--:|
| **MaaS** | 文本/多模态 LLM，支持流式、工具调用、深度思考开关、上下文缓存 | ❌ |
| **SIS** | ASR + TTS **分离**（实时语音识别支持连续模式 + 端点检测） | ❌ |
| ModelArts | 训推平台 | ❌ |

华为云的路线是 **SIS(ASR) + MaaS(LLM) + SIS(TTS) 三段拼接**，三个问题：

1. **延迟叠加**（ASR → LLM → TTS，链路长）
2. **不支持真正的全双工**（无法在模型说话时被打断）
3. **不支持语义轮次判定**（`smart_turn` 这类能力无从实现）

而本项目目标用户是**口语化、带语气词、停顿长的老人**，全双工与语义轮次判定**恰好是体验的决定性因素**。

> **这是正当的客观条件限制**：换更强的团队也拿不到——因为这个产品**不存在**。
> → 实时语音通道采用第三方；**华为云承担平台与事务层职责**（§五 双模型分工）。
> → 在材料中按 `07` §7.1 的分层写法如实陈述，并给出替代路径。

## 三、语音模型选型

### 3.1 Qwen `qwen-audio-3.1-realtime-plus`

| 项 | 内容 |
|---|---|
| 定位 | **实时双工语音对话模型**，支持文本和音频输入输出、**工具调用**、**联网搜索**、声音复刻 |
| 默认音色 | `longanqian_v3.1` |
| 上下文 | 262,144 tokens；最大输入 245,760；最大输出 16,384 |
| 接入协议 | **WebSocket**、**AOQ**、**WebRTC** |
| 地域 | 华北2（北京）、新加坡 |

**价格（华北2 北京，每百万 Token）：**

| 文本输入 | 音频输入 | 文本输出 | **音频输出** |
|---:|---:|---:|---:|
| 5 元 | 40 元 | 40 元 | **150 元** |

> ⚠️ **音频输出 150 元/百万 token 是本项目最大的单项成本风险。** 对策见 §七。

**三种交互模式（对老人场景价值极高）：**

| 模式 | 说明 | 意义 |
|---|---|---|
| `server_vad` | 声学 VAD，服务端自动判断起止 | 基础可用 |
| **`smart_turn`** | **"融合声学感知与语义理解判断轮次边界，无意义附和声（如"嗯""啊"）不会打断对话"** | ⭐⭐⭐ **老人场景的关键能力** |
| `push-to-talk` | 手动控制 | 老人端"按住说话"备选 |

> ⭐ **`smart_turn` 直接解决一个真实痛点**：老人说话常带语气词、停顿长、自我重复。
> 传统 VAD 会被"嗯""啊"打断，体验很差。
> **这一条应写进申报书的技术方案**——它证明我们不是随便选了个模型，而是**按场景特征选的**。

**Python SDK：**

| 项 | 内容 |
|---|---|
| 官方 SDK | **`dashscope`**（PyPI） |
| 版本要求 | 实时多模态 ≥ 1.26.5；实时语音合成 ≥ 1.25.11 |
| 官方示例仓库 | [`aliyun/alibabacloud-bailian-speech-demo`](https://github.com/aliyun/alibabacloud-bailian-speech-demo) |
| SDK 结构 | `fun_realtime/` 负责 WebSocket 连接、事件序列化、会话配置、音频编解码；**有意保持精简**（无轮次状态机、无内置路由器） |

> ✅ **`fun_realtime` "有意保持精简"很适合我们**——不预设架构，正好套进 `04` 的 ReAct 循环
> 和 `07` 的端口设计，不会打架。

## 四、自建联网搜索（`web_search` 工具）

### 4.1 为什么要自建

Qwen 官方原文：**"联网搜索通过 `enable_search` 开启，不能与 Function Calling 同时启用。"**

而 AgeGuard 的 Agent 全靠 Function Calling（`04` §五 的工具集）。**必须绕开。**
→ 把搜索包装成**自己的一个工具**，全程只用 FC。

### 4.2 方案对比

| 方案 | 结论 |
|---|---|
| **博查（BochaAI）** ⭐ | ✅ **选定**。国内公司、专为 LLM 设计、**免费 1000 次**、有语义排序与结构化模态卡 |
| Tavily | 备选。Python SDK 成熟（`tavily-python`，MIT，1.4k★），但是**海外服务**，大陆访问稳定性与合规性需评估 |
| 自建爬虫 + 索引 | ❌ 与项目无关的工程量，且法律风险高 |
| 直接用模型内置知识 | ❌ 知识截止，天气/新闻类必然答错 |
| 用 `enable_search` | ❌ 与 FC 互斥，事务层会废 |

### 4.3 博查 API 事实

**平台定位**：*"给 AI 用的世界知识搜索引擎"* —— **DeepSeek 官方联网搜索供应方**，
阿里/腾讯/字节官方推荐的搜索 API，服务 60,000+ 泛企业客户。

| 项 | 内容 |
|---|---|
| Base URL | `https://api.bochaai.com` |
| 鉴权 | `Authorization: Bearer {{API_KEY}}` |
| 内容源 | 全网近千亿网页 + 生态内容（短视频/新闻/百科/天气/医疗/火车票/酒店/餐厅/景点/企业/学术） |
| **免费额度** | **控制台可免费领取 1000 次调用资源包** |
| 三个 API | **Web Search**、**AI Search**、**Semantic Reranker** |

**Web Search** — `POST /v1/web-search`

| 参数 | 说明 |
|---|---|
| `query` | 必需 |
| `freshness` | `noLimit`(默认) / `oneDay` / `oneWeek` / `oneMonth` / `oneYear` / `YYYY-MM-DD..YYYY-MM-DD` / `YYYY-MM-DD`。官方推荐用 `noLimit`（算法会自动做时间改写） |
| `summary` | bool，是否显示文本摘要。默认 `false` |
| `include` | 限定网站范围（根域名/子域名，`\|` 或 `,` 分隔，≤100 个） |
| `exclude` | 排除网站范围（同上） |
| `count` | 1–50，默认 10 |

返回：网页标题、链接、摘要与正文、发布时间、网站名称。

**AI Search** — `POST /v1/ai-search`

| 参数 | 说明 |
|---|---|
| `query` | 必需 |
| `freshness` / `include` / `count` | 同上 |
| **`answer`** | bool，**默认 `true`** → 返回**总结答案 + 追问问题** |
| `stream` | bool，默认 `false` |

返回：**多模态参考源 + 总结答案 + 追问问题**，以及**结构化模态卡**
（天气卡、百科卡、**医疗卡**、日历卡、股票卡）。

**错误码**：400（参数缺失）/ 401（Key 无效或**无接口调用权限**）/ 403（余额不足）/
429（频率超限）/ 500（服务端异常）。排错时保留响应里的 **`log_id`**。

> ⚠️ `ai-search` 可能需要**单独开通白名单权限**（返回 401 + "无接口调用权限" 即未开通）。

### 4.4 选型：主用 `ai-search`

| 理由 | 说明 |
|---|---|
| **一次调用拿到总结答案** | `answer: true` 直接返回总结 → **省掉我们自己的一次摘要 LLM 调用**（省 token、省钱、省延迟） |
| **有结构化模态卡** | 天气卡 / 百科卡 / **医疗卡** / 日历卡 —— 恰好命中 v1 原始构想里的"天气信息，提醒增减衣物""解答生活小问题" |
| **返回参考源** | 可标注来源 → 与 `04` §十一 的证据意识一致 |
| **省 token** | 相比把 top-10 原始 SERP 塞给 Qwen，结构化的总结答案短得多 |

`web-search` 作为补充：需要原始多来源时使用。

### 4.5 工具定义（给 Qwen 与 MaaS 的 JSON Schema）

> 也是"确定性程序参与决策"的体现（`04` §1.4）。

### 4.6 实现骨架（Python）

```python
# app/tools/web_search.py
import os, hashlib, json
from dataclasses import dataclass, asdict
import httpx

BOCHA_URL   = "https://api.bochaai.com/v1/ai-search"
BOCHA_KEY   = os.environ["BOCHA_API_KEY"]          # 只从环境变量读
CACHE_TTL   = {"weather": 1800, "news": 3600, "encyclopedia": 604800,
               "life": 86400, "health": 86400}

@dataclass
class SearchResult:
    answer: str | None            # 博查的总结答案
    cards: dict                   # 结构化模态卡（天气/百科/医疗/日历）
    sources: list[dict]           # [{title, url, site, published}]
    log_id: str | None            # 排错用
    cached: bool = False

async def web_search(query: str, category: str = "life",
                     freshness: str = "noLimit", redis=None) -> SearchResult:
    # ---- 1) 缓存 ----
    key = f"ws:{hashlib.sha256(f'{query}|{category}|{freshness}'.encode()).hexdigest()}"
    if redis:
        cached = await redis.get(key)
        if cached:
            d = json.loads(cached)
            d["cached"] = True
            return SearchResult(**d)

    # ---- 2) 域名策略（§4.7）----
    payload = {"query": query, "count": 10, "answer": True, "stream": False}
    if freshness != "noLimit":
        payload["freshness"] = freshness
    dom = DOMAIN_POLICY.get(category, {})
    if dom.get("include"): payload["include"] = dom["include"]
    if dom.get("exclude"): payload["exclude"] = dom["exclude"]

    # ---- 3) 调用 ----
    async with httpx.AsyncClient(timeout=8) as c:
        r = await c.post(BOCHA_URL, json=payload,
                         headers={"Authorization": f"Bearer {BOCHA_KEY}"})
        if r.status_code == 403:
            return _fail("额度不足", category)
        if r.status_code == 429:
            return _fail("查询过于频繁", category)
        r.raise_for_status()
        raw = r.json()

    result = _normalize(raw)                       # 见 §4.7 的裁剪策略

    # ---- 4) 回填缓存 ----
    if redis:
        await redis.setex(key, CACHE_TTL.get(category, 86400),
                          json.dumps(asdict(result), ensure_ascii=False))

    # ---- 5) 审计 ----
    await audit_log(category=category, query_digest=key[:16],
                    log_id=result.log_id, cached=False)
    return result
```

**ReAct 侧（`04` §五）对应关系：**

```
① 发 messages + tools  → ② finish_reason == "tool_calls"，name == "web_search"
③ 校验 arguments（category 必须在枚举内！）
④ await web_search(...)   → ⑤ 追加 {role:"tool", content: 裁剪后的结果}

```

### 4.7 ⭐ 老年人场景的安全与体验设计

**这是本方案区别于"随便接个搜索"的地方。**

#### （1）按类别分级处理

| `category` | 数据来源 | 处理策略 |
|---|---|---|
| `weather` | 博查**天气模态卡** | ✅ 直接可用。可触发 `04` §四 场景：提醒增减衣物、带伞 |
| `encyclopedia` | 百科卡 + 摘要 | ✅ 直接可用 |
| `news` | 新闻结果 | ⚠️ 只取标题级信息，**不展开争议性话题** |
| `life` | 生活小问题（菜谱等） | ✅ 可用，长度受限 |
| **`health`** | 医疗卡 + 网页 | 🔴 **降级处理**：只给"这类问题建议问医生或子女"的引导，**不给具体医疗建议** |

**为什么 `health` 要降级**（对照 `04` §十一 三条红线）：
1. 搜索结果里医疗内容质量参差，**不能当医嘱**
2. 老人是**保健品/理疗仪诈骗**的主要目标人群
3. "不做医疗判断"是已定原则（`04` §十一）→ 搜索也不能绕过

#### （2）域名策略

```python
DOMAIN_POLICY = {
    "health": {   # 只信权威源
        "include": "nhc.gov.cn|dxy.cn|msdmanuals.cn|yiigle.com",
    },
    "news": {
        "exclude": "*.ad.*|*.shop.*",     # 占位，实际需维护黑名单
    },
}
```
> ⚠️ `include` 域名清单需**实测调优**（`12` T-49）；黑名单需持续维护。

#### （3）结果裁剪（老人的信息长度偏好是"简短"）

| 项 | 处理 |
|---|---|
| `answer` 长度 | 截断到 **≤120 字**（`04` §7.1 的"优先简短"） |
| 卡片 | 只保留与问题直接相关的字段 |
| `sources` | **语音场景不念 URL**，只保留站点名（"据中国气象局"）；UI 端可展示完整来源 |
| 原始正文 | **不进上下文**（token 与安全双重考虑） |

#### （4）铁律延伸：**搜索层也不直接说话**

`ai-search` 的 `answer` 是博查的 LLM 生成的，**风格不可控**（可能很长、可能用书面语）。

> ✅ 正确做法：把 `answer` 作为**工具结果**返回给 Qwen，
> 由 Qwen 按 `04` §七 的沟通策略（简单表达、简短、可重复）**重新组织语言**。
>
> → 这是 `04` §1.3 铁律 1 的延伸：**任何外部内容都不直接念给老人，都要经过语音层翻译。**

#### （5）"答不上来"时的行为

```
搜索结果为空 / 相关度过低
   → 不编造。Qwen 说："这个我不太确定，要不我帮您问问家里人？"（可转 request_task）
```

### 4.8 缓存与限流

| 项 | 策略 |
|---|---|
| **缓存** | Redis，key = `sha256(query\|category\|freshness)`；TTL 按类别（天气 30min、新闻 1h、百科 7d） |
| **为什么缓存重要** | 老人**会反复问同样的问题**（"今天天气怎么样"），命中率天然高，直接省钱 |
| **限流** | 每用户 3 次/分钟、50 次/天；全局 QPS 上限 |
| **降级** | 限流触发或额度耗尽 → 不静默失败，Qwen 说"我查得有点多，稍等一下好吗？" |
| **成本** | 免费 1000 次；超出后按次计费（**具体单价待核实**，`12` T-48） |

### 4.9 可观测性

| 记录项 | 用途 |
|---|---|
| `log_id` | 博查官方排错凭据（出问题时要提供） |
| `query` 摘要（哈希） | 隐私友好：不落原文明文 |
| `category` / `cached` / 耗时 | 命中率与成本分析 |
| 结果条数与是否为空 | 判断查询改写质量 |

> 进 `03` §五 的审计体系；对应 `10` 的 E-13/E-14 思路。

### 4.10 与两层架构的关系

`04` §十六 曾留了一个待确认：**语音层是否允许直接调 `web_search`？**

**结论：允许，且同一个实现暴露两个入口。**

| 入口 | 调用方 | 场景 |
|---|---|---|
| **语音层工具** | Qwen | "今天天气怎么样"——无副作用、延迟敏感、不涉事务状态 |
| **事务层工具** | MaaS | 任务需要外部信息时，如"帮我记一下：周三去体检"→ 先查医院信息再建事项 |

**为什么这样不违反 `04` §1.3 的"窄接口"原则**：
该原则要防的是**两层都在判意图**（谁来决定"这是不是一个事务"）。
而 `web_search` 是**纯查询**，不涉及意图判断、无副作用、不需要授权 → 不会造成分叉。

### 4.11 待确认

见 `12` §二（T-48～T-52）。

## 五、华为云 MaaS

### 5.1 是什么

> **MaaS（Model as a Service，模型即服务）** 是华为云的一站式大模型调用与托管服务。
> 把主流大模型预置好、免部署、按 Token 计费地开放出来，
> **不需要自己买卡、部署、运维**，一个 HTTP 请求就能调用。

**官方定义**：

> "MaaS 是一种基于 AI 算力适配主流大模型的服务模式。它作为企业与开发者的大模型敏捷应用枢纽，
> **免除了用户自行进行模型训练、部署与运维的高昂成本**。"

**与已有技术的关系（容易搞混）：**

```
CodeArts 代码智能体   ← 【开发工具】赛题一强制
       │  官方明确"兼容主流 AI 工具……支持华为云码道（CodeArts）"
       └─→ MaaS 可作 CodeArts 的模型后端
MaaS 模型即服务       ← 【推理引擎】我们要用的
ModelArts             ← 【底层平台】MaaS 是它的一个能力面，需配委托授权
SIS 语音交互服务       ← 【ASR/TTS】分段式
```

**四个选它的理由：**
1. **赛题一的"华为云"技术栈体现**
2. **支持工具调用**（OpenAI 兼容的 `tools` / `tool_choice`）—— Agent 的命脉
3. **有上下文缓存折扣**，官方明说"特别适用于**多轮对话、工具调用**" → **精确命中我们的场景**
4. **是华为云自家产品，代金券理论上可覆盖**（而 Qwen/豆包必须自付）

### 5.2 可用模型（**仅"西南-贵阳一"**）

### 5.3 选型建议（两条硬约束驱动）

**约束一：`tool_choice` 支持度不同** — openPangu 只有 `none`/`auto`；需要**强制调用某工具**时须用 DeepSeek / GLM。
AgeGuard 以 `auto` 为主，openPangu 够用。

**约束二：`thinking.type` 能否关闭** — **GLM-5.3 强制开思考**，
会显著拉长首 Token 时间 → **不适合实时对话**。

| 用途 | 模型 | 理由 |
|---|---|---|
| **实时对话 / 事项理解** | `openpangu-2.0-flash` + `thinking=disabled` | 低延迟；auto 工具调用够用 |
| 复杂推理 / 多假设推断 | `openpangu-2.0-pro` 或 `deepseek-v4.1-flash` | 需要更强推理 |
| 记忆闲时整理 | `deepseek-v4-flash` | 离线任务，成本敏感 |

> ⭐ **用 openPangu 作主模型，是"赛题契合度"与"技术可用性"的最佳交点**：
> 华为自家模型 + 可关思考 + 支持工具调用，三项都满足。

### 5.5 API 细节

| 项 | 值 |
|---|---|
| API 地址 | `https://api.modelarts-maas.com/v2/chat/completions` |
| 鉴权 | `Authorization: Bearer $MaaS_API_KEY` |
| 协议 | **OpenAI 兼容**（`messages` / `stream` / `tools` / `tool_choice`） |

**我们关心的请求参数**：`model`、`messages`（system/user/assistant/tool 四种 role）、`stream`、
`tools`、`tool_choice`、`thinking.type`、`prefix`（前缀续写）。

**响应关键字段**：

| 字段 | 说明 |
|---|---|
| `choices[].finish_reason` | `stop` / `length` / **`tool_calls`** |
| `choices[].message.tool_calls[]` | `id` / `type`(仅 `function`) / `function.name` / `function.arguments`（**JSON 字符串**） |
| `choices[].message.reasoning_content` | 思维链（仅深度思考模型） |
| `usage.prompt_tokens_details.cached_tokens` | **缓存命中 token 数** ← 成本监控 |
| `usage.completion_tokens_details.reasoning_tokens` | 思考消耗 |
| `first_token_return_time` | **流式首 Token 返回时间** ← 延迟监控 |

**工具调用示例（官方，已验证）：**

```python
import requests, json

url = "https://api.modelarts-maas.com/v2/chat/completions"
api_key = "MAAS_API_KEY"          # ← 从环境变量读，不要硬编码

data = {
    "model": "openpangu-2.0-flash",
    "stream": False,
    "messages": [
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user",   "content": "北京今天天气怎么样？"},
        {   # 上一轮 assistant 返回的 tool_calls 原样带回
            "role": "assistant",
            "reasoning_content": "...",
            "content": "",
            "tool_calls": [{
                "id": "call_df646371a477403597ad63c4",
                "type": "function",
                "function": {"name": "get_weather",
                             "arguments": "{\"city\": \"北京\", \"unit\": \"celsius\"}"},
            }],
        },
        {   # 我们执行工具后的结果回传
            "role": "tool",
            "tool_call_id": "call_df646371a477403597ad63c4",
            "content": "{\"city\": \"北京\", \"temperature\": 26, \"condition\": \"晴\"}",
        },
    ],
    "tools": [{
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的实时天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"},
                    "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]},
                },
                "required": ["city"],
            },
        },
    }],
    "tool_choice": "auto",
}

resp = requests.post(url, headers={
    "Content-Type": "application/json",
    "Authorization": f"Bearer {api_key}",
}, data=json.dumps(data))
```

**对应 `04` §五 的 ReAct 循环：**

```
① 发 messages + tools      → ② 若 finish_reason == "tool_calls"
                                取出 tool_calls[].function.name / arguments
③ 校验 arguments（确定性层！）→ ④ 执行工具
⑤ 追加 {role:"tool", tool_call_id, content}
⑥ 再发一次                  → ⑦ finish_reason == "stop" 时返回最终回复
```

> ⚠️ **官方明确警告**：*"模型并不总是生成有效的 JSON，并且可能会虚构出一些您的函数参数规范中未定义的参数。
> 在调用函数之前，请在您的代码中验证这些参数是否有效。"*
> → 直接对应 `04` §1.4 的**确定性校验层**。

### 5.6 缓存命中优化（省钱关键）

官方原文：

> "上下文缓存旨在优化您调用模型服务的体验……**命中缓存的输入享有折扣优惠**。
> 这一机制**特别适用于多轮对话、工具调用**、角色扮演等场景。
> **无需额外配置**。用户发起请求时，系统会自动识别请求内容的**公共前缀**并进行缓存。"

**落地策略——把 prompt 设计成"稳定前缀 + 变化后缀"：**

```
[ 稳定前缀 —— 尽量长、尽量不变 ]           ← 会被缓存
  ① system 人设（04 §七 的沟通原则）
  ② 工具定义（04 §五 的 12 个 tools，JSON schema 很长）
  ③ 老人画像摘要（记忆里的 preference）
[ 变化后缀 ]                                ← 不被缓存
  ④ 最近 N 轮对话
  ⑤ 当前这一句
  ⑥ 召回的长期记忆片段
```

监控 `usage.prompt_tokens_details.cached_tokens`。

> ⚠️ 官方也提示"缓存命中率**不确定**"，且未命中时"首 Token 时延可能会有一定程度的增加"。
> → **缓存是成本优化，不是延迟优化**。延迟靠 `thinking.type=disabled` 控制。

| **按需计费** | 按 Token，用多少付多少 ← 主用 |
