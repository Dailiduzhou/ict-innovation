## 一、为什么"要推送"必然导致"先做 Android"

这不是偏好问题，是**平台能力**问题：

| 平台 | 后台推送能力 | 结论 |
|---|---|---|
| **Android** | 有厂商系统级通道（华为 HMS Push 等），可在 App 未运行时送达 | ✅ 可做 |
| **iOS** | APNs 需**付费开发者账号（$99/年）+ 真机调试证书** | ❌ 学生团队成本高，二期 |
| **Web / PWA** | Web Push 依赖浏览器与推送服务；国内 Chrome/FCM 链路不可用；iOS Safari 限制多 | ⚠️ 只能做在线时的 WebSocket 提示，**不是真正的离线推送** |

**所以：要"子女在 App 没打开时也能收到事项通知"这个核心闭环，Android 是唯一现实选项。** 这个推理过程本身应该写进申报书——它是**能力边界推导**，体现判断力。

### 2.3 ❗ 更正：**荣耀不是华为**（重要的前提错误）

很多人把"华为荣耀"当一类，但**荣耀已于 2020 年从华为拆分**，推送通道也已独立：

| 依据 | 内容 |

> ❗ **结论：荣耀新机型必须接 HONOR Push，HMS Push 对它们无效。**
> → 这也纠正了 `11` 早期版本和聊天中的表述。

## 三、推荐架构：双通道 + 统一抽象

```
                       事项状态变更
                            │
                            ▼
                  ┌───────────────────┐
                  │  NotifyService     │  ← 确定性程序（04 §1）
                  │  频率限制 / 静默时段 │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  PushChannel(端口) │  ← 与 09 的数据源抽象同构
                  ├───────────────────┤
                  │ HmsPushChannel    │  主通道：App 离线也能收
                  │ WebSocketChannel  │  兜底：App 在线时走长连接
                  │ (MockPushChannel) │  演示/测试用
                  └───────────────────┘
```

**关键设计（与 `09` 的端口—适配器一致）**：

```typescript
interface PushChannel {
  capabilities(): Promise<{
    available: boolean;
    requiresDeviceVendor?: 'huawei' | 'any';
    supportsOffline: boolean;     // 离线能否送达
    unavailableReason?: string;
  }>;
  register(deviceToken: string, userId: string): Promise<void>;
  send(userId: string, payload: PushPayload): Promise<SendResult>;
}
```

**发送策略**：
1. 优先 `HmsPushChannel`（**通知消息**，离线可达，见 §4.3）
2. 若不可用 → `WebSocketChannel`（仅 App 在线可达）
3. 两者都不可用 → **不静默失败**，在双端 App 内留下"未读事项"红点（拉取兜底）

> **`capabilities()` 驱动降级**——与 `09` 同一套机制。UI 上亲属端可显示"当前设备暂不支持离线提醒"。
>
> ⚠️ **关键设计约束**：主通道**必须用通知消息而非数据消息**，否则 JS 线程被回收时会丢消息（见 §4.3）。"。

## 四、客户端技术选型（✅ 已定 D-07b）

> ✅ **决议（2026-10-14）D-07b**：
> **UI/业务逻辑 100% 用 TypeScript + React Native 写；
> Android 原生（Kotlin）仅承担推送、桌面小组件、签名、Manifest 声明等 RN 覆盖不到的部分。**

### 4.1 这个边界的含义

```
┌─────────────────────────────────────────────────────────┐
│  TypeScript + React Native  ← 100% UI 与业务逻辑         │
│  · 页面 / 导航 / 状态管理 / 主题（适老化大字大按钮）       │
│  · 与后端的所有 HTTP / WebSocket                        │
│  · PushChannel 抽象层（TS 实现，调 native module）        │
│  · 领域逻辑：事项状态机（客户端侧）、证据等级渲染、        │
│    能力声明驱动的 UI 降级                                  │
└───────────────┬─────────────────────────────────────────┘
                │  ★ 所有跨边界调用必须走 TS 类型定义
                │    （Codegen 由 TS spec 生成 Kotlin 抽象类）
┌───────────────▼─────────────────────────────────────────┐
│  Kotlin（仅 RN 覆盖不到的）                               │
│  · PushModule（HMS Push 的桥接，优先用官方 RN 插件）       │
│  · WidgetProvider（桌面小组件：RemoteViews / Glance）    │
│  · 签名 / Manifest / ProGuard / gradle 配置              │
│  · （可选）BootReceiver / 前台服务保活                   │
└─────────────────────────────────────────────────────────┘
```

**纪律**：Kotlin 侧**不写业务逻辑**。它只暴露窄接口（拿 token / 监听消息 / 更新小组件），
业务判断全部在 TS。否则两边逻辑分叉后无法维护。

### 4.2 ⭐ 好消息：推送有官方 RN 插件（但新架构下风险升高）

| 项 | 内容 |
|---|---|
| 包名 | **`@hmscore/react-native-hms-push`** |
| 维护方 | **HMS Core 团队（第一方插件）** |
| 仓库 | <https://github.com/HMS-Core/hms-react-native-plugin> |
| 许可 | Apache-2.0 |
| 最新版 | **`6.13.0-302`**（2026-08 发布） |
| 包内含 | `android/`（原生）+ `src/index.d.ts`（**TypeScript 类型定义**）+ `example/` |
| 周下载量 | 约 3.3K ~~ 5.3K |
| 健康度 | 第三方评估："Modestly maintained"（维护一般）、"Pretty popular"、"Security Needs attention" |
| ⚠️ 架构 | **旧架构 Native Module 写法**（非 TurboModule） |
| ⚠️ 已知 open issue | `#286` fails to build Android with RN 0.72.0（5 👍，仍 open）<br>`#301` Android build error v0.72.6 [HMS-PUSH]（仍 open） |

**意义**：**如果**它能用，你们的 Kotlin 工作量从"写一套 HMS Push 桥接"降到"接一个现成插件 + 少量适配"。

> ⚠️ **但在 RN 0.82+ 上这个"如果"很不可靠。**先看 `11` §4.2.1。

**⚠️ 三个必须注意的风险**：

1. **版本对齐**：插件版 `6.13.0-302` 对应 HMS Push SDK `6.13.0.301`。升级时要**两边一起看**。
2. **RN 新架构兼容性**：它是传统 Native Module 写法，在新架构下只能走 **Interop Layer**。事件（`NativeEventEmitter`）正是互操作层最容易出问题的地方。
3. **"Modestly maintained"**：维护频率一般；且仓库里针对 RN 版本升级的构建问题 **issue 仍处于 open 状态**。

#### 4.2.1 🔴 必须先知道的事实：旧架构已被移除

核实到的 RN 官方时间线（2026-10-14）：

| 版本 | 日期 | 关键变化 |
|---|---|---|
| 0.76 | 2024-10-23 | 新架构**默认启用** |
| **0.82** | 2025-10-08 | **第一个完全在新架构上运行的版本；旧架构配置被忽略（“仅限新架构”）** |
| 0.83 | — | **移除旧架构代码** |
| **0.84** | 2026-02-11 | 继续移除旧架构组件；**Node.js 最低要求 v22** |
| **0.88** | 2026-10-12 | **当前最新稳定版**（本项目应锁定的版本级别） |

**这意味着**：

> ❗ **“使用新架构”在今天已经不是一个选项，而是唯一状态。**
> RN 0.82+ 上已经没有旧架构了，`newArchEnabled=false` 会被忽略。
>
> 所以 D-07b / T-18 实际上**不是团队的选择，而是框架给定的事实**。

**对官方插件的影响**：

- 它是旧式 Native Module → 在 0.82+ 上**只能走 Interop Layer**
- 官方文档原话：*"The Interop Layer makes it possible to use existing native modules written for the legacy architecture with the New Architecture"*
  → 即：**理论上仍可用**
- **但**：事件（推送模块的核心）正是互操作层的薄弱点；已有 RN 0.86 Bridgeless 下 `RCTEventEmitter` 失效的踩坑记录
- **结论**：**大概率要自己写 TurboModule**。→ 但这反而是好事，见 §4.7

### 4.3 ⚠️ 推送消息类型的选择（容易踩的坑）

Push Kit 支持两类消息：

| 类型 | 行为 | 需要 App 运行吗 | 适用 |
|---|---|:--:|---|
| **通知消息**（Notification） | 由推送服务直接展示在通知栏，用户点击触发跳转 | ❌ 不需要 | ⭐ **本项目选用这个** |
| **数据消息**（Data / 透传） | 传给 App，由 App 自己处理 | ✅ 需要（或需被拉起） | ❌ 不适用 |

**为什么选通知消息**：RN 的 JS 线程在后台会被系统回收。若用数据消息，
App 不在运行时**消息会丢**。而通知消息由系统级通道展示，与 JS 是否运行无关。

**落地方式**：**通知消息 + 点击跳转（Deep Link）到对应事项页**。
JS 只在被拉起后通过 `getInitialNotification()` 类接口读取跳转参数。

> 这样设计后，**推送链路完全不依赖 JS 常驻**——这是 RN 架构下的正确做法，也应在技术方案里写明。（RN 没有官方 JS 侧的离线推送能力）

### 4.4 桌面小组件（Kotlin 必须做的部分）

| 端 | 小组件建议 | 实现 |
|---|---|---|
| 老人端 | 「我有件事想说」大按钮 + 今日事项状态 | RemoteViews / Glance |
| 亲属端 | 待接手事项数 + 最新一条 | 同上 |

**技术选择**：
- `RemoteViews`（AppWidgetProvider）—— 传统方案，稳，兼容性好
- **`Glance`**（Jetpack Compose 风格）—— 写法现代，但与 RN 项目共存需额外依赖

**建议**：先用 `RemoteViews`（稳），组里有 Compose 经验再上 Glance。

> ⚠️ 小组件的数据怎么来？**不要把业务逻辑搬到 Kotlin**。
> 做法：TS 侧将“要展示的快照”写入 `SharedPreferences` / 本地 DB，
> Widget 只负责**读快照 + 渲染**。这样业务逻辑仍在 TS。

### 4.5 为什么其他方案被否决（备案）

| 方案 | 否决理由 |
|---|---|
| Flutter | 团队是 Web 背景，**TS 比 Dart 复用度高**；且用户已明确选 RN |
| Android 原生 Kotlin 全量 | UI 开发效率低；且无法与“Web 开发经验”复用 |
| WebView 壳 + 原生推送 | 体验差；评审可能认为技术含量低（赛题一创新性占 60%） |
| Web / PWA | 无法做离线推送（`11` §一） |

### 4.6 对赛题一的额外好处

- **CodeArts 对 TypeScript 支持好**：项目级代码生成、单元测试生成在 TS 生态里更成熟，
  有利于满足 M1（必须用 CodeArts 开发）并留下可展示的证据
- **一套 TS 覆盖两角色**：老人端/亲属端可用同一 RN 工程 + 角色判定，**降低工作量**
- **可测性好**：业务逻辑在 TS 里，可写单元测试（对接 `07` 的评测）

### 4.7 TurboModule 设计（新架构下的正确写法）

> 因为旧架构已移除（§4.2.1），本节是**唯一可行的原生模块写法**。
> 下面的 API 模式来自 RN 官方文档，可直接照抄。

#### （1）TS Spec —— 唯一的接口真相源

`src/specs/NativePush.ts`：

```typescript
import type {TurboModule, CodegenTypes} from 'react-native';
import {TurboModuleRegistry} from 'react-native';

export type PushTokenPayload = {
  token: string;
};

export type NotificationPayload = {
  itemId: string;
  deepLink: string;
  title: string;
  body: string;
};

export interface Spec extends TurboModule {
  // ---- 方法 ----
  getToken(): Promise<string>;
  deleteToken(): Promise<void>;
  /** 冷启动时从通知点击进入 → 读跳转参数（配 §4.3 的 Deep Link 方案） */
  getInitialNotification(): Promise<NotificationPayload | null>;
  /** 小组件：TS 写入展示快照，Kotlin 只读快照渲染（§4.5 纪律） */
  setWidgetSnapshot(snapshotJson: string): Promise<void>;

  // ---- 事件 ----
  readonly onTokenReceived: CodegenTypes.EventEmitter<PushTokenPayload>;
  readonly onNotificationOpened: CodegenTypes.EventEmitter<NotificationPayload>;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativePush');
```

**要点**：
- 用 `getEnforcing` 而非 `get`——模块缺失时**直接报错**，便于早期发现
- 事件用 `CodegenTypes.EventEmitter<T>` 声明，**不是** `NativeEventEmitter`

#### （2）Codegen 配置

`package.json`：

```json
{
  "codegenConfig": {
    "name": "NativePushSpec",
    "type": "modules",
    "jsSrcsDir": "src/specs",
    "android": { "javaPackageName": "com.ageguard.push" }
  }
}
```

手动生成（否则构建时自动跑）：

```bash
cd android && ./gradlew generateCodegenArtifactsFromSchema
```

Codegen 会生成抽象类 `NativePushSpec`，并**自动生成 `emitOnTokenReceived(...)` / `emitOnNotificationOpened(...)` 方法**。

#### （3）Kotlin 实现（薄层，无业务逻辑）

```kotlin
class NativePushModule(reactContext: ReactApplicationContext) :
    NativePushSpec(reactContext) {

  override fun getName() = NAME

  override fun getToken(promise: Promise) {
    HmsMessaging.getInstance(reactContext).token
      .addOnCompleteListener { task ->
        if (task.isSuccessful) promise.resolve(task.result) else promise.reject("E_TOKEN", task.exception)
      }
  }

  override fun setWidgetSnapshot(snapshotJson: String, promise: Promise) {
    reactApplicationContext
      .getSharedPreferences("ageguard_widget", Context.MODE_PRIVATE)
      .edit().putString("snapshot", snapshotJson).apply()
    AgeGuardWidgetProvider.refresh(reactApplicationContext)   // 通知小组件重绘
    promise.resolve(null)
  }

  /** 由 HMS Push 的 Service 调到 */
  fun publishToken(token: String) {
    val map = Arguments.createMap().apply { putString("token", token) }
    emitOnTokenReceived(map)          // ← Codegen 生成
  }
}
```

**要点**：
- 事件参数用 `Arguments.createMap()` 造 `WritableMap`
- **map 里的 key 必须与 spec 里 type 的属性名完全一致**（文档明确强调这点）
- 方法必须签名匹配 Codegen 生成的抽象类，否则编译报错（这正是新架构的类型安全优势）

#### （7）不需要用 Fabric

小组件是 **Android 系统级 `AppWidget`**，与 RN 渲染管线无关，**不需要 Fabric Native Component**。

→ **本项目不需要写任何 Fabric 组件。**
