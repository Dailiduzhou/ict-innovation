# 06 · 客户端与推送

> 推送覆盖的事实与出处见 `08` §六。本文件只写设计。

---

## 一、为什么 Android 优先

| 平台 | 后台推送能力 | 结论 |
|---|---|---|
| **Android** | 有厂商系统级通道（华为 HMS Push 等），App 未运行时仍可送达 | ✅ 一期 |
| iOS | APNs 需**付费开发者账号（$99/年）+ 真机证书** | ❌ 二期 |
| Web / PWA | Web Push 依赖浏览器与推送服务；国内链路不可用；iOS Safari 限制多 | ⚠️ 只能做在线时的 WebSocket 提示，**不是真正的离线推送** |

**核心闭环要求"亲属在 App 未打开时也能收到事项通知"** → Android 是唯一现实选项。
这个推导过程应写进申报书——它是**能力边界推导**，体现判断力。

## 二、推送覆盖现实

| 厂商 | 系统级通道 | 学生团队可用性 |
|---|---|---|
| 华为 | HMS Push | ✅ 个人开发者可申请（需 AGC 开通权益） |
| **荣耀** | **HONOR Push（独立）** | ⚠️ 腾讯云文档：需**荣耀开发者企业账户** |
| 小米 | 小米推送 | ⚠️ 极光文档"上架说明"：**要求必须上架应用市场** |
| OPPO / vivo / 魅族 | 各自通道 | ⚠️ 部分有上架要求 |
| 其他 Android | 无系统通道 | ❌ 只能长连接 |

> ❗ **荣耀不是华为**（2020 年已拆分），新机型 HMS 通道无效，需单独接 HONOR Push。
> 详见 `08` §六。

**结论：两个硬门槛（企业账户 / 上架应用市场）学生团队大概率拿不到 →
长连接兜底不是可选项，而是必需品。**

| 方案 | 华为 | 荣耀 | 小米/OV | 其他 | 与赛题一 | 建议 |

## 三、双通道架构

```
                       事项状态变更
                            │
                            ▼
                  ┌───────────────────┐
                  │  NotifyService     │  ← 确定性程序（04 §1.4）
                  │  频率限制 / 静默时段 │
                  └─────────┬─────────┘
                            ▼
                  ┌───────────────────┐
                  │  PushChannel(端口) │  ← 与 07 的数据源抽象同构
                  ├───────────────────┤
                  │ HmsPushChannel    │  主通道：华为设备离线可达
                  │ WebSocketChannel  │  兜底：App 在线可达
                  │ MockPushChannel   │  开发/演示用
                  └───────────────────┘
```

```typescript
interface PushChannel {
  capabilities(): Promise<{
    available: boolean;
    requiresDeviceVendor?: 'huawei' | 'any';
    supportsOffline: boolean;
    unavailableReason?: string;
  }>;
  register(deviceToken: string, userId: string): Promise<void>;
  send(userId: string, payload: PushPayload): Promise<SendResult>;
}
```

**发送策略（三级降级）：**
1. 优先 `HmsPushChannel`（**通知消息**，离线可达）
2. 不可用 → `WebSocketChannel`（仅在线可达）
3. 都不可用 → **不静默失败**，双端 App 内留"未读事项"红点（拉取兜底）

> ⚠️ **主通道必须用通知消息而非数据消息**（§七）。

## 四、客户端技术栈与 TS/Kotlin 边界

> **UI / 业务逻辑 100% 用 TypeScript + React Native；Kotlin 只做 RN 覆盖不到的部分。**

```
┌─────────────────────────────────────────────────────────┐
│  TypeScript + React Native  ← 100% UI 与业务逻辑         │
│  · 页面 / 导航 / 状态管理 / 适老化主题（大字大按钮）       │
│  · 与后端的所有 HTTP / WebSocket                        │
│  · PushChannel 抽象层（TS 实现，调 native module）        │
│  · 领域逻辑：事项状态机（客户端侧）、证据等级渲染、        │
│    能力声明驱动的 UI 降级                                  │
└───────────────┬─────────────────────────────────────────┘
                │  ★ 所有跨边界调用走 TS 类型定义
                │    （Codegen 由 TS spec 生成 Kotlin 抽象类）
┌───────────────▼─────────────────────────────────────────┐
│  Kotlin（仅 RN 覆盖不到的）                               │
│  · PushModule（HMS Push 桥接，优先用官方 RN 插件）        │
│  · WidgetProvider（桌面小组件：RemoteViews / Glance）    │
│  · 签名 / Manifest / ProGuard / gradle 配置              │
└─────────────────────────────────────────────────────────┘
```

**纪律**：Kotlin 侧**不写业务逻辑**，只暴露窄接口（拿 token / 监听消息 / 更新小组件）。
业务判断全部在 TS。否则两边逻辑分叉后无法维护。

## 五、TurboModule 设计

> RN 0.82（2025-10）起"仅限新架构"，0.83 移除旧架构代码 → **不是选项，是唯一状态**。
> 详细依据见 `08` §6.5。

### 5.1 官方推送插件的情况

| 项 | 内容 |
|---|---|
| 包名 | **`@hmscore/react-native-hms-push`**（HMS Core 团队第一方，Apache-2.0） |
| 最新版 | `6.13.0-302` |
| 结构 | `android/` + `src/index.d.ts` + `example/` |
| 健康度 | 第三方评估 "Modestly maintained"；有**仍 open** 的 RN 版本构建 issue |
| ⚠️ 架构 | **旧架构 Native Module 写法** → 在 0.82+ 只能走 Interop Layer |
| ⚠️ 关键风险 | **事件是互操作层的薄弱点**，而推送模块的核心恰恰是事件 |

**判断：大概率要自己写 TurboModule。** 但这不是坏消息——它反而是答辩的技术亮点。

### 5.2 TS Spec（唯一接口真相源）

`src/specs/NativePush.ts`：

```typescript
import type {TurboModule, CodegenTypes} from 'react-native';
import {TurboModuleRegistry} from 'react-native';

export type PushTokenPayload = { token: string };

export type NotificationPayload = {
  itemId: string;
  deepLink: string;
  title: string;
  body: string;
};

export interface Spec extends TurboModule {
  getToken(): Promise<string>;
  deleteToken(): Promise<void>;
  /** 冷启动从通知点击进入 → 读跳转参数 */
  getInitialNotification(): Promise<NotificationPayload | null>;
  /** 小组件：TS 写入展示快照，Kotlin 只读快照渲染 */
  setWidgetSnapshot(snapshotJson: string): Promise<void>;

  readonly onTokenReceived: CodegenTypes.EventEmitter<PushTokenPayload>;
  readonly onNotificationOpened: CodegenTypes.EventEmitter<NotificationPayload>;
}

export default TurboModuleRegistry.getEnforcing<Spec>('NativePush');
```

**要点**：用 `getEnforcing` 而非 `get`（模块缺失直接报错，早发现）；
事件用 `CodegenTypes.EventEmitter<T>`，**不是** `NativeEventEmitter`。

### 5.3 Codegen 配置

`package.json`：

```json
{
  "codegenConfig": {
    "name": "NativePushSpec",
    "type": "modules",
    "jsSrcsDir": "src/specs",
    "android": { "javaPackageName": "com.ageguard.push" }
  }
}
```

```bash
cd android && ./gradlew generateCodegenArtifactsFromSchema
```

Codegen 会生成抽象类 `NativePushSpec`，并**自动生成 `emitOnTokenReceived(...)`**。

### 5.4 Kotlin 实现（薄层，无业务逻辑）

```kotlin
class NativePushModule(reactContext: ReactApplicationContext) :
    NativePushSpec(reactContext) {

  override fun getName() = NAME

  override fun getToken(promise: Promise) {
    HmsMessaging.getInstance(reactContext).token
      .addOnCompleteListener { task ->
        if (task.isSuccessful) promise.resolve(task.result)
        else promise.reject("E_TOKEN", task.exception)
      }
  }

  override fun setWidgetSnapshot(snapshotJson: String, promise: Promise) {
    reactApplicationContext
      .getSharedPreferences("ageguard_widget", Context.MODE_PRIVATE)
      .edit().putString("snapshot", snapshotJson).apply()
    AgeGuardWidgetProvider.refresh(reactApplicationContext)
    promise.resolve(null)
  }

  fun publishToken(token: String) {
    val map = Arguments.createMap().apply { putString("token", token) }
    emitOnTokenReceived(map)          // ← Codegen 生成
  }
}
```

**要点**：事件参数用 `Arguments.createMap()` 造 `WritableMap`；
**map 里的 key 必须与 spec 里 type 的属性名完全一致**。

### 5.5 JS 侧消费

```typescript
useEffect(() => {
  const sub: EventSubscription | undefined =
    NativePush.onTokenReceived(({token}) => void registerDevice(token));
  return () => { sub?.remove(); };     // ← 必须 remove，否则泄漏
}, []);
```

### 5.6 工作量估算

| 文件 | 行数（估） |
|---|---|
| `NativePush.ts`（spec） | ~35 |
| `NativePushModule.kt` | ~150–250 |
| HMS 的 `HmsMessageService` 子类 | ~40 |
| `AgeGuardWidgetProvider.kt` | ~120–200 |
| **合计** | **~350–530 行 Kotlin** |

这就是 Kotlin 的全部工作量（且不含业务逻辑），其余全在 TS。

### 5.7 退路决策树

```
先试官方插件 @hmscore/react-native-hms-push（走 Interop Layer）
      │
      ├─ 能跑通 → ✅ 省下 ~350 行，直接用
      │           ⚠️ 仍要写 WidgetProvider
      │
      └─ 跑不通（概率不低）→ 写 §5.2-5.5 的 TurboModule
                 → 反而成为**答辩的技术亮点**
```

### 5.8 不需要 Fabric

小组件是 **Android 系统级 `AppWidget`**，与 RN 渲染管线无关，**不需要 Fabric Native Component**。
适老化大按钮用 RN 的 `Pressable` + 主题即可。**本项目不写任何 Fabric 组件。**

## 六、桌面小组件

| 端 | 建议内容 | 实现 |
|---|---|---|
| 老人端 | 「我有件事想说」大按钮 + 今日事项状态 | RemoteViews / Glance |
| 亲属端 | 待接手事项数 + 最新一条 | 同上 |

**技术选择**：先用 `RemoteViews`（AppWidgetProvider，稳、兼容性好）；组里有 Compose 经验再上 `Glance`。

> ⚠️ **数据怎么来**：**不要把业务逻辑搬到 Kotlin**。
> TS 侧将"要展示的快照"写入 `SharedPreferences`，Widget 只负责**读快照 + 渲染**。

## 七、推送消息类型（容易踩的坑）

| 类型 | 行为 | 需 App 运行 | 采用 |
|---|---|:--:|:--:|
| **通知消息**（Notification） | 由推送服务直接展示在通知栏，点击触发跳转 | ❌ | ⭐ **本项目选用** |
| 数据消息（Data / 透传） | 传给 App，由 App 自己处理 | ✅ | ❌ |

**为什么选通知消息**：RN 的 JS 线程在后台会被系统回收。
若用数据消息，App 不在运行时**消息会丢**。通知消息由系统级通道展示，与 JS 是否运行无关。

**落地方式**：**通知消息 + 点击跳转（Deep Link）到对应事项页**。
JS 只在被拉起后通过 `getInitialNotification()` 读取跳转参数。

> 这样推送链路**完全不依赖 JS 常驻**——RN 架构下的正确做法，应写进技术方案。

## 八、材料陈述规范

### ✅ 可以写

> "为实现**亲属在应用未启动时仍能收到事项提醒**这一核心闭环，一期客户端优先适配 **Android**：
> Android 提供厂商系统级推送通道，而 iOS 需付费开发者账号与真机证书、Web 端在国内缺乏可用的推送链路，
> 因此后两者列为二期。
>
> 客户端采用 **TypeScript + React Native** 实现全部 UI 与业务逻辑，Android 原生（Kotlin）
> 仅保留在 React Native 无法覆盖的能力边界（推送桥接、桌面小组件、签名与 Manifest 声明），
> 并通过类型化的原生模块接口通信，保证业务逻辑单点维护。
>
> 在 React Native 新架构下，原生模块统一采用 **TurboModule + Codegen**：以 TypeScript 规格文件
> 作为唯一接口真相源，由 Codegen 生成 Kotlin 抽象类与事件发射方法，实现编译期类型安全；
> 事件通过 TurboModule 的 `EventEmitter` 机制传递，替代已弃用的 `NativeEventEmitter`。
>
> 推送采用 **PushChannel 抽象**，主通道为**华为 Push Kit**（通知消息 + Deep Link 跳转），
> 并以自建 WebSocket 长连接兜底，保证不同厂商设备均可收到在线提醒。"
