# 04 · 第一次团队对齐会：会议大纲与主持话术

> **对象**：IoT 社团队友，默认没有后端、Agent 开发经验。  
> **建议时长**：75 分钟。时间安排、工作包和阶段范围均为会议建议，不是已通过的团队决定。  
> **会议目标**：大家能够用自己的话讲清产品，知道哪些已经确定、哪些仍是假设，并带着明确的下一步离开。  
> **不是本次目标**：讲完全部技术、选定所有框架、解决所有细节，或承诺完整产品的交付日期。

产品方向以 [用户](01-用户.md)、[需求](02-需求.md) 为准。本文是主持工具，不新增已批准需求，也不证明任何能力已经实现。

## 一、会前准备

### 发给队友的通知，可直接复制

> 这次主要对齐我们到底为谁做、解决什么问题、第一阶段先验证什么，不要求大家提前懂后端或 Agent。会上会先看一个具体使用故事，再解释各部分怎么配合，最后确定下一阶段的任务和验收方式。大家可以先看产品故事，准备三个问题：用户为什么需要它、哪一步最容易出错、自己愿意承担哪类工作。也请带上可投入时间和可用于测试的手机信息。

### 最少准备

- **队友**：读 [讲故事](03-讲故事.md) 的主叙事和养鱼场景；不要求读完全部技术文档。
- **主持人**：预先打开 [交互原型](../prototype/user-flow.html) 与 [对话回放](../prototype/conversation-demo.html)，选择少量片段，不逐屏讲完。
- **记录人**：打开本文末尾的会议纪要模板；人少时可兼任计时。
- **资源信息**：每人可投入时间、熟悉或愿学的方向、可借用手机／设备、预算和账号现状。能否联系到目标用户只记录招募可能性，不在群里公开家庭隐私或联系方式。
- **现场纪律**：使用虚构数据。任何真实访谈、录音或家庭试用前，先确认知情同意、采集范围、退出和删除方式；子女不能自动代老人同意。

### 演示前必须说明

> 今天看到的是设计原型和模拟回放，不是已经接通的产品。它们帮助我们讨论体验；真实语音、长期保存、提醒和消息送达是否可用，需要后续分别测试。

现有原型有待对齐细节，不能把界面出现的内容直接当成已批准规则：

- 交互原型“下次聊什么”显示了换水安排与完成反馈，但前面只展示了分享鱼近况原话的许可。不要据此讲成“确认提醒后家属就能看到”；应补齐授权或移除私人安排。见 [原型](../prototype/user-flow.html) 与 [对话演示边界](../prototype/conversation-demo/README.md)。
- 原型“手机没网时会告诉你没送到”的表述过强。应区分发送失败、终端状态未知，以及实际实现的本地提醒能力，不能保证一定知道对方有没有看到。

## 二、75 分钟议程总览

| 时间 | 环节 | 要回答的问题 | 现场产出 |
|---|---|---|---|
| 00–05 | 开场与项目现状 | 今天要对齐什么？现在做到哪里？ | 共同的会议目标与证据边界 |
| 05–15 | 用户与问题 | 谁会用？为什么打开它？ | 优先用户情境＋最重要的需求假设 |
| 15–27 | 走一个完整故事 | 用户说完后，系统应该做什么？ | 一条共同理解的使用流程 |
| 27–37 | 白话解释技术分工 | 手机、语音、Agent、后端各管什么？ | 对职责和权限边界的共同理解 |
| 37–52 | 阶段范围与关键规则 | 先做什么？什么要确认？什么不能做？ | 阶段范围草案＋规则待办 |
| 52–60 | IoT 位置与可参与工作 | 硬件为什么接？队友能承担什么？ | 可选硬件去留／验证题＋能力认领 |
| 60–70 | 任务、资源与检查点 | 谁在什么时候交付什么证据？ | 少量可执行任务、复核人、日期 |
| 70–75 | 复述与收尾 | 是否真的理解一致？ | 读回决定、保留分歧、确认下次检查 |

**控时办法**：某个技术方案争论超过约两分钟，先判断它是否阻塞当前决定。不阻塞就写入“会后查证”；阻塞则明确查证者与时间，不用现场猜测代替结论。隐私和安全前置条件不能以“以后再看”为由跳过。

## 三、逐环节主持稿

### 1. 开场：先告诉大家今天不是技术答辩（5 分钟）

**可以直接说：**

> 今天我们先不从大模型、数据库和开发框架开始。我们先想清楚：一个老人什么时候会打开这个东西，说完一句话以后，希望发生什么。把这个讲通了，再看需要哪些技术、大家怎么分工。
>
> AgeGuard 想做的是老人用手机就能使用的语音生活助理。老人可以自然聊天；系统在允许的范围内记住生活背景，把确认过的安排变成提醒。老人愿意分享时，家人可以了解少量近况、接着聊，也能留下真实回应。确实需要帮助，才形成具体请求。
>
> 目前我们有文档、交互原型和模拟回放，还没有真实语音、后台处理、存储、提醒与家庭消息贯通的完成证据。今天不是宣布功能已经做好，而是统一要验证什么。

**先划清三条线：**

- 老人自己使用也要有价值；不先要求绑定子女或购买设备。
- 我们减少的是整理和重复交代的负担，不是减少真实家庭交流。
- 不做诊断、改药或急救保证，不用“监测一切”解释产品。

**检查理解的问题：**“如果没有家属加入，也没有传感器，老人还能获得什么？”

### 2. 用户与问题：别只说“老人市场很大”（10 分钟）

**可以直接说：**

> 我们先服务的不是所有老年人，而是能够表达自己的意愿、理解基本分享选择，希望获得交流和记事帮助，又不喜欢复杂操作的人。独居、患病或者子女异地，都不是必须条件。
>
> 有些家庭里，父母愿意发很长的语音，孩子忙时听不完。但这里有一个不能跳过的问题：原来愿意跟孩子说的话，老人愿不愿意先对 AI 说？这是需要验证的假设，不是我们写进方案就成立的事实。

**现场只集中讨论三个问题：**

1. 我们最容易接触、也最可能独立受益的是哪类用户情境？不要用真实姓名公开讨论。
2. 老人第一次为什么打开它：记住一个安排、获得提醒，还是想交流？谁帮助首次安装和使用？
3. 相比现有微信／电话＋闹钟，哪一步值得改变习惯？什么情况下完全没必要用我们？

**要记录的不是“大家觉得不错”，而是：**

- 优先验证的用户情境与首次使用理由。
- 一条最重要的待验证假设，以及可能推翻它的反例。
- 谁去找具体经历作为证据；不把年轻队友代演当作老人可用性结果。

### 3. 走故事：先让所有人看见同一个产品（12 分钟）

**讲述用语，人物和对话均为虚构：**

> 陈阿姨打开手机说：“那几条鱼今天好多了，小林小时候就爱看它们。周六九点提醒我换水……不，十点。还有，想请小林回来时带一袋鱼粮。”
>
> 我们不能只把它总结成一个待办。这里有她的生活、一个家庭回忆、她自己的安排，以及一件想请家人帮忙的事。它们应该走不同的处理方式。

| 这句话里的内容 | 用户应该获得什么 | 系统不能擅自做什么 |
|---|---|---|
| 喜欢养鱼、鱼的近况 | 在允许的范围内记住，下次可以接着聊 | 保存所有话，或凭一次表达形成永久判断 |
| 小时候看鱼的回忆 | 她愿意时，分享给指定家人，成为联系话题 | 自动共享全部聊天或个人档案 |
| 九点改十点的安排 | 按最后明确意愿落实提醒，能查询、修改和取消 | 建两条提醒，或把一次安排变成永久周期 |
| 请小林带鱼粮 | 核对接收人与内容后发送，可答应、协商或拒绝 | 自动广播给全家，或假装小林已答应 |

**演示方式：**

- 选看“改口”“分享确认”“保存失败”三个片段；不连续播放全部原型再讲全部架构。
- 说明下次会话仍能找到获准保留的背景，是未来要实测的目标，不是页面播放就证明完成。
- 补充一个无任务场景：“今天花开了，想随便聊聊。”没有提醒和求助，也应允许自然交流。
- 家人回应必须是真人发送；系统不知道的微信聊天、外部电话，不记成已经发生。

**提问：**“哪部分只是私人记忆？哪部分需要额外分享许可？哪部分才需要接手处理？”

### 4. 解释技术：Agent 不是万能后台（10 分钟）

**可以直接说：**

> 可以把系统理解成接待员、整理助手、规则审核、正式记录本和闹钟。接待员负责和老人说话；整理助手理解哪些信息可能值得保留、要不要查询旧记录；规则审核决定这个人有没有权、有没有确认；正式记录本保存结果；闹钟负责到时执行。
>
> Agent 就是这里会根据上下文选择下一步、申请使用工具的整理助手。它可能先查记忆，再整理候选，发现时间含糊就请求澄清。它不是想怎么做就怎么做，也不需要一直不停推理。

| 名词 | 白话解释 | 本项目的职责 |
|---|---|---|
| 前端／手机界面 | 用户看见和操作的入口 | 开始／停止交流、看提醒、纠错、决定分享 |
| 实时语音 | 接待员 | 听和回应，处理播放中的插话、停顿和改口 |
| Agent | 整理助手 | 查获准记忆、理解上下文、提出候选、申请调用工具 |
| 后端业务服务 | 规则审核与执行 | 检查身份、授权、确认和版本，执行合法操作 |
| 数据库 | 正式记录本 | 保存记忆、安排、权限和消息；支持纠错删除 |
| 调度程序 | 闹钟 | 按已保存的计划执行，不靠模型临时想起来 |
| 可选设备 | 额外的信息来源 | 提供它确实观测到的存在、开关等事件 |

这是职责划分，不代表必须七个独立程序或多个模型。

**三个必讲的区别：**

> **全双工**：助理在说话时，老人也能插话并让它停下来，不必等播放完。它不等于全天监听；是否达到自然交流，还要测误打断、回声和长停顿。
>
> **并行处理**：老人继续聊天时，后台仍在整理前面说过的事。但后台没保存成功，前面就不能说“已经记好了”。
>
> **长期记忆**：不是把全部聊天一直塞给模型，而是保存允许保留、能追溯、能纠正的信息，下次按权限找回来。

**给 IoT 队友的连接句：**

> 我们熟悉的“输入、校验、保存、执行、反馈”仍然存在。AI 增加了理解自然语言和提出候选的能力，没有替代认证、可靠记录和执行规则。比如网络重发不应让执行器动作两次，在这里就对应重试不应创建两条提醒、发送两遍消息。

**检查理解的问题：**“Agent 说用户同意了，就能直接发给家属吗？到周六十点，是模型还是调度程序负责触发？”

### 5. 定阶段范围：区分产品目标与下一次交付（15 分钟）

**可以直接说：**

> 我们现在要区分三件事：最终产品承诺、先跑通的一条流程、下个检查点能拿出的证据。它们不是同一张清单。不能今天想到一个功能，就变成所有人下周都必须交付。
>
> 可以先限制手机范围、家庭人数和具体场景，也可以按阶段实现；但不能把分段录音称为全双工，把模拟通知称为真实送达，或者把暂未实现的权限保护称为已经安全。

**先确认既有方向，不重新当作自由选项投票：**

- 手机是基础入口；硬件可选。
- 全双工与并行 Agent 是核心目标；分段录音只是开发或明确降级方式。
- 个人长期记忆、受控提醒、经授权的家庭连接是主线。
- 子女端不只有任务；普通分享、联系邀请、明确求助分开处理。
- 可靠存储、权限、纠错删除和失败反馈不能因赶演示而取消。

**会上必须收拢的四件事：**

| 事项 | 本次要得到的结论 | 尚不能决定时怎么办 |
|---|---|---|
| 优先验证什么价值 | 先验证老人交流／记事，还是家庭理解／回应；另一条仍保留在产品目标中 | 指定访谈或原型比较，不凭喜好下结论 |
| 第一个阶段场景 | 指定入口、用户、成功结果和一个失败分支；写清平台与测试条件 | 先安排小实验，确认可行性再承诺日期 |
| 保存、执行与分享边界 | 哪些明确意愿可以落实，哪些要再问；未回答、拒绝、改口怎么处理 | 写成待定规则；未定高风险动作不进入真实试用 |
| 下一检查点范围 | 哪些任务启动、哪些明确不启动，拿什么证据验收 | 按人力和依赖裁剪，不把所有工作默认交给后端 |

**可供讨论的起步方案，不是现有决定：**

- 早期并行做两件事：指定手机上的真实双向语音／打断／后台处理小实验，以及用户首次使用理由和家庭视图原型验证。
- 再逐步贯通：获准记忆保存→结束会话后召回→一个生活提醒及修改取消→授权近况与话题→家人真实回应及明确求助。
- 起步可以先限制为普通话、指定 Android 手机、一位获授权亲属、单次生活提醒和文字留言；哪些限制适用，会上按资源确认。这是阶段范围建议，不是删除其他核心目标。
- 不把复杂周期规则、多亲属协作、多个平台、更多媒体形式和硬件接入同时压进首个检查点；明确求助的完整流程仍须在后续核心验收中验证。

**需要写下的最低规则：**

1. 普通生活记忆是否能自动保存、保存什么、保留多久，需有本人理解的明确设置；不默认无限保存全部音频和文字。具体规则设负责人，真实采集前定案。
2. 明确语音可以作为确认输入，但须对应当前用户、动作和版本；含糊时间、接收人或敏感分享需要核对，不能只让模型填“已确认”。
3. 收起、没回答不等于同意。改口后的旧结果不能继续生效。
4. 记住、创建提醒、分享给家属是不同权限；默认私人，不因亲属关系自动开放。
5. “正在处理”“保存成功”“发送失败／终端状态未知”“本人已反馈”分开表达；拒绝分享不向家属留下暗示。

**防止推责的解释：**

> 某手机系统限制后台，这是要限定实测范围的外部条件；我们暂不做语音盒，是投入取舍；如果提醒重复执行、没有授权就共享，则是系统需要解决的问题。三者不能混为一谈。现在没有实现证据，也不等于已经发现了某个线上运行漏洞。

### 6. IoT 放在哪：不为了有硬件而接硬件（8 分钟）

**可以直接说：**

> IoT 社团可以做一个以手机为核心、可接设备的产品，不必先造两个盒子。硬件应该回答：接上它以后，用户少输入了什么、少受了什么打扰？如果答不上来，它就先作为探索，不占主线交付资源。
>
> 传感器看到的事实也有边界。检测到区域里有人，不等于知道是陈阿姨；药盒打开，不等于已经服药。我们可以利用具体观测，但不能把它包装成不存在的判断能力。

**硬件只选一个验证题，或者明确本阶段不启动：**

- 想改善哪个具体动作或互动时机？没有设备时如何完成？
- 设备实际提供什么字段？如何认证、绑定、处理离线和旧数据？
- 自建或第三方的接口、SDK 语言／平台、权限和成本，由谁核查？未核查不声称支持。
- 通过什么有／无设备对照，判断增益值得维护成本？

**不写后端也能认领的工作：**真机音频与后台测试、用户访谈和原型走查、重复／乱序事件测试、设备适配、隐私边界检查、联调与独立复现。实现、测试、文档都需要负责人，不把“不会 Agent”变成无法参与的门槛。

### 7. 分工：认领可检查的产物，不认领一句“负责 AI”（10 分钟）

**可以直接说：**

> 分工不写“你做前端、我做 AI”就结束。每项至少写清：谁主责、谁复核、交付什么、什么情况算通过、依赖谁，以及何时检查。下次我们看产物和失败记录，不只听“还在研究”。

下面是工作包菜单，**不是全部下周启动的清单**。按人数和可投入时间选少量任务，必要时合并；实现不了的写明不启动。

| 工作包 | 可检查的产物 | 主要依赖／关联任务 |
|---|---|---|
| 用户与首次使用 | 合规访谈／概念测试记录，说明具体经历、反例、首次使用理由和原型问题 | 招募与同意流程；T-79／80 |
| 手机语音小实验 | 指定真机的双向音频、播放中打断、长停顿和失败记录；说明平台和条件 | 账号、音频接口与框架核查；T-76 |
| 并行整理小实验 | 对话与后台事件时间线，改口使旧候选失效、重复输入不重复处理的测试 | 来源与事件契约；T-77 |
| 个人记忆与提醒 | 保存／读取／纠错、单次提醒修改取消与重启测试，不只展示模型回答 | 业务规则、存储与身份边界；T-78／81／83 |
| 家庭视图验证 | 授权近况、联系前回顾、真实留言、明确求助的走查；含无待办与拒绝分享 | 共享规则；T-80／82 |
| 可选设备探索 | 一份具体型号、合法通路、真实字段、时间质量与增益测试方案 | 预算、SDK／权限核查；T-84，仅选用时启动 |

任务编号仅供会后查 [风险与待验证](../ideas/12-风险与待验证.md)，不要求队友会上记住。

**同时问清四项资源：**

- 每人本阶段真实可投入多少时间，谁能协助学习和联调？
- 哪些测试手机、账号、权限已经有证据可用，哪些只是计划申请？
- 预算上限和付费操作由谁确认？语音服务费用、云资源、设备费用分开，不默认代金券覆盖所有账单。
- 下次检查的具体日期是什么？可建议约一周后，但以团队现场确认日期为准。

### 8. 复述与结束：检查理解，不只问“大家懂了吗”（5 分钟）

请不同队友分别用自己的话回答：

1. “为什么老人没有子女加入也能用？第一次会为了什么打开？”
2. “什么不能由 AI 自己决定？什么内容家属默认看不到？”
3. “我下一次交付什么，谁来复核，用什么证明完成？”

**收尾可以直接说：**

> 我读一下今天真正确定的内容。这里哪些是沿用的产品方向，哪些只是本阶段临时方案，哪些还要验证，我们分别标记。没解决的问题会保留，不把今天没人反对当成已经证明可行。
>
> 下次我们不要求所有功能都完成，而是检查约好的证据。如果用户不愿意用，或者真机链路不支持预期，我们就根据证据调整，不能靠更漂亮的演示跳过问题。

## 四、解释和控场速查话术

| 队友的问题／现场情况 | 可以直接用的说法 |
|---|---|
| “不就是一个语音聊天软件吗？” | “自然聊天是入口。我们还要验证聊过的信息能否跨次使用、确认的安排能否以后执行，以及家人能否在授权下接着交流。这些是拟验证的组合价值，不是说别的产品都没有。” |
| “是不是用 AI 替孩子陪父母？” | “不是替孩子编造关心。系统帮助整理上下文，转达真人回应；如果孩子省时了、老人却觉得被敷衍，也不能算成功。” |
| “Agent 就是调用一次模型吗？” | “调用模型可以是其中一步。Agent 还会根据当前结果选择查记忆、提出候选、请求澄清或申请工具调用；执行次数、费用和权限都有边界，不是无限循环。” |
| “先让 AI 全做了，再加限制？” | “保存、发消息、改提醒会影响真实的人。权限和确认是基础路径，不是演示之后才补的装饰；没有这些，只能用明确隔离的虚构数据做实验。” |
| “每件事都要再问，会不会很烦？” | “会，所以要区分明确意愿和系统猜测。目标是少重复确认，不是少授权；具体规则需要用例和老人可用性验证。” |
| “没网就是我们没办法吧？” | “网络是外部条件，但保存计划、记录未知、恢复时不重复、对用户如实说明是我们的责任。能否离线提醒，要看实际实现和测试。” |
| “接个传感器就算 IoT 创新吗？” | “先说明它帮用户少做哪一步，再证明实际观测和独立增益。事件数量、设备数量本身不是价值。” |
| “先定用哪个框架？” | “先把要验证的手机能力和验收条件写清，再用小实验比较。今天可以定谁去测，不必在没有证据时选死。” |
| “这个设想很棒，顺便加上吧。” | “先放进候选区，写明用户收益和依赖。只有排了资源、定义了验收，才进入本阶段范围。” |
| “比赛要求一定要有某个设备吗？” | “赛事硬要求按现有官方核查记录并复核当届通知，不用旧稿印象下结论。开发工具／Skills 和产品运行时 Agent 也不是一回事。” |
